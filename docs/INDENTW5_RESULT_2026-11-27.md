# INDENTW5 결과 — 폭 표 내어쓰기 추가 시간

## 결론

- 작은 문서의 추가 시간은 대부분 **사용 중인 스냅샷을 지우려는 재시도 대기**였다. 대기를 없앴다.
- 확정 문단이 59개 미만이면 자동으로 기존 한/글 방식을 쓴다. 14문단 문서는 켬·끔의 COM 호출 수가 같고 시간 차이는 반복 편차 안이다.
- 59·299문단 합성 문서에서는 켬이 평균 4.6%·5.9% 빨랐다.
- 그래도 **모든 문서에서 느려지지 않는다고 보장할 수 없어 기본값을 끔으로 바꿨다**(아래 "기본값을 끈 이유").
- 측정한 24회(최종 코드 16회 + 크기 판정 전 코드의 300문단 8회) 모두 글·글자 모양·기타 문단 모양 차이 0, left/intent 오차 0pt, 쪽수 동일, 원본·사본 불변.

## 범위

`feature/INDENTW5`. 설치본·서비스·사용자 설정 변경, 푸시·태그·main 병합 없음.

합성 문서는 구역 설정 빈 문단을 포함해 15·60·300문단(서식 확정 14·59·299문단), HWP·HWPX, 끔/켬 각 2회다. 실제 `format` 파이프라인을 새 DispatchEx 인스턴스에서 돌렸고, `.com-test.lock`을 배타 생성한 동안에만 시간을 쟀다.

## 변경 전 비용 분해 — 실측

14문단 합성 HWPX, 설정 켬, 1회. 겹친 자식 호출 시간을 뺀 값(초). "후"는 크기 판정을 넣기 전, 삭제 대기 제거·패키지 공유만 적용한 상태다.

| 두 내어쓰기 단계의 비용 | 전 | 후 |
|---|---:|---:|
| 스냅샷 SaveAs·저장 완료 확인, 2회 | 0.833 | 0.748 |
| 패키지 읽기·안전 검사, 2회 | 0.309 | 0.281 |
| XML 파싱, 4회 | 0.010 | 0.009 |
| 환경 지문·구역·문단·글자 조건 판정 | 0.010 | 0.010 |
| 폭 계산·글꼴 검증 | 0.137 | 0.118 |
| 계획 작성 나머지·단계 준비 | 0.030 | 0.031 |
| **사용 중인 스냅샷 삭제 재시도, 2회** | **3.831** | **0.001** |
| COM 값·문단 글 재확인, 28회 | 0.209 | 0.183 |
| 순회·기존 Shift+Tab 등 나머지 | 1.566 | 1.343 |
| 두 단계 합 | 6.937 | 2.728 |

전체 시간은 32.57초 → 27.06초였다. 전후 결과 문서의 글·서식·여백 차이 0. 원자료: `docs/measurements/INDENTW5_PROFILE_2026-11-27.json`.

XML 직접 기록(일괄 서식 단계)은 변경 전 약 0.6초였고, 그중 계획 작성이 약 0.3초였다.

## 구현

- 스냅샷 삭제를 1회만 시도한다. SaveAs 뒤 한/글이 파일 핸들을 잡고 있어 기존의 20회 재시도(0.1초 간격)는 모두 실패하고 시간만 썼다. 남은 폴더는 기존의 `hwp_format_first_` 오래된 임시폴더 정리가 다음 실행에서 지운다.
- 한 저장본의 변환 확인과 계획 작성이 안전 검사를 통과한 같은 `PackageSnapshot` 바이트를 쓴다. XML 직접 기록 때 경로나 현재 바이트가 다르면 거부한다.
- 계획 하나 안에서 같은 문단 모양 참조의 판정을 공유한다.
- **단계 사이 스냅샷 재사용은 하지 않았다.** 부연설명·쪽 배치 등에서 문서가 바뀔 수 있고, 바뀌지 않았다고 증명할 값이 없어 매번 다시 저장한다.
- **자동 폴백:** XML 일괄 서식으로 확정한 서로 다른 문단 글이 59개 미만이면 저장·파싱·COM 확인 없이 기존 방식을 쓴다. 문서마다 판정을 초기화한다.
- 제외 조건, 환경 지문, COM 값 재확인, 원본 보존 조건은 바꾸지 않았다.

### 동작 범위가 좁아진 점

표 계산은 이제 표준서식 XML 일괄 적용이 성공하고 내어쓰기를 쓰는 문서에서만 동작한다. 일괄 적용을 거치지 않으면 켬이어도 모두 Shift+Tab이다(전에는 Shift+Tab 단계에서 표를 쓸 수 있었다).

## 크기별 비교 — 실측

시간은 문서 1건 전체(초), 한 칸은 1회·2회다.

| 확정 문단 | 형식 | 끔 | 켬 | COM 호출 끔 → 켬 | 코드 |
|---:|---|---|---|---|---|
| 14 | HWPX | 27.06 / 27.21 | 27.21 / 26.43 | 19,894 → 19,894 | 최종 |
| 14 | HWP | 27.44 / 27.33 | 27.53 / 27.53 | 19,898 → 19,898 | 최종 |
| 59 | HWPX | 100.22 / 93.69 | 89.47 / 89.54 | 103,366 → 97,978 | 최종 |
| 59 | HWP | 93.19 / 92.60 | 92.37 / 90.97 | 103,370 → 97,982 | 최종 |
| 299 | HWPX | 491.81 / 472.11 | 445.44 / 454.02 | 548,456 → 521,523 | 크기 판정 전 |
| 299 | HWP | 472.69 / 472.34 | 445.38 / 452.06 | 548,460 → 521,527 | 크기 판정 전 |

내어쓰기 단계만의 시간(4회 범위, 초):

| 확정 문단 | 끔 | 켬 |
|---:|---|---|
| 14 | 2.61 ~ 2.86 | 2.56 ~ 2.67 (폴백) |
| 59 | 11.21 ~ 12.26 | 7.73 ~ 8.23 |
| 299 | 63.86 ~ 65.08 | 39.12 ~ 39.85 |

- 입력 크기는 약 105~118KB, 결과 쪽수는 3·13·64쪽(끔·켬 동일)이다.
- 14문단: 켬−끔은 -0.78 ~ +0.20초, 같은 설정의 반복 차이도 1초 안팎이다.
- 크기 판정 전 코드의 14문단은 COM 호출이 6% 적었지만 내어쓰기 단계가 4회 모두 0.09~0.23초 느렸다. 이것이 폴백을 넣은 근거다.
- 59문단 HWP는 전체 시간 이득(0.8~1.6초)이 반복 편차보다 작다. 내어쓰기 단계 이득(약 3.4초)은 4회 모두 나타났다.
- 299문단은 크기 판정을 넣기 전 코드로 쟀다. 299 ≥ 59라 같은 표 경로를 타지만 **최종 코드로 다시 재지는 않았다.**

원자료: `docs/measurements/INDENTW5_PIPELINE_2026-11-27.json`(`before_size_gate`, `with_size_gate`).

16회 실측 뒤에, 크기 판정의 안내 로그가 설정 읽기 함수가 없을 때 `NameError`를 내던 것을 고쳤다(관련 시험에서 발견). 설정을 정상으로 읽는 실행의 동작은 같다. 고친 뒤의 코드로 14문단 HWP 켬 1회를 실제 한/글에서 다시 돌렸다: 27.54초, COM 19,898회(위 표와 동일), 폴백 로그 정상, 오류 0, 원본·사본 불변.

## 기본값을 끈 이유

1. 실측한 크기는 14·59·299문단뿐이다. 15~58문단의 손익분기점은 모른다(안전하게 폴백). 59는 "이득을 확인한 가장 작은 크기"이지 손익분기점이 아니다.
2. 판정 기준은 문단 수 하나다. 59문단 이상이어도 표를 쓸 수 있는 문단이 적은 구성(미검증 글꼴·조건 위주)은 저장 비용만 들 수 있고, 재지 않았다.
3. 한 대의 PC, 한 한/글 판, 합성 문서만 쟀다.

## 시험

| 묶음 | 결과 |
|---|---|
| 내어쓰기·서식·파이프라인 관련 43모듈(COM 잠금 아래) | `Ran 405 tests in 79.340s` / `OK` |
| 설정·기본값·폭 표 관련 29모듈 | `Ran 335 tests in 50.508s` / `OK (skipped=8)` |

두 묶음은 일부 모듈이 겹친다. 첫 실행에서는 `NameError` 2건(위)과 기본값 대조 파일 `docs/settings_defaults.json` 미갱신 2건이 실패해 고친 뒤 다시 돌렸다.

기존 시험 `tests/test_indent_table.py`, `tests/test_indent_hwp_validation.py`는 기본값 변경에 맞춰 설정 켬을 명시하도록 고쳤다. 새 시험은 `tests/test_indent_latency.py`.

## 남은 문제·미확인

- **이미 저장된 설정:** `settings.json`에 `indent_table: true`가 저장돼 있으면 기본값을 바꿔도 켬이 유지된다. 엔진은 기본값 전체를 되쓰므로 INDENTW3 이후 코드를 실행한 환경에는 저장돼 있을 수 있다(실제 사용자 설정은 확인·변경하지 않았다). 그 경우에도 59문단 미만은 폴백한다.
- 15~58문단, 300문단 초과, 표·그림이 많은 실문서, 다른 한/글 판·PC는 미확인.
- 전체 Python 시험, Flutter, Rust 설정 창 빌드, EXE는 돌리지 않았다.
- 문서 처리 시간의 대부분은 "개별 문단 페이지 배치"(299문단에서 약 82%)다. 이번 범위 밖이다.
