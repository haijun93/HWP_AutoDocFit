# DOCDB1 — 문서뷰 목록 DB: 즉시 표시 + 바뀐 것만 반영 (2026-11-26)

기준: `github/main` + `feature/SCANSPEED1`(`1523ea96`, 병합 `1914b273`. 충돌은 `TODO.md` 하나이며 양쪽 항목을 모두 남김).

## 바꾼 것

- 공용 모듈 `docfit_app/library_db.py`(사진뷰도 쓸 수 있게 문서 전용 코드 없음)
  - `LibraryDB`: 경로·이름·확장자·폴더·size·mtime·cloud·썸네일 키·마지막 확인(`seen_at`).
  - `ViewSync`: DB 목록 내보내기 → 원천 행 비교 → 마무리. 추가·변경(`op: update`)·삭제(`op: remove`)만 이어서 보낸다.
- 화면 공용 반영 `flutter_ui/lib/features/common/library_delta.dart`.
- 문서뷰: `list_default` 는 곧바로 돌아오고, DB 목록과 변경분을 SCANSPEED1 의 `scan_progress` `since` 통로로 보낸다(묶음 최대 4,000).
- 원천은 그대로 검색 색인 서비스, 없으면 klib, 그다음 파이썬 순회. 새 파일 감시기는 없다.
- 색인 서비스 행에는 크기·수정 시각이 없어, 파일이 있는 폴더를 한 번씩 훑어 채운다. 서비스·Rust 는 바꾸지 않았다.
- DB 위치: `<앱 데이터>/library-view/documents.db`(썸네일 폴더 옆). 이전 저장 목록 `scan-cache/documents.json` 은 DB 가 비었을 때 한 번 옮겨 쓴다(파일은 남겨 둠).

## 처리 규칙

| 상황 | 동작 |
|---|---|
| 삭제 반영 | 원천을 끝까지 읽었고 행이 하나 이상이며, **디스크에 실제로 없는** 파일만 |
| 취소·실패·부분 결과·빈 응답 | 삭제하지 않음(찾은 추가·변경은 저장) |
| 색인에는 없지만 파일은 있음 | 남김 |
| 색인에 남은 지워진 파일(서비스 원천) | 폴더에 없으면 삭제 반영 |
| 빠진 드라이브 | 화면에서 숨기고 DB 에는 남김 |
| 제외 폴더 | DB 에는 남기고 화면에서만 숨김(제외를 풀면 바로 보임) |
| 파일 작업(FILEOPS1) | DB 와 진행 중인 비교에 함께 반영(지운 파일이 되살아나지 않음) |
| 클라우드 전용 | 목록에서 뺌 |
| 경로 대소문자·1초 미만 시각 차이 | 변경으로 보지 않음(원천 엔진이 바뀌어도) |
| DB 손상·다른 버전 | 우리 캐시 DB 만 지우고 새로 만듦. 잠금·권한 오류로는 지우지 않음 |

DB 쓰기는 검색이 끝날 때(취소·실패 포함) 한 번에 한다. 검색 중에 앱 프로세스가 죽으면 그 회차의 변경은 남지 않는다.

## 속도에서 확인한 것

`sqlite3` 와 `os.path.normcase` 가 행마다 파이썬 실행 잠금을 놓아, 화면 폴링과 함께 돌면 크게 느려졌다(바쁜 스레드를 함께 돌린 합성 5천 건: 합계 250초 이상 → 약 5초). DB 읽기·쓰기를 SQL 문 하나(`json_each`)로 바꾸고 키를 문자열 연산으로 만들었다. 검색 중 2천 건마다 나눠 저장하던 것도 끝에 한 번으로 바꿨다.

## 측정 (합성 PDF 65,000개, 전 = `1914b273`)

`scripts/bench_library_scan.py --kind doc --count 65000 --runs first cached cached changed --source-kind service|klib`. 화면과 같은 순서로 서비스를 부르며 브리지 전달은 JSON 변환·해석으로 대신했다(설치본 시간 아님). 단위 초. 전·후를 번갈아 한 번에 돌린 마지막 회차다.

- `service`: 색인 서비스처럼 경로·이름만 주는 **모의 원천**(미리 만든 목록을 즉시 돌려줌). 설치된 서비스는 부르지 않았으므로 서비스 응답 시간은 들어 있지 않다.
- `klib`: 서비스가 없을 때의 경로.
- 첫 묶음: 화면에 항목이 처음 보이는 시점. 전체 표시: 목록이 모두 도착한 시점. 완료: 비교·저장까지 끝난 시점.

| 원천 | 상황 | 첫 묶음 전 → 후 | 전체 표시 전 → 후 | 완료 전 → 후 |
|---|---|---|---|---|
| service | 첫 열기 | 0.17 → 0.21 | 0.65 → 1.46 | 1.1 → 3.7 |
| service | 두 번째(2회) | 1.36~1.57 → 0.47~0.59 | 1.36~1.57 → 0.87~0.94 | 2.5~2.7 → 3.3~3.5 |
| service | 1% 변경 | 0.97 → 0.54 | 0.97 → 1.26 | 1.9 → 5.4 |
| klib | 첫 열기 | 0.19 → 0.28 | 3.9 → 3.8 | 5.2 → 10.2 |
| klib | 두 번째(2회) | 2.23~2.27 → 0.78~0.90 | 2.23~2.27 → 1.9~2.2 | 4.9~5.1 → 9.4~12.4 |
| klib | 1% 변경 | 1.14 → 0.92 | 1.14 → 2.2 | 3.9 → 9.7 |

1% 변경(수정 260·추가 195·삭제 195)에서 변경분이 화면에 모두 도착한 시점: service 2.7, klib 5.9. 변경 전은 목록 전체를 다시 받는 완료 시점(1.9, 3.9)이 이에 해당한다.

읽는 법:
- **좋아진 것:** 두 번째 열기부터 첫 묶음이 1초 안(0.5~0.9)이다. service 원천은 전체 목록도 1초 안, klib 원천 측정은 약 2초다. 목록 전체를 두 번 보내지 않는다.
- **나빠진 것:** 배경 비교가 끝나는 시점은 더 늦다(첫 열기 약 2~3.4배, 그 뒤 약 1.3~2.8배). 1% 변경이 화면에 반영되는 시점도 변경 전보다 늦다.
- **편차:** 같은 코드도 회차마다 크게 달랐다. 앞선 회차의 변경 전 service 값은 첫 열기 완료 2.9, 두 번째 4.6~5.9였고, 변경 후 klib 두 번째 완료는 6.4~8.8이었다. 정밀한 비교값으로 보지 않는다.
- win32 방식(klib 출력만 읽음)은 첫 줄 0.03~0.05, 전체 0.6~0.9.

## 남은 문제

- 배경 비교 완료가 변경 전보다 느리다(위 표). 원인별 시간은 다 가르지 못했다. 후보: 행마다의 비교, `seen_at` 6.5만 행 갱신, 첫 열기의 DB 삽입, 서비스 원천의 폴더 훑기.
- 실제 드라이브·설치본·실제 색인 서비스로는 재지 않았다. 폴더가 많이 흩어진 PC 는 서비스 원천의 폴더 훑기가 더 걸릴 수 있다.
- 이 PC 서비스의 `names_list` 자체가 문서 6.5만 건에 7.4~10.9초라(PM 실측) 새 파일·삭제 반영은 그만큼 늦다. 서비스가 크기·시각을 함께 주면 폴더 훑기를 없앨 수 있다.
- 원천이 비어 있으면 삭제하지 않으므로, 문서를 모두 지운 PC 는 앱 밖에서 지운 항목이 목록에 남는다.
- 사진뷰는 아직 이 모듈을 쓰지 않는다(PHOTOSYNC1).
