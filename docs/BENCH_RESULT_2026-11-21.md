# Everything 대 몽땅검색 검색 성능 측정 결과 (2026-11-21, 이 PC, 1회 측정)

측정 조건: 이 PC(Windows 11) 1대, 관리자 색인 서비스 `HwpAutoDocFit.Index`(kfind `--service`, 이 날 처음 설치·시작) 대 Everything 1.4.1(GUI 실행 중, IPC 질의). 두 쪽 모두 색인이 준비된 상태. 질의: `qms_bench sample-queries`로 저장소 파일 이름 2,787개에서 40개(seed 42)를 뽑은 세트. 반복 5회·예열 1회, 상위 1,000건 요청. 도구: `qms_bench run`(Rust). 측정은 1회차 1번만 했다(반복 회차 없음).

## 속도(질의 지연, 200회 측정 값)
| 항목 | 몽땅검색(서비스) | Everything(IPC) |
|---|---:|---:|
| p50 | 7.27 ms | 100.70 ms |
| p95 | 13.71 ms | 261.01 ms |
| 평균 | 13.59 ms | 129.35 ms |
| 최댓값 | 680.2 ms(첫 질의) | 721.9 ms |
| 첫 질의(예열) 중앙값 | 12.6 ms | 105.0 ms |

p50 기준 몽땅검색이 약 14배 빠르다. 단 Everything 쪽은 IPC 응답에 결과 1,000건 전달이 들어가는 비용이 있어 공정한 비교인지 한계가 있다(미확인). 결과 건수는 40개 질의 중 4개에서 달랐다(원인 미확인).

| 프로세스 | 작업 집합 | 전용 메모리 |

색인 항목: 서비스 3,343,333개(C: 258만, E: 76만, D: 115개), 서비스 색인 생성 31.8초. **메모리는 Everything이 전용 메모리 기준 약 절반으로 더 작다**(Everything 쪽 색인 항목 수·생성 시간은 이번에 재지 않음).

## 알려진 문제
- `scripts/qms_bench_analyze.py` 가 만든 비교 보고서에서 두 엔진의 p50·p95 열이 같은 값(1.00x)으로 나왔다. 실행 JSON을 직접 읽으면 두 엔진 값이 다르므로 분석 스크립트의 짝짓기 오류로 보인다(미수정). 위 표는 `run` 출력의 progress 줄에서 직접 계산했다.
- 측정 파일(JSON/CSV)은 저장소에 올리지 않았다.
- 이 PC에는 "합의각서"·"과업지시서" 파일이 없다(Desktop·D: 검색 결과 0, 색인 질의 0). 퀵몽땅검색 0건 보고는 다른 PC에서 서비스 없이 생긴 일일 가능성이 있다.
