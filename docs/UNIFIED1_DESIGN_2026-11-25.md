# UNIFIED1 통합 검색 계약 (2026-11-25)

## 범위와 합격 기준

설정 `unified_search`는 기본 false다. true일 때 ktm의 All 검색만 새 경로를 사용한다. 기존 검색 API·파일명 전용 모드·Python SearchBackend는 유지한다. 결과 보고는 `UNIFIED1_RESULT_2026-11-25.md`, 진행 기록은 `UNIFIED1_PROGRESS.md`다. 변경 크레이트 전체 cargo test와 전체 Python unittest가 통과해야 한다. 합성 문서 1,000개(seed 20261124)의 집합·순위 단·중복 제거를 독립 기대값과 대조한다. Everything·Docufinder 실측은 범위 밖이다.

## 현재 호출 흐름

`window::event(Effect::Search)` → Pending.search에 Names(20), Hierarchy(20), Body(40) 세 작업 → 같은 worker에서 차례로 실행 → Reply::Search → UI의 combine_results → GDI 그리기다. Names는 서비스의 names_query, 위계·본문은 기본 mmap Backend이며 --backend pipe일 때 query 파이프다. 위계 검색은 제목만 필터하는 검색이 아니라 같은 본문 일치를 위계 순으로 정렬하는 **위계기반 본문검색**이다. 이 의미는 유지한다.

기존 combine_results는 경로를 키로 대표 행을 남기되 모든 일치 종류를 한 행에 병기한다. 각 입력 배치를 상한으로 먼저 자르므로 중복 제거 후 빈 자리를 채우지 않는다. 파일명 실패 후 나머지 성공이 완료 상태·오류를 덮어쓸 수 있다. 새 경로는 결과 합성·단별 완료·오류를 backend 세션 하나가 관리한다.

MG2 기록의 과거 측정은 파일명 파이프 p50 1.08~1.27ms, mmap 본문 0.55~0.64ms, 위계 0.40ms다(합성 3,000건). 이번 변경의 기준선으로 오인하지 않는다. 현재 소스·1천 건의 측정과 단계별 시간은 결과 문서에 따로 기록한다.

## 요청과 응답

- 입력: query, names sort, 본문 범위(기간·폴더·확장자), match_mode, 화면 총상한(최대 80), 취소 Arc. 이름·위계·본문에 같은 입력 하나를 사용한다. 공통 파서의 `;` 묶음 안 AND → 묶음 간 문서 교집합을 재사용한다. 파일명은 이름 전체가 한 단위이고, 서로 다른 단끼리 묶음의 일부를 합쳐 일치로 만들지 않는다.
- 세 단의 정의: names_query 반환 후보 → 위계 순위 query 후보 → 본문 관련도 query 후보. **단은 기존 검색 방식의 우선순위**이며 제목 수준 필터를 새로 만들지 않는다. 한 문서가 여러 후보 목록에 있으면 파일명 > 위계 > 본문에서 하나만 반환한다.
- 각 원천 후보는 최대 200건, 출력 단별 상한은 20·20·40건이다. 순서가 정해진 후보 목록에서 중복을 제거한 뒤 단별 상한을 적용한다. 상위 단의 표시 상한 때문에 숨은 후보도 하위 단으로 재등장하지 않는다. 각 단 안의 원래 정렬 순서는 유지한다. 화면 총상한은 마지막에 적용한다.
- 이 계약은 **반환 후보 창 안의 통합 목록**이다. 전체 결과를 전수 열거하거나 200건 밖의 상위 단 일치를 판정한다고 주장하지 않는다. 더 큰 결과의 페이지 처리·전역 단 배정은 후속 단계다. 후보 창을 넘어선 문서가 본문 단에 나타날 수 있다. 무제한 전수 수집으로 메모리 규칙을 깨지 않는다.
- 문서 키: Windows 경로의 대소문자·슬래시·후행 구분자·점 경로·확장 경로 접두사를 정규화한다. 같은 basename의 다른 폴더는 다른 문서다. doc_id가 같은 경로 없는 행은 경로 있는 행과 연결한다. ID도 경로도 없으면 서로 다른 익명 행으로 취급한다. 심볼릭 링크·하드링크의 파일 ID 동일성은 이번 범위 밖이다.
- 행: 기존 Row 유지. match_kinds에는 선택된 단 하나만 넣는다. 이름 단은 파일명 자체가 근거이고, 위계·본문 단은 location(위계/문단)과 snippet/preview가 근거다. 원문 없는 색인에서는 위치만 표시한다. 원본을 열어 근거를 만들어내지 않는다.

## 상태·스트리밍·취소

상태는 Names → Hierarchy → Body → Complete이며 세대는 요청 전체에 하나다. 원천 실패는 해당 단을 완료 처리하고 errors에 남긴 뒤 다음 단을 실행한다. 취소 전·원천 호출 후·발행 직전에 검사한다. 취소된 세션은 더 이상 발행하지 않는다. 오래된 세대의 응답은 UI에서 폐기한다. 파일명 응답을 먼저 발행하고 다음 검색을 시작하므로 본문 완성을 기다리지 않는다. UI 스레드는 조회·파일 I/O를 하지 않고 최대 80행 교체와 상태 갱신만 한다.

기존 worker·Condvar와 최신 검색 대체를 재사용하며 새 상주 스레드·타이머·색인은 만들지 않는다. 세션의 최대 600 후보는 요청 종료 때 해제한다. 파이프는 기존 5초 제한을 유지한다. 입력→첫 그리기 16ms와 쉴 때 메모리는 별도 실측 항목이며 backend 시간만으로 달성 판정하지 않는다. 파이프 호출 도중 취소는 기존 제한시간 안에서 회수되고, 완료 이후 발행은 차단된다.

## 비교 측정 제안

같은 PC에서 각 도구에 같은 합성 파일 목록·범위·검색식·표시 상한을 사용한다. 색인 완료 뒤 각 프로세스를 순차 실행하고 cold(프로세스 첫 검색)와 warm을 분리한다. 외부 탐침의 동일 입력 시각부터 첫 파일명 결과가 실제 그려진 시각, 본문 포함 완료 그림 시각을 기록한다. 집합·정렬·단 배정·오류도 함께 저장한다. 16ms 판정은 입력→실제 GDI 결과 그림으로 하고, 엔진 계산·파이프 왕복은 별도 표로 둔다. 다른 빌드·시험은 중지한다. Everything의 본문 미지원은 파일명끼리만 비교하고 Docufinder는 지원 문법 교집합만 비교한다. 사용자 문서는 쓰지 않는다.
