# 업데이트 서명 활성화 점검 목록 (2026-11-18)

이 문서는 서명 검증을 기본 꺼짐에서 활성화하기 전에 운영자가 확인할 항목만 기록한다. 서명 형식·검증 동작·도구 사용법은 [UPDATE_SIGNATURE_DESIGN.md](UPDATE_SIGNATURE_DESIGN.md)를 참조한다.

## 키 생성과 보관

- [ ] 신뢰 가능한 전용 환경에서 Ed25519 키를 생성한다. `scripts/update_signing.py keygen --key-file <저장소 밖 경로>`를 사용할 수 있다.
- [ ] 생성한 비밀키를 접근 통제된 오프라인 보관소 또는 승인된 비밀 저장소에 보관하고, 복구용 백업과 접근 담당자를 정한다. 선택한 저장 방식·담당자·백업 복구 절차: **미확인**.
- [ ] 키 파일 권한과 백업·복구 절차를 실제 운영 OS에서 확인한다. 도구는 POSIX 모드 `0600`을 요청하지만 Windows에서의 유효한 접근 통제는 **미확인**.
- [ ] 비밀키를 저장소, 작업 산출물, CI 로그·아티팩트, 공개 문서에 넣지 않았는지 확인한다. 이 문서에는 키 값이나 토큰 값을 기록하지 않는다.

## 공개키 배포와 사전 검증

- [ ] 공개키를 독립된 신뢰 경로로 담당자에게 전달하고 지문을 대조한다. 독립 배포 채널·지문 확인 절차: **미확인**.
- [ ] 승인한 공개키를 `docfit_core/update_signature.py`에 반영하고 해당 앱 버전을 빌드·배포한다. 현재 상수는 비어 있다.
- [ ] 활성화 전 배포본에서 서명된 manifest 검증 성공, 서명 누락·변조·다른 키·잘못된 형식·미설정 키의 거부를 확인한다. 실제 릴리스 환경에서의 검증 결과: **미확인**.
- [ ] 공개키를 바꿀 때 기존 설치본이 새 키를 신뢰할 수 없음을 반영해, 새 공개키가 포함된 앱을 먼저 배포한다. 기존·신규 키 병행 신뢰를 위한 별도 키링이나 전환 기능: **미확인**.

## CI와 배포 연결

- [ ] CI 또는 승인된 서명 환경에서 빌드 산출물·SHA256을 확정한 뒤 최종 `latest.json`을 만들고, 업로드 직전 정확히 그 파일에 서명하는 단계를 정한다.
- [ ] `.github/workflows/build-windows-exe.yml`, `.github/workflows/github-release.yml`에 서명 단계가 연결되어 있는지 확인한다. 현재 검색한 워크플로에는 `update_signing.py` 호출이나 `latest.json` 서명이 보이지 않는다.
- [ ] `scripts/publish_gitlab_downloads.py`의 manifest 생성 결과에 서명을 붙이는 방법과 서명 검증 후 게시하는 게이트를 정한다. 현재 스크립트는 manifest를 생성하지만 서명하지 않는다.
- [ ] 서명 주체·환경, 승인/수동 단계, CI 비밀 변수 사용 여부, 로그 마스킹, 재실행·재서명 정책을 확정한다. **미확인**.
- [ ] GitHub와 GitLab 업데이트 경로 각각에 서명된 메타데이터를 제공하고, 클라이언트가 검증하는 경로와 게시 순서를 정한다. 서명 활성화 시 앱은 서명 없는 GitHub 릴리스 정보 경로를 거부한다. 배포 위치·폴백 최종 정책: **미확인**.
- [ ] 실제 게시 전 테스트용 manifest로 CI 산출→서명→게시→클라이언트 검증의 연결을 점검하고, 실패 시 게시가 중단되는지 확인한다. **미확인**.

## 활성화 및 실패 처리

- [ ] 서명된 `latest.json`이 배포 경로에 게시되고 다운로드 가능함을 먼저 확인한 뒤, 공개키 포함 앱을 충분히 배포한다. 단계별 대기 기준·사용자 도달 확인 방법: **미확인**.
- [ ] 전환 순서와 `DOCFIT_VERIFY_UPDATE_SIGNATURE` 환경변수의 운영 적용 위치를 확정한다. 코드 기본값은 꺼짐이며, 켠 뒤에는 signature 오류 시 업데이트가 거부된다.
- [ ] 서명 실패 시 사용자 오류 표시, 업데이트 중단, 재시도·운영자 알림 및 장애 공지 절차를 확인한다. 코드상 signature 오류는 업데이트 실패 상태로 전달되나, 알림·대응 담당자 및 절차는 **미확인**.
- [ ] 서명 검증 실패를 일반 네트워크 오류로 숨기지 않고, 서명 없는 GitHub 경로로 우회하지 않는지 경로별로 확인한다. 실제 장애 상황에서의 확인 결과: **미확인**.
- [ ] 게시 실패·잘못된 서명·키 서비스 장애 시 기존 설치본과 업데이트 서버가 취할 복구 절차를 정한다. **미확인**.

## 키 교체·유출·폐기

- [ ] 정기 교체 주기, 책임자, 교체 승인·기록, 유출 판정 및 긴급 폐기 연락 절차를 정한다. 모두 **미확인**.
- [ ] 키 유출 시 해당 키로 서명된 업데이트를 신뢰하지 않도록 하는 절차를 마련한다. 공개키 교체에는 새 키가 든 앱 배포가 필요하므로, 구 키 폐기부터 새 앱 보급까지의 간격과 대응 방안은 **미확인**.
- [ ] 키 교체 전환(구·신 키 동시 신뢰 여부, 전환 기간, 구 키 제거 버전)과 복구 시험을 문서화한다. 현재 코드에서 키링·복수 공개키 교체 지원은 **미확인**.
- [ ] 비밀키 백업 폐기, 접근 권한 회수, 사고 기록 보존 및 키 폐기 확인 절차를 정한다. **미확인**.
- [ ] 서명만으로는 오래된 정상 manifest 재전송(롤백/동결)을 막지 못한다. 버전 단조 증가·만료 검사가 활성화 요건인지 결정한다. 현재 설계상 2단계 과제이며 적용 여부는 **미확인**.
