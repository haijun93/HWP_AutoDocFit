# ROLLBACK6 — 1쪽 맞춤 실패 때 장평·조정 글자색 원복

작성: 2026-11-27 · 브랜치: `feature/ROLLBACK6` · 로컬 커밋만, 푸시 없음.

## 확인

ROLLBACK5의 남은 문제 1·2는 사실이었다. '장평 줄이기'를 켜면 당김이 줄인 장평이, 자간 조정 글자색을 켜면 칠한 색이 1쪽 맞춤이 실패·취소·예외로 끝난 뒤에도 남았다.

## 수정

| 파일 | 내용 |
|---|---|
| `docfit_engine/spacing.py` | 장평을 처음 바꾸기 직전에, 이미 읽어 둔 글자별 장평을 `쪽맞춤_장평기록`에 담는다. 색을 칠하기 직전에는 칠할 구간의 글자색을 글자별로 읽어 `쪽맞춤_색기록`에 담는다(1쪽 맞춤 중이고 색 설정이 켜진 경우만). |
| `docfit_engine/page_fit.py` | 1쪽 맞춤의 '줄 수 맞춤' 구간에서 자간·장평·색 기록을 함께 연다. 성공하지 못하면 셋을 따로 원복한다(하나가 실패해도 나머지는 시도). |
| `docfit_engine/layout_restore.py` | `restore_char_spacing`을 `restore_char_values`(되쓰기 → 글자별 다시 읽어 확인)로 일반화. 글자색 읽기·쓰기 함수 추가. 확인하지 못하면 `fail_required_edit`(저장 차단). |
| `docfit_engine/com_driver.py` | `색상_적용_현재선택(칠하기=True)`. |

- 색은 줄 처음부터 칠하므로, 자간 보관에서 빠지는 문두(항목기호·라벨)까지 따로 읽는다. 자간 보관 읽기를 재사용하지 않은 이유다.
- 원래 색을 읽지 못하면(중단·위치 확인 실패) 그 당김에는 색을 칠하지 않는다. 되돌릴 수 없는 변경을 만들지 않기 위해서다.
- 맞춤이 성공하면 줄인 장평과 칠한 색은 그대로 남는다.
- 본체 `hwp-auto-docfit.py`는 바꾸지 않았다.

## 실제 한/글 전후 확인(합성 문서)

COM 잠금을 배타 생성하고(전체 시험 잠금이 있으면 대기) DispatchEx 새 인스턴스만 사용했으며 끝나면 종료했다. 설정 폴더는 임시 폴더로 돌렸다. 수정 전은 HEAD 사본이다. 파이프라인 전체나 EXE가 아니라 `보고서_1쪽_맞춤`을 직접 불렀고 원본 줄 수는 문단마다 1줄로 지정했다.

문서 3종(어절 단위 줄바꿈, 구간별 장평 101%·글자색·굵게·자간 혼합):

- 자간 문서(40문단): 자간만으로 1쪽 성공.
- 혼합 문서(40문단): 넘친 문단 일부가 자간 -40%라 장평을 켜야 성공.
- 실패 문서(65문단): 어느 설정이든 1쪽 실패.

'남은 글자'는 시도 전 저장본과 비교한 장평 / 글자색이 다른 글자 수, '줄 수'는 본문 화면줄 합이다.

저장본 비교:

- 성공 3건과 끔·끔 전 사례: 수정 전·후 `section0.xml`·`header.xml`이 **바이트 동일**.
- 수정 후 실패·취소·예외 사례: `header.xml`이 시도 전과 바이트 동일. `section0.xml`은 바이트 동일하지 **않고**, 줄 배치 캐시를 빼고 같은 글자 모양의 인접 구간을 합치면 시도 전과 같다.

## 남은 문제

- 색을 켠 경우의 추가 읽기는 줄일 여지가 있다(당김이 이미 읽는 구간의 색을 함께 담고 문두만 추가로 읽기). 하지 않았다.
- 켬·켬 실패는 호출이 약 2배다(자간·장평·색을 각각 되쓰고 확인). 한 번에 읽어 확인하면 줄일 수 있다.
- 원복 뒤에도 같은 글자 모양의 구간 분리가 저장본에 남는다(ROLLBACK5와 같음).
- 당김 통계·로그의 '다음 단어 당김 적용'은 원복해도 남는다.
- 복원 실패·부분 적용·원래 색 읽기 실패는 실제 한/글에서 만들지 않았고 가짜 hwp 시험으로만 확인했다.
- 설정을 하나만 켠 성공 사례, 쪽 맞춤 전체 파이프라인, 표가 있는 문서, 실제 문서, 다른 한/글 판, 설치본·EXE는 확인하지 않았다.
