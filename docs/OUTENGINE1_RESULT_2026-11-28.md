# OUTENGINE1 — 아웃라이너 엔진 실행 비용

## 범위와 판정 계획

- 기준 소스: `be87c53f`, 기능 브랜치 `feature/OUTENGINE1`. 푸시·배포·main 병합 없음.
- 합성 페이지 10·200·2000블록, 임시 데이터 폴더만 사용한다. 설치본·실행 중 앱·사용자 데이터·설정은 건드리지 않는다.
- 서비스 `execute`의 파일 검사·해시·JSON 직렬화·프로세스 실행·응답 파싱을 포함해 명령별 5회 이상 측정한다. 준비·초기화 시간은 제외하며 빌드·다른 시험과 겹치지 않는다.
- 0.2초 목표를 이미 만족하면 제품 코드는 바꾸지 않는다. 필요할 때만 상주화를 구현한다.
- 상주화가 필요하면 상태를 미시작 → 준비 → 요청 중 → 준비, 실패 → 재시작 1회 → 단발 대체, 종료로 명시한다. 잠금으로 요청·응답을 직렬화하고 요청별 ID를 검증한다. 응답을 못 받은 쓰기는 재전송하지 않는다.
- `outliner_core/src/main.rs`는 이미 줄 단위 JSON을 반복해서 읽고 응답마다 flush한다. 엔진 자체의 다중 요청 지원 변경은 필요하지 않다.
- 최종 결과물: 이 문서, 재현 측정 도구, TODO, 로컬 커밋. 기존 시험은 변경하지 않는다.

## 결과

상주화로 새 프로세스 실행은 본 명령 330회 합계 390회에서 0회로 줄었다. 응답과 저장 파일은 330쌍 모두 SHA-256 일치했다.

**0.2초 목표는 전체 충족하지 못했다.** 상주 후에도 2000블록 이름 변경·되돌리기·편집→저장→역링크 묶음의 중앙값이 200ms를 넘었다. 쓰기 및 일부 조회에는 큰 편차도 남았다. 빠른 정상 명령과 첫 실행·복구 비용을 구분해야 한다.

### 측정 조건과 유효 범위

- 최초 원본 제품 코드에서 21종 × 3크기 × 5회 = 315회 측정했다. 2000블록 이름 변경 중앙값 304.933ms, 되돌리기 366.094ms로 상주화 필요를 판정했다.
- 최종 비교는 동일한 release 엔진 파일, 기존 단발 경로(persistent=False)와 상주 경로(persistent=True)로 수행했다. Rust 소스·실행 파일은 전후 동일하다. 원자료에 실행 파일 SHA-256을 기록했다.
- 명령 21종과 연속 동작 1종, 3크기, 각 5회로 전후 각각 330회다. 세 합성 페이지 각각 10·200·2000블록(전체 30·600·6000블록)이며 모든 블록에 한글·페이지 링크·태그·블록 참조를 넣었다. 생성 명령은 기존 동작대로 새 1블록 페이지를 만든다.
- 각 회차는 새 임시 폴더·서비스 인스턴스를 사용한다. 처음 parse 1회를 먼저 재고, 그 인스턴스로 본 명령을 잰다. 따라서 아래 본 명령 표의 상주 값은 준비가 끝난 상태다. 최초 parse 비용은 별도 표에 모두 포함한다. 이름 변경 되돌리기·휴지통 복원은 준비 동작을 본 명령 시계 밖에서 수행한다.
- 시계는 execute 진입 직전부터 반환 직후까지다. 파일 검사·해시·JSON 입출력·엔진 처리를 포함한다. 연속 동작 행은 execute 3회(edit, save, backlinks)의 합계다. 인스턴스 생성·합성 자료 준비·종료 정리는 본 명령 시간에서 제외한다.
- 화면 방식 설정과 실제 창 열기는 금지 범위여서 제외했다. 직접 실행·브리지 왕복·화면 그리기·실제 설치본의 사용 반응 시간 측정은 아니다.
- 측정 중 자체 시험·빌드를 함께 돌리지 않았다. 실행 중 앱을 조작하지 않았고 재부팅·외부 부하 통제를 하지 않아 시작 지연과 파일 작업 편차가 컸다. 전후 배율을 일반적인 성능 보장으로 해석하지 않는다. 실패·초과 표본도 버리지 않았다.
- 단발 준비 비용도 같은 parse 1회로 기록한다. 단발에서는 준비 뒤에도 본 명령마다 새 프로세스를 실행하므로 실행 횟수에 포함된다. 상주 준비는 회차마다 새 프로세스 1회이며 본 명령에서는 모든 표본이 0회다.

## 구현과 상태

- 제품 변경은 Python 서비스의 프로세스·파이프 어댑터에 한정한다. Rust 엔진은 기존 다중 줄 프로토콜을 그대로 사용한다. Flutter·파일 형식·앱 버전·기존 시험은 바꾸지 않는다.
- 상태는 `OutlinerEngine.state` 한곳에 `stopped / ready / busy / fallback / closed`로 둔다. `closed`에서는 새 요청을 받지 않는다. 서비스의 잠금은 파일 검사부터 결과 반영까지, 전송의 잠금은 요청부터 해당 응답까지 직렬화한다. 브리지의 최초 서비스 생성도 잠근다.
- 요청마다 새 ID를 붙이고 응답 ID·성공 여부의 자료형·결과/오류 봉투를 검증한다. 이전 응답이 남거나 잘못된 JSON이 오면 해당 프로세스와 파이프를 버린다. 서로 다른 프로세스의 응답 큐도 공유하지 않는다.
- 입출력 전용 스레드에서 쓰기·flush·한 줄 읽기를 함께 처리하므로 입력 파이프가 꽉 차는 경우도 제한 시간에 걸린다. 표준 오류는 버려 별도 파이프가 차서 멈추지 않는다. 모든 콘솔 프로세스 실행에 `CREATE_NO_WINDOW`를 지정한다.
- 응답 대기는 시도마다 기본 30초다. 읽기 명령만 상주 재시도 1회, 다시 실패하면 기존 단발 실행으로 대체한다. 이후 그 서비스 인스턴스는 단발 방식을 유지한다. 세 시도가 모두 시간 초과하면 응답 대기 합계는 최대 90초이며, 자식 회수 대기는 각 2초·스레드 합류 각 2초가 별도로 붙을 수 있다. OS의 실행 파일 복사·프로세스 생성 시간은 이 응답 대기 한도 밖이다.
- `save`·`rename_page`를 포함해 읽기 허용 목록 밖의 요청은 전송 뒤 응답이 끊겨도 재전송하지 않는다. 새 엔진에는 빈 문서 `parse` 점검만 보내고, `OUTLINER_ENGINE_UNCERTAIN`으로 다시 불러와 확인하도록 안내한다. 점검도 실패하면 다음 요청부터 단발 방식이다. 전송 전에 실행 자체가 실패한 경우에는 중복 적용이 없으므로 재시작·단발 대체를 허용한다.
- 이름 변경 뒤 링크 갱신의 응답이 불확실하면 파일명을 되돌리지 않는다. 엔진이 일부 또는 전부 갱신했을 수 있기 때문이다. 페이지·링크를 다시 확인해야 하며 여러 파일의 트랜잭션 보장은 이번 범위 밖이다.
- 명시적 `close()`와 WebView 종료 연결로 자식을 회수한다. 대기 중이면 자식을 먼저 종료해 파이프를 깨우고, 실행 중 요청도 닫힘 오류로 풀어준다. 정상 인터프리터 종료·객체 회수에는 finalizer도 적용한다. 임시 폴더 finalizer보다 프로세스 정리가 먼저 실행되도록 순서를 지정한다.

## 설치 파일 잠금

- 상주 프로세스는 패키지의 실행 파일을 임시 전용 폴더에 복사해 실행한다. 설치 폴더의 원본 EXE는 복사가 끝나면 열어 두지 않는다. 설정이나 사용자 데이터 폴더에 실행 파일을 만들지 않는다.
- 현재 배포 소스는 MSVC 정적 C 런타임 설정을 사용한다. 나중에 실행 파일 옆의 DLL 의존성을 더하면 임시 사본에서도 로딩되는지 재확인해야 한다. 임시 경로 실행이 차단되거나 상주 시작에 실패하면 단발 실행으로 대체한다.
- 실제 Windows 시험에서 종료 직후 임시 EXE 삭제가 WinError 5로 거절됐다. 원인 핸들은 따로 추적하지 않았다. 정리는 50ms 간격으로 최대 2초 재시도하고, 계속 실패하면 경고만 남긴다. 그 경우 남는 것은 임시 사본이며 설치 원본의 잠금은 아니다.
- 단발 대체 중에는 예전처럼 실행하는 동안 원본 EXE의 잠금이 생긴다. 강제 프로세스 종료·전원 중단에서는 임시 사본이 남을 수 있다. 설치 프로그램 전체 동작·정책 프로그램·실제 업데이트는 조작 금지 범위라 검증하지 않았다.
