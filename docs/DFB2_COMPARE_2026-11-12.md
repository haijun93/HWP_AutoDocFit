# DFB2 Docufinder 대 우리 본문 검색 — 같은 자료·같은 검색어 (2026-11-12)

작업: `feature/instant-search`. Docufinder 쪽 숫자는 DFB1(`C:/HWP_AUTODOCFIT/v1803/reports/DFB1.final.md`, `E:/docfit-tmp/dfbench/DFB1-report.md`)을 그대로 옮겼고 다시 재지 않았다. 우리 쪽은 이번에 같은 corpus로 쟀다. 원자료: [JSON](DFB2_COMPARE_RAW_2026-11-12.json). 구동기: `kfind/engine-bench/dfb2.py`.

비교한 우리 엔진 세 가지:
- **B** = IS-S1 직접 구현(fst + roaring, 권고안). 문장 단위, 띄어쓰기 무관(비교형).
- **A** = IS-S1 Tantivy 시제품. 규칙은 B와 같음.
- **P** = 현행 앱 Python `ContentSearchIndex.index_file` + `keyword_search`. 문단 단위, 낱말 그대로 일치, bm25 순위.

## ⚠ 측정 방식이 다르다 — 직접 비교 금지

| | Docufinder(DFB1) | 우리(DFB2) |
|---|---|---|
| 무엇을 쟀나 | UIA로 입력을 넣고 **화면 결과를 관찰**할 때까지 시간의 **상한**(관찰 간격·UIA 스냅샷 비용 포함). 앱이 스스로 표시한 시간은 0.07~0.21초 | **엔진 안 계산 시간**(프로세스 안 `Instant`/`perf_counter`). **입력 처리·Python 중계·화면 그리기·화면 왕복은 빠져 있다** |
| 결과 범위 | 파일명 + 본문 함께, 화면 최대 50건 | **본문만**(A·B는 파일명 검색 없음, P는 본문 FTS만) |
| 결과 수 | 화면에 보인 수(50 상한) | 전체 일치 문서 수, 그리고 비교용 "상위 50 기준" = min(전체, 50) |
| 반복 | 검색어마다 1회 | 검색어마다 **첫 회 1번 + 이어서 5회**(중앙값). 첫 회는 그 프로세스에서 그 검색어를 처음 계산한 시간 |

따라서 아래 표의 Docufinder 초 단위와 우리 ms 단위는 **같은 것을 잰 숫자가 아니다**. Docufinder 쪽에 공정한 비교는 앱 자체 표시 시간(0.07~0.21초)이고, 우리 쪽에는 앞으로 화면 왕복(S4·S8)이 더해진다.

## 비교표 3 — 한 글자씩 입력(상위 20, ms)

음절 완성 단위(예산 → 예산집 → 예산집행), 각 단계 5회. "새로" = 매번 새로 찾기, "재사용" = 앞 결과 좁히기 + 낱말 캐시(IS-S1 세션). P는 앱 그대로 매 단계 새 검색(순위 보관 비움).

| 단계 | 일치 문장 / B·A 문서 | B 새로 중앙 / 재사용 중앙 | A 새로 / 재사용 | P 첫 / 중앙 | P 표시 수 |
|---|---|---:|---:|---:|---:|
| 예산 | 47,975 / 3,000 | 0.78 / 0.66 | 2.46 / 3.56 | 8,076 / 3,672 | 20 |
| 예산집 | 209 / 200 | 0.02 / 0.05 | 0.13 / 0.09 | 3.3 / 0.1 | **0** |
| 예산집행 | 209 / 200 | 0.07 / 0.05 | 0.08 / 0.12 | 0.1 / 0.1 | **0** |
| 세 단계 합 | | 0.88 / 0.75 | 2.73 / 3.82 | — | |

참고(입력기 중간 상태 포함 붙여쓰기 `ㅇ→예→옛→예사→예산→예삱→예산지→예산집→예산집ㅎ→예산집해→예산집행`, 11단계): B 합 중앙 0.57ms(재사용 0.64), A 2.57ms(3.08). 1글자 상태(ㅇ·예·옛)는 A·B가 Q8에 따라 본문 검색을 하지 않는다. P는 1글자도 검색해 'ㅇ' 225ms, '예' 3,421ms, '옛' 233ms가 들며, '예산' 단계 3,271ms다(단계마다 중앙값). Docufinder는 DFB1에서 "문→문화→문화의" 자동 갱신만 관찰했고 단계별 시간은 재지 않았다.

- A·B 색인 시간은 `corpus.tsv`(이미 문장으로 나눈 사본)를 읽어 색인을 만드는 시간이다. txt·md 3,000개를 읽고 문장으로 나누는 앞 단계는 따로 쟀고(Python, 디스크 캐시가 따뜻한 상태 3회) 1.05~1.09초였다. 구동기 전체 준비 단계 33.5초는 정답 구현용 비교형 만들기가 포함된 값이라 색인 시간에 넣지 않았다.
- P 색인은 앱 경로 그대로(`batch()` 안에서 `index_file` 3,000번: 추출·위계 판정·문단 FTS·문서 FTS·2글자 조각 표·메타). 오류 0건. 진행 관찰상 뒤로 갈수록 느려졌다(20분에 2,220개, 그 뒤 약 20분에 780개). 메모리는 MB 단위(1MB = 1,048,576바이트) 프로세스 피크다. Docufinder는 MiB로 적혀 있다(같은 단위).
- Docufinder 메모리는 앱 전체(화면·WebView 포함)이고, 우리 값은 색인·질의 도구 프로세스 하나다. 화면을 가진 실제 앱 메모리와는 비교할 수 없다.

## 요약

- 같은 corpus·같은 8개 검색어에서 권고안 B의 엔진 계산은 상위 20 첫 회 **0.02~1.36ms**, 중앙 **0.00~0.63ms**, 전체 결과 최악 2.74ms. 입력 흉내 3단계 합 0.88ms. 결과 수는 Q3·Q5·Q8 규칙의 정답 구현과 완전히 일치.
- 현행 P는 흔한 말 상위 20에 **2.2~4.3초**, 전체 6~8초, 색인 39.7분이며 "예산집행"은 0건.
- Docufinder와의 속도 우열은 이 표로 판정하지 않는다: Docufinder는 화면 관찰 상한(앱 표시 0.07~0.21초)이고 우리는 화면 왕복이 빠진 엔진 내부 시간이다. 공정한 비교는 우리 화면(S4·S8)이 생긴 뒤 같은 UIA 방식으로 재야 한다.

## 남은 문제·확인 못 한 것
