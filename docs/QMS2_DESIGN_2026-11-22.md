## 1. 개요 및 설계 목적

본 문서는 `TODO.md`의 핵심 검색 과제인 **'몽땅검색 통합 검색(2026-11-14)'**, **'몽땅검색 연관 검색어 `;`'**, **'퀵몽땅검색 고도화 — Docufinder 모든 기능'**, **'퀵몽땅검색 UI 고도화 — Anything 레퍼런스'**의 잔여 작업을 완수하기 위한 종합 기술 설계서이다.

2026-11-21 감사(`docs/TODO_AUDIT_2026-11-21.md` 행 6·8·9·35·38) 결과, 퀵몽땅검색 단축키 창(`ktm`)을 중심으로 1단계 통합 검색(`combine_results`)과 Anything 레퍼런스 UI 이식이 상당 부분 진척되었으나, 다음과 같은 중대한 구조적 격차가 남아 있음이 확인되었다.

1. **앱-단축키 화면의 이원화 및 중복**: 앱 내부 탭(`TimemachineScreen`)은 여전히 파일명·본문·위계가 분리된 3종 탭 구조를 유지하고 있으며, Win32 네이티브 `ktm` 창과 완전히 분리되어 코드 중복과 사용자 혼선을 초래하고 있다.
2. **`;` 연관 검색어의 기능 단절**: `kfind/core` 엔진 수준에서만 문장 단위 교집합이 구현되었을 뿐, 파일명(names) 경로의 문서 교집합, 서비스 파이프(`HwpAutoDocFit.Index`) 연관 그룹 필드, UI 묶음별 결과 강조가 누락되어 있다.
3. **Docufinder 대비 잔여 편의 기능 및 첫 입력 지연**: 포맷별 위치 메타 완전성 및 창 표시 직후 첫 타이핑 시 377~586ms의 지연이 여전히 존재한다.

본 설계는 **'전면 Rust 전환 원칙(Rust+Win32 우선·최고 속도·최저 자원)'**에 입각하여 앱 화면을 `ktm`으로 일원화하는 구체적 아키텍처와 `;` 연관 검색어의 완전한 엔드투엔드 파이프라인을 정의한다.

## 2. ① 현재 구조 지도 및 중복 분석

현재 시스템은 동일한 검색 목적을 위해 3개의 상이한 계층과 프로세스가 공존하며 비효율과 중복을 발생시키고 있다.

```
+-----------------------------------------------------------------------------------+
| [1] 앱 몽땅검색 탭 (Flutter UI)                                                   |
|   - 파일: flutter_ui/lib/features/timemachine/timemachine_screen.dart (2,109줄)  |
|   - 상태: InstantSearchController (initialTab: 'file', 'content', 'related' 분리)  |
|   - 경로: Flutter UI -> (HTTP/IPC) -> Python TimemachineService -> subprocess     |
+-----------------------------------------------------------------------------------+
                                         |
                                         | (기능·UI 중복 및 검색 방식 불일치)
                                         v
+-----------------------------------------------------------------------------------+
| [2] 퀵몽땅검색 ktm 창 (Rust Win32 네이티브 독립 프로세스)                         |
|   - 파일: ktm/src/window.rs (4,400+줄), tm_state.rs (450+줄), backend.rs (2,100+줄) |
|   - 상태: combine_results (파일명 > 위계 > 본문 실시간 통합 병합, 중복 제거)       |
|   - 경로: ktm.exe (GDI) -> Named Pipe / kfind-core 직접 호출                     |
+-----------------------------------------------------------------------------------+
                                         |
                                         | (질의 요청 및 색인 조회)
                                         v
+-----------------------------------------------------------------------------------+
| [3] kfind 검색 서비스 / 사용자 모드 (Rust)                                        |
|   - 파일: crates/kfind/src/pipe.rs, names.rs, kfind/core/src/index.rs             |
|   - 서비스 모드: SYSTEM 서비스 (HwpAutoDocFit.Index), NTFS MFT 전체 색인          |
|   - 사용자 모드: 서비스 미실행 시 fallback, 사용자 폴더 순회 및 프로세스 내 캐시  |
+-----------------------------------------------------------------------------------+
```

### 2.1. 앱 몽땅검색 탭 구조
- **코드 위치**: `flutter_ui/lib/features/timemachine/timemachine_screen.dart`, `timemachine_api.dart`
- **검색 방식**: `InstantSearchController`(`timemachine_screen.dart:62-68`)를 통해 `file`(파일명), `content`(본문), `related`(위계) 탭을 물리적으로 분리하여 검색함.
- **백엔드 연동**: Python `TimemachineService`(`docfit_app/timemachine_service.py`)의 `content_search`, `related_search` API를 비동기 호출(`timemachine_screen.dart:357-361`).
- **한계점**: 한 번의 질의로 파일명, 위계, 본문을 아우르는 통합 검색(`combine_results`)이 부재함. 결과를 보려면 사용자가 탭을 일일이 전환해야 함.

### 2.2. 퀵몽땅검색 ktm 창 구조
- **코드 위치**: `ktm/src/window.rs`, `ktm/src/tm_state.rs`, `ktm/src/backend.rs`
- **검색 방식**: 단축키(`Ctrl+Alt+Space`)로 호출되는 경량 독립 실행 파일(`ktm.exe`). `combine_results`(`ktm/src/tm_state.rs:273-301`)를 통해 `ResultKind::Names`(우선순위 0), `ResultKind::Hierarchy`(우선순위 1), `ResultKind::Body`(우선순위 2) 결과를 하나의 피드로 실시간 병합하고, 동일 문서는 최고 우선순위 항목 1건으로 단일화함.
- **UI 구성**: 접이식 사이드바, 정렬 5종(관련도/신뢰도/최신/오래된/이름), 파일 형식 및 기간 필터, 2줄 카드/격자 보기, 연관 검색어 칩, CSV 내보내기.

### 2.3. kfind 서비스 및 사용자 모드 구조
- **코드 위치**: `crates/kfind/src/pipe.rs`, `crates/kfind/src/names.rs`, `kfind/core/src/index.rs`
- **서비스 모드 (SYSTEM)**: 네임드 파이프 `\\.\pipe\HwpAutoDocFit.Index`를 열고 고정 드라이브 전체의 NTFS MFT를 직접 읽어 이름 색인(`names.rs`)을 메모리에 상주 유지함.
- **사용자 모드**: 서비스가 미설치되거나 미실행일 때, `ktm`이 직접 인덱스 파일을 열거나 백그라운드 스레드에서 폴더를 순회(walk)함.

### 2.4. 주요 중복 및 문제점 지점
1. **화면·UI 계층의 거대한 중복**: Flutter 위젯 트리(`timemachine_screen.dart` 약 2,109줄)와 Rust Win32 GDI(`window.rs` 약 4,400줄)가 검색창, 결과 목록, 필터링, 미리보기 기능을 각각 따로 유지보수하고 있음.
2. **호출 파이프라인의 이중화**: Flutter는 Dart → Python IPC → 서브프로세스/파이프라는 다단계 계층을 거치며 지연이 누적되는 반면, `ktm`은 Rust 직접 호출 및 네임드 파이프 통신을 수행함.
3. **검색 동작의 불일치**: `ktm`은 이미 1단계 통합 검색(`combine_results`)이 구현되었으나, 앱 화면은 과거의 3종 분리 탭 방식을 고수하여 사용자에게 파편화된 경험을 제공함.

## 4. ③ `;` 연관 검색어 보강 항목 및 구현 지점

### 4.1. 현황 및 격차 분석

### 4.2. 경로/파일명 문서 교집합 구현 지점

```
[입력: "2026; 공사 계약"]
   |
   +--> parse_groups() 로 분리: 그룹1("2026"), 그룹2("공사 계약")
   |
   +--> [kfind/names/src/query.rs]
   |      그룹1 MFT 비트맵 검색 (hit_set_1)
   |      그룹2 MFT 비트맵 검색 (hit_set_2)
   |      교집합 수행: result_set = hit_set_1 & hit_set_2
   |
   +--> [crates/kfind/src/names.rs]
          Names::search_groups(groups, opts) -> DocHit 교집합 결과 반환
```

- **구현 파일 1**: `kfind/names/src/query.rs`
  - 세미콜론 분리 질의를 파싱하는 `parse_name_groups(text: &str) -> Vec<ParsedQuery>` 함수 추가.
  - 각 그룹별 파싱 결과에 대해 MFT 인덱스 순회를 실행하고 결과 `RoaringBitmap` 간 `intersection` 연산 수행.
- **구현 파일 2**: `crates/kfind/src/names.rs`
  - `NamesQuery` 처리 루틴(`names.rs:163-180`)에서 입력 텍스트에 `;`가 포함된 경우 다중 그룹 검색 분기 실행.
- **구현 파일 3**: `ktm/src/backend.rs`
  - `pipe_names` 호출 시 단일 질의 대신 그룹 분할이 반영된 요청을 보내거나, 로컬 fallback 검색 시 파일명 그룹 교집합을 직접 계산.

  - `crates/kfind/src/pipe.rs:636`: `let result = index.search(text, &opts)?;` (단일 검색만 호출).
- **구현 지점**:

     ```rust

         #[serde(default)]
     ```

## 6. ⑤ 시험 및 성능 기준

### 6.1. Everything 대비 p50 응답 시간 유지 기준
- **검색 응답 시간 (p50)**:
  - 파일명(names) 검색: Everything 대비 동등 이상의 속도(23/23 빠름 기록, `0d6204e3`) 유지.
  - 통합 검색(`combine_results`): 키 입력 종료 후 첫 화면 렌더링까지 **16ms (60fps 1프레임)** 이내 완료.
- **비동기 취소 보장**:
  - 빠른 연속 타이핑 시 이전 질의의 스레드 또는 파이프 I/O가 즉시 취소(`AtomicBool` cancel 플래그)되어 최신 세대(Generation) 결과만 화면에 표시되어야 함.

### 6.2. 첫 입력 지연(Cold Start) 개선 기준
- **현상 및 원인 분석**:
  - 단축키 창이 뜬 직후 바로 타이핑할 때 첫 결과가 377~586ms 지연되는 현상(`docs/MG2_KTM_2026-11-14.md` 남은 문제 1, `docs/TODO_AUDIT_2026-11-21.md` 행 6).
  - 주원인 후보: 파이프 핸들 지연 오픈, NTFS MFT 메모리 매핑 초기 페이지 폴트(Page Fault), IME 컨텍스트 초기화 경합.
- **목표 성능**:
  - 창 생성/초기화 시점에 백그라운드 워밍업(파이프 사전 연결, 색인 세그먼트 터치)을 수행하여 **표시 직후 첫 입력 응답 시간을 50ms 이내**로 단축.

### 6.3. 메모리 및 시스템 자원 상한 기준
- **유휴 상태(Idle) 메모리**: **5MB 이하** (현재 실측치 2.3~2.6MB 유지, `docs/MG2_KTM_2026-11-14.md`).
- **상주 증가량(Footprint)**: 대규모 연관 검색 및 프리셋 전환 후에도 유휴 복귀 시 메모리 증가가 **2MB 이하**여야 함.
- **자원 누수 0**: GDI Object, HDC, 메모리 버퍼 누수 전수 검증.

### 6.4. 검증 도구 및 회귀 시험 계획
1. `qms_bench`: Everything 대 몽땅검색 비교 벤치마크 엔진을 이용한 p50/p90 지연 시간 및 메모리 자동 계측.
2. `tools/app1_equivalence.py`: 연관 검색어 질의 구문 해석 및 검색 결과 동등성 회귀 검증.
3. Cargo 단위 시험: `kfind/core`, `kfind/names`, `ktm`의 단위/통합 시험 100% 통과 유지.

### 7.2. 주요 위험 요인 3가지 및 대응 전략

#### 위험 1: 서비스 파이프 스키마 변경 시 클라이언트 호환성 파손 위험
- **위험 내용**: `crates/kfind/src/pipe.rs`는 `deny_unknown_fields` 속성을 엄격하게 적용하고 있어, 프로토콜 수정 시 이전 버전 클라이언트와의 역호환성이 깨지거나 서비스 패닉이 발생할 수 있음.
- **대응 전략**:
  - 신규 필드는 반드시 `#[serde(default)]`로 선언하여 누락 시에도 기본값으로 파싱되도록 보장.
  - 별도의 신규 명령(`query_groups`)을 추가하거나, 기존 `text` 필드의 내부 세미콜론 문자열 파싱을 우선 활용하여 스키마 충돌을 원천 회피.

#### 위험 2: Flutter 메인 창과 네이티브 Win32 `ktm` 창 간의 포커스 스틸링(Focus Stealing) 위험
- **위험 내용**: Windows 11의 포커스 보호 정책으로 인해 Flutter 앱에서 `ktm.exe` 창을 활성화할 때 창이 최상위로 오지 못하고 작업표시줄에서 깜빡이기만 할 위험.
- **대응 전략**:
  - `AllowSetForegroundWindow(ASFW_ANY)` API를 호출하여 권한을 명시적으로 위임.
  - 상주 중인 `ktm` 프로세스에 윈도우 메시지를 전달할 때 `AttachThreadInput` 기법을 적용하여 포커스를 안정적으로 전환.

#### 위험 3: NTFS 전체 파일명 대상 `;` 다중 교집합 시 성능 저하 위험
- **위험 내용**: 수백만 건의 MFT 레코드에 대해 세미콜론으로 분리된 여러 패턴을 순차 순회할 경우, 단일 질의 대비 검색 시간이 선형 증가하여 p50 16ms 프레임 예산을 초과할 위험.
- **대응 전략**:
  - 가장 검색 결과가 적은 그룹(희소 토큰)의 비트맵을 먼저 계산한 뒤, 해당 비트맵의 인덱스들만 대상으로 후속 그룹 패턴을 검증하는 단락 평가(Short-circuit evaluation) 적용.
