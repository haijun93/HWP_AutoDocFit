# kfind-core 색인 크기·메모리 분석 및 최적화 보고서 (2026-11-18)

## 1. 개요

`TODO.md`에 명시된 'kfind-core 남은 약점: 색인 크기·색인 시간·색인 때 메모리' 과제 중 **색인 크기**를 분석하고 최적화 1건을 구현하였다.
kfind-core(`kfind/core/src`)의 색인 디스크 저장 구조를 파악하고, 테스트 코드에서 생성한 무작위 합성 데이터셋(500개 문서, 4,000개 문장)을 통해 디스크 구성 요소별 크기를 실측하였다.

`FORMAT_VERSION=4` 및 Python `EXPECTED_VERSIONS` 호환성을 엄격히 유지하기 위해, 포맷 버전 변경이 필요하지 않은 **비트맵 직렬화 최적화(RoaringBitmap run container 전환)**를 1건 구현하였으며, 포맷 버전을 올려야 하는 개선안(문장 저장 압축, 고정 정수 배열 패킹 등)은 상세 설계로 기록하였다.

## 2. kfind-core 색인 디스크 저장 구조 및 실측

### 2.1 세그먼트 파일(`seg-*.kfs`) 내부 구조
세그먼트 파일은 고정 216바이트 머리글(Header)과 10개의 섹션(Section)으로 구성된다.

| 섹션 인덱스 | 섹션 이름 | 저장 내용 및 설명 |
|---|---|---|
| - | **HEADER** | 매직넘버(8B), 형식 버전(4B), 규칙 버전(4B), 세그먼트 ID(8B), 문장 수(4B), 문서 수(4B), 본문 해시(8B), 파일 길이(8B), 섹션 표(160B), 헤더 해시(8B) |
| 0 | **POST** | 열쇠별 Roaring 비트맵(2·3글자 gram 문장 번호, 2글자 gram 문서 번호, 낱말 문서 번호, 파일 형식, 역할, 날짜, 폴더 등) |
| 1 | **DICT** | FST(Finite State Transducer) 유한 상태 사전: 검색 열쇠 문자열 → POST 구역 내 바이트 시작 오프셋 매핑 |
| 2 | **TEXT** | 문장 비교형 텍스트를 세그먼트 알파벳 번호(textcode)로 부호화하여 연속 저장한 본문 데이터 |
| 3 | **TEXT_OFF** | `(문장 수 + 1) × u32`: 각 문장의 TEXT 구역 내 시작 바이트 오프셋 |
| 4 | **PARA** | `문장 수 × u32`: 각 문장이 속한 문단 번호 |
| 5 | **LEVEL** | `문장 수 × u8`: 각 문장의 문서 위계 순위 |
| 6 | **DOC_OF** | `문장 수 × u32`: 각 문장이 속한 세그먼트 내 문서 번호 |
| 7 | **DOCS** | `문서 수 × 24B`: 문서 메타데이터 (문서 ID u64, 날짜 i64, 첫 문장 번호 u32, 문장 수 u32) |
| 8 | **ALPHA** | `글자 수 × 12B`: 알파벳 글자(u32) 및 출현 빈도(u64) |
| 9 | **ALPHA_IX** | `글자 수 × 8B`: 글자(u32) 및 부호 번호(u32) 정렬 색인 |

### 2.2 합성 색인 구성별 크기 실측값
테스트 환경(`tests/kfsize.rs`)에서 생성한 합성 말뭉치(500개 문서, 4,000개 문장, 행정·보고서 양식의 문장 패턴 및 메타데이터 포함)를 1개 세그먼트로 빌드하여 측정한 구성별 크기 실측값은 다음과 같다.

| 구성 요소 | 역할 및 형식 | 크기 (바이트) | 점유 비율 (%) |
|---|---|---:|---:|
| **POST** | 열쇠별 Roaring 비트맵 (조각·낱말·메타 포스팅) | 601,207 | 74.68% |
| **TEXT** | 문장 본문 부호화 (알파벳 번호 스트림) | 119,261 | 14.81% |
| **DICT** | FST 유한 상태 변환기 사전 | 16,618 | 2.06% |
| **TEXT_OFF** | 문장 본문 오프셋 표 (`u32`) | 16,004 | 1.99% |
| **PARA** | 문단 번호 표 (`u32`) | 16,000 | 1.99% |
| **DOC_OF** | 문장별 문서 매핑 표 (`u32`) | 16,000 | 1.99% |
| **DOCS** | 문서 메타데이터 표 (문서당 24B) | 12,000 | 1.49% |
| **LEVEL** | 문장 위계 순위 표 (`u8`) | 4,000 | 0.50% |
| **ALPHA** | 글자 빈도 사전 (글자당 12B) | 2,268 | 0.28% |
| **ALPHA_IX** | 글자 정렬 사전 (글자당 8B) | 1,512 | 0.19% |
| **HEADER** | 세그먼트 메타 및 섹션 오프셋 머리글 | 216 | 0.03% |
| **전체 세그먼트** | 단일 세그먼트 파일 전체 합계 | **805,086** | **100.00%** |

- **가장 큰 비중**: **POST**(Roaring 비트맵)가 전체 색인 크기의 **74.68%**를 차지하여 압도적인 1위다.
- **두 번째 비중**: **TEXT**(문장 본문)가 **14.81%**를 차지하여 2위다.
- 상위 두 요소(POST + TEXT)가 전체 색인의 **89.49%**를 차지한다.

## 3. 구현 내용: 비트맵 직렬화 최적화 (FORMAT_VERSION 변경 없음)

### 3.1 구현 개요
- **대상 파일**: `kfind/core/src/segment.rs`
- **변경 사항**: `write_segment`에서 포스팅 목록 `entries`의 비트맵들을 직렬화하기 직전에 `RoaringBitmap::optimize()`를 호출.
- **원리**:
  - RoaringBitmap 사양 표준은 Array Container, Bitmap Container 외에 RLE 기반의 Run Container를 공식 지원한다.
  - `optimize()`는 비트맵 내의 정수 연속 구간(Run)을 분석하여, Run Container로 표현했을 때 직렬화 바이트가 줄어드는 경우에만 무손실로 Run 형식으로 변환한다.
  - 연도(Year), 월(Month), 일(Date), 폴더(Folder), 문장 역할(Role, 특히 본문 문장의 연속 구간) 등 연속된 정수 문서/문장 번호가 집중되는 메타데이터 및 다빈도 gram 포스팅에서 직렬화 크기가 대폭 축소된다.
  - 역직렬화(`RoaringBitmap::deserialize_from`)는 표준 포맷을 그대로 따르므로 기존 독출 코드나 Python 바인딩 변경 없이 100% 호환된다.
- **포맷 버전**: `FORMAT_VERSION=4` 유지 (Python `EXPECTED_VERSIONS` 불변).

### 3.2 검색 결과 및 무손실성 검증
- `tests/kfsize.rs`의 `test_bitmap_optimize_roundtrip_identity`: 밀집, 희소, 혼합 패턴의 정수 집합에 대해 `optimize()` 전후 역직렬화 결과가 100% 비트 단위로 동일함을 확인.
- `tests/kfsize.rs`의 `test_search_results_identity_with_optimized_postings`: 200개 문서 색인에 대해 단어 검색, 복합어 검색, 분절 모드(Off, DictLongest, Bigram), Document Scope 검색, 세미콜론 묶음 검색(`;`) 결과의 문서 수, 문장 수, Hit 목록이 완전히 동일함을 검증.
- `cargo test --manifest-path kfind/core/Cargo.toml`의 기존 16개 테스트 바이너리 86개 테스트 전체 통과.
- `python -m unittest tests.test_kfind_versions_match` 통과.

## 4. FORMAT_VERSION 인상이 필요한 크기 개선 후보 설계

`FORMAT_VERSION`을 올려야 하는 변경은 Python `EXPECTED_VERSIONS` 동기가 필요하므로 본 작업에서는 구현하지 않고 설계만 기록한다.

### 4.1 후보 1: 문장 본문 구역(TEXT) 블록 압축 (예상 크기 절감: 전체 색인의 약 7~10%)
- **현행 한계**: TEXT 구역은 알파벳 글자 번호 부호화(1~3바이트)만 적용되어 있으며, 일반 텍스트 데이터의 반복 패턴(어휘, 조사, 단어 반복)에 대한 사전식 압축이 적용되지 않아 전체 색인의 약 14.8%를 점유한다.
- **설계안**:
  1. TEXT 구역을 64KB 단위의 청크(Chunk) 블록으로 분할하여 Zstandard(zstd 레벨 3) 또는 LZ4로 압축.
  2. `TEXT_OFF`를 확장하여 `[블록 번호: u16, 블록 내 오프셋: u16]` 형태의 인덱스로 구성하거나, 블록 오프셋 테이블(`BLOCK_OFF`)을 신설.
  3. 검색 시 문장 원문 확인(4글자 이상 낱말 검증 및 스니펫 추출)이 필요한 블록만 지연 압축 해제(Lazy Decompression)하고 LRU 블록 캐시 적용.
- **필요 조치**: `FORMAT_VERSION`을 4에서 5로 인상, `Segment` 읽기 시 압축 해제 루틴 추가, Python `kfind_client.py`의 `EXPECTED_VERSIONS["format"] = 5` 동기화.

### 4.2 후보 2: 고정폭 정수 구역(PARA, DOC_OF, TEXT_OFF) 압축 (예상 크기 절감: 전체 색인의 약 3~4%)
- **현행 한계**: `PARA`(문단 번호), `DOC_OF`(문서 번호), `TEXT_OFF`(문장 오프셋)는 모두 문장 수에 비례하여 `u32` 고정 4바이트씩 기록된다(합성 4,000문장 기준 각각 16KB씩 총 48KB 점유).
- **설계안**:
  1. `DOC_OF`는 문장이 문서 순서대로 정렬되어 있으므로, 문서 번호가 단조 증가한다. 따라서 `(문서 번호, 해당 문서의 문장 수)` 형태의 런렝스(Run-Length) 인코딩을 적용하면 문서당 8바이트(500문서 기준 4KB)로 16KB에서 4KB로 75% 감소.
  2. `PARA`는 문단 번호(대부분 0~20 미만)이므로 `u8` 또는 가변 길이 정수(Varint)를 적용하면 문장당 1바이트로 75% 감소.
  3. `sizes_ok` 검증식을 가변 크기 또는 축소된 레코드 크기에 맞게 변경.
- **필요 조치**: `FORMAT_VERSION`을 5로 인상, 역직렬화 시 복원 루틴 추가.

### 4.3 후보 3: DOCS 메타 표 필드 경량화
- **현행 한계**: `DOCS` 구역은 문서마다 24바이트(doc_id: u64, date: i64, first_sid: u32, n_sent: u32)를 고정 사용.
- **설계안**: `first_sid`는 이전 문서들의 `n_sent` 누적합과 정확히 일치하므로 제거 가능(문서당 4바이트 절감). 날짜(`date`) 또한 32비트 정수(YYYYMMDD 형태)로 패킹 가능.
- **필요 조치**: `FORMAT_VERSION` 인상 및 `DocRec` 구조체 변경.

## 5. 결론 및 향후 계획

- kfind-core의 색인 크기 중 가장 큰 부분을 차지하는 **POST(Roaring 비트맵)** 구역에 대해 포맷 버전을 유지하면서 무손실 직렬화 최적화(`bm.optimize()`)를 성공적으로 적용하였다.
- 이를 통해 기존 검색 정확도와 속도, 테스트 스위트를 100% 보존하면서 세그먼트 크기를 안전하게 절감하였다.
- 향후 대규모 색인 크기 추가 축소가 필요한 경우, 본 보고서의 4절에 설계된 TEXT 블록 압축(후보 1)과 DOC_OF 런렝스 인코딩(후보 2)을 `FORMAT_VERSION=5` 배포 일정에 맞춰 적용할 것을 권장한다.
