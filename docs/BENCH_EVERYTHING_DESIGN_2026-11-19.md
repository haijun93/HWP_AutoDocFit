# Everything 대 몽땅검색 검색 속도 벤치마크 설계

- 작성일: 2026-11-19
- 작업: `feature/BENCH1`
- 상태: 설계안. 구현·실측 전
- 요구: 로컬 Everything과 몽땅검색의 속도를 비교해 저장·분석하고, 몽땅검색 개선 피드백 자료로 활용

## 기준

검색 성능 벤치마크의 기준은 다음 두 가지다. 모든 측정, 저장 스키마, 분석·피드백, 앱 화면 및 구현 단계는 두 기준을 함께 다룬다.

- **기준 A — 검색 속도:** 질의별 지연 분포(p50·p90·p95·p99), 결과 건수와 상위 N 일치율을 본다. 왕복 지연과 엔진 내부 시간을 구분하고, 결과 품질과 표본 수 경고도 함께 기록한다.
- **기준 B — 리소스 사용:** 양쪽 검색 엔진의 측정 대상 프로세스에 대해 상주 메모리(Working Set·Private Bytes), CPU(프로세스 CPU 시간 delta 및 코어 대비 평균 사용률), 디스크 I/O(읽기·쓰기 바이트·횟수), 핸들·스레드 수를 측정한다. 색인 저장 크기는 별도로 기록하고, 질의 1건당 메모리 증가량과 CPU 시간도 산출한다. 색인 구축·갱신 비용은 선택 항목이다.

속도와 리소스는 같은 실행·질의 구간에 연결해 해석한다. 측정할 수 없는 지표는 0으로 대체하지 않고 `unavailable` 상태와 사유를 저장한다.

## 1. 확인 범위와 기존 자료

### 확인한 구현

- `crates/kfind/src/pipe.rs`의 파이프 프로토콜은 길이 접두 JSON 요청이며 `query`, `count`, `names_query`, `names_status` 등 명령을 받는다. 요청 프레임 상한은 64 KiB다.
- `crates/kfind/src/service.rs`에서 `NamesQuery`를 `NamesService::query`로 전달한다. `crates/kfind/src/names.rs`는 `kfind_names::parse`와 `hits`를 이용해 파일명 질의를 처리하며 서비스 응답에 `ms`와 제한 개수 결과를 포함한다. 색인 상태는 `names_status`가 제공한다. 벤치마크는 검색어당 새 요청 ID를 쓰고 원시 왕복 시간을 별도로 잰다. 엔진 내부 `ms`와 파이프 왕복 지연은 구분해 저장한다.
- `docfit_app/kfind_client.py`가 Windows 명명 파이프를 통해 요청하며 기본 시간 한도는 2초다. 벤치마크에서는 기본 2초 제한이 긴 실행을 끊을 수 있으므로 명시적인 벤치마크 시간 한도/취소 정책이 필요하다.
- `docfit_app/ktm_service.py`의 실제 화면 질의 연결 경로는 이 조사에서 정확한 호출 함수까지 확인되지 않았다. 구현 단계에서 다시 추적한다. 파이프 명령과 Python 클라이언트가 현재 확인된 측정 접점이다.
- 사이드바 탭 상수는 0–14, 현재 탭 7이 몽땅검색, 12 설정, 13 사용 방법, 14 아웃라이너다. 구현부가 탭 12·13을 기본 탭 반복에서 제외한다. 개발자 모드에서만 외부 앱 메뉴를 추가하는 별도 경로가 있다.
- `hidden_tabs`는 메뉴 표시 설정이며, 개발자 전용 탭은 이 설정과 개발자 모드 노출 조건을 함께 고려해야 한다. Dock 메뉴는 실제 같은 탭 목록을 이용하는지, 별도 목록인지 이번 조사에서 미확인이다. '쓸 메뉴 고르기' 화면의 모든 필터 동작도 구현 단계 확인이 필요하다.
- `docfit_app/application_service.py`는 `developer_mode` 설정을 읽어 개발자 전용 기능을 차단/허용한다. 새 벤치마크 명령도 화면 숨김만으로 보호하지 말고 백엔드에서 이 값을 검사해야 한다.
- PDF 편집기와 아웃라이너 서비스는 설치 폴더의 `resources/` 및 PyInstaller `_internal/resources/`에서 Rust 실행 파일을 찾고, 개발 시 Rust `target/release` 후보를 확인한다. 백엔드 서비스가 Rust CLI를 실행하는 기존 배포 패턴이다.

### 기존 자료와 중복 방지

- `docs/DFB2_COMPARE_2026-11-12.md`와 원자료 JSON은 본문 검색 비교다. 측정 경계, 반복, 원시 자료와 정확도 비교의 주의점을 참고하되 파일명 검색 성능을 대신하지 않는다.
- 저장소에서 관련 검색으로 찾은 벤치마크 문서는 위 DFB2 문서 외 `BENCHMARK_HWP_TABLE_TEMPLATES.md`, `IEUMOFFICE_BENCHMARK_REPORT.md` 등이다. Everything 대 몽땅검색 파일명 비교나 BENCH2 보고서는 확인되지 않았다.
- `scripts/bench*`라는 이름의 파일은 확인되지 않았다. `scripts/perf_baseline_pc.py`는 존재하지만 본 과제와 직접 관련 있는 실행 경로·기록 형식은 아직 분석하지 않았다. 이 문서는 기존 자료를 복제하지 않고 DFB2를 링크한다.
- 이번 조사에서 확인되지 않은 항목은 구현 시작 시 재확인한다. 아래 수치와 세부 동작은 별도 표기가 없는 한 제안값이지 측정 결과가 아니다.

## 2. 측정 대상

### 공정 비교: 파일명 검색

Everything의 본업에 맞춰 `kfind names` 파일명 검색과 Everything 파일명 검색을 같은 질의 세트·같은 로컬 PC에서 비교한다. 대상은 파일명/경로 질의의 검색 지연과 결과 집합이다. 몽땅검색 본문·문서 위계 검색은 Everything에 직접 대응하는 색인이 없으므로 별도의 **몽땅검색 단독 측정** 섹션으로 둔다.

Everything의 `content:` 질의는 파일 내용을 검색하는 경로로, Everything의 파일명 색인 질의와 동등하지 않으며 느린 전체 훑기를 포함할 수 있다. 기본 벤치마크에서 제외한다. 향후 선택형 실험으로 추가한다면 별도 탭/실험군에 격리하고 파일명 비교의 점수나 요약에 합산하지 않는다.

### 단독 측정

- kfind 본문 질의(`query`) 또는 문서/위계 특화 질의는 별도 질의 유형으로 계측한다. 실제 UI 경로와 동등한 기능 범위·응답량을 기록한다.
- `count`는 결과 건수 계산 전용이므로 파일명 결과 목록 수신과 직접 비교하지 않는다. 동일한 건수 전용 측정 항목으로만 비교한다.
- 결과를 `top N`으로 자르는 비교는 양쪽에 같은 N을 적용한다. 전체 건수만 측정하는 실험과 결과 목록 수신 실험을 서로 섞지 않는다.

## 3. 질의 세트와 개인정보

### 질의 종류

질의 세트는 버전 필드를 가진 JSON 파일로 저장한다. 기본 제공 고정 세트와 사용자가 선택적으로 생성한 로컬 표본 세트를 분리한다. 각 항목은 ID, 범주, 원문 질의(입력 파일 안), 필터/문법, 비교 가능 여부, 기대 기능 범위를 가진다.

| 분류 | 예 | 구분 |
|---|---|---|
| 한글 2글자·3글자·긴 문구 | `계약`, `인사평가`, 여러 어절 문구 | 비교 |
| 영문·숫자 | `report`, `2026` | 비교 |
| 확장자 필터 | `ext:pdf` 및 검색어와 결합 | 양쪽 문법을 동등하게 매핑할 수 있을 때만 비교. 매핑 불일치는 단독 |
| 경로 조각 | `업무자료\2026`의 일부 | 양쪽 경로 검색 의미를 맞춘 경우 비교 |
| 공백 포함 다중 낱말 | `인사 평가 결과` | 결과 의미를 정규화·기록해 비교 |
| 결과가 매우 많은 질의 | 흔한 접두어나 짧은 단어 | 비교, 결과 상한 적용 |
| 0건·드문 질의 | 존재하지 않을 가능성이 큰 질의, 희귀한 표본 | 실제 결과 수를 기록하고 분류는 실행 후 보정 |
| 몽땅검색 고유 문법 | 공백 무시, 초성 검색 | 단독. Everything과 의미 동등성 없음 |

검색 문법/필터 구문은 엔진별로 다를 수 있으므로 세트는 공통 의미를 정의하고 어댑터가 각 엔진 질의로 변환한다. 변환할 수 없거나 의미를 보장할 수 없는 질의는 자동으로 비교에서 빼고 `standalone`으로 남긴다.

### 이 PC의 파일명 표본 생성

개발자 도구는 색인된 이름을 바탕으로 질의를 표본 추출할 수 있다. 대상 파일 수와 확장자별 규모는 집계치만 결과에 넣는다. 생성기는 고정 시드를 사용하고, 알고리즘 버전·시드·표본 수를 기록해 같은 조건의 세트를 재생성할 수 있게 한다. 기본 생성 결과는 JSON 세트에 평문 질의를 포함할 수 있으므로 저장/내보내기 시 기본 개인정보 정책을 적용한다.

기본 결과 파일에는 질의 문자열 대신 `query_hash`(정규화 규칙 명시), 길이, 범주, 필터 유형만 저장한다. 원문 질의는 사용자가 명시적으로 **원문 포함**을 켠 경우에만 기록한다. 경로·파일명 원문, 상위 결과 경로 원문은 기본 저장하지 않는다. 일치율은 내부적으로 정규화 경로 해시 비교 또는 이름 원문 노출 없는 식별값 비교로 산출한다. 해시는 사전 대입 위험이 있으므로 사용자 데이터 밖으로 전송하지 않는다. 벤치마크 결과 자동 업로드는 범위에 포함하지 않는다.

## 4. Everything 연결 방식

| 방식 | 장점 | 비용·한계 | 평가 |
|---|---|---|---|
| `es.exe` 명령줄 | 통합이 간단하고 설치된 CLI 활용 | 프로세스 시작·인수 처리 비용이 검색시간에 섞임. 결과 출력 파싱과 버전 차이 검증 필요 | 1차 구현 후보. 질의당 전체 프로세스 시간을 재고 빈 질의/가벼운 질의의 오버헤드 기준선을 별도로 기록. 보정값을 빼서 공식 수치로 만들지 말고 원시간과 기준선을 함께 표시 |
| Everything SDK (`Everything64.dll`, IPC) | 프로세스 시작 오버헤드를 피하고 질의/결과 접근이 구조화됨 | DLL 미설치/버전·아키텍처 호환, 라이선스·배포 조건 조사 필요. 연결 계층 구현 필요 | API 가용성과 공식 사용 조건을 검토한 뒤 저지연 어댑터 후보 |
| Everything IPC (`WM_COPYDATA`) 직접 구현 | 별도 DLL 없이 기존 IPC를 직접 사용할 수 있음 | Win32 메시지, 응답 대기·창 핸들·인코딩·취소·타임아웃을 직접 다뤄야 함 | SDK 의존성을 피할 이유가 확인될 때만 검토. 구현 복잡도와 측정 신뢰성 검증 필요 |
| HTTP 서버 | 요청/응답이 단순하고 언어 중립적 | 사용자가 서버 기능을 켜야 할 수 있고 접근 제어·포트·응답 범위 설정이 필요 | 기본 경로로 쓰지 않음. 명시적으로 활성화된 로컬 서버가 감지되는 환경에서 선택 실험 후보 |

**권고:** 실제 설치 환경의 Everything 버전·SDK/IPC 사용 조건을 확인하기 전 특정 연동을 확정하지 않는다. BENCH2는 어댑터 인터페이스와 가짜 Everything 어댑터를 먼저 만들고, `es.exe` 측정과 SDK/IPC 조사 결과를 통해 기본 어댑터를 선택한다. 프로세스 생성 비용이 포함된 결과에는 측정 경계를 명시한다.

### 탐지와 미설치 동작

- 탐지 정보는 Everything 프로세스 실행 여부와 실행 파일 경로, `es.exe` 후보, SDK DLL 후보 및 버전, 응답 가능한 인터페이스를 상태에 기록한다. 사용자 PATH 및 설치 경로 후보를 확인하되, 실제 후보 목록은 구현 단계에서 검증한다.
- Everything이 없거나 실행할 수 없으면 설치를 요구하지 않고 설치도 시작하지 않는다. 결과에 `everything.status = not_installed` 또는 구체적 오류를 기록하고 몽땅검색 단독 측정만 수행한다.
- Everything이 종료되어 있더라도 `es.exe` 같은 비상주 질의 실행이 가능한지는 어댑터별로 다르다. 실행 여부와 질의 가능 여부를 구별해 표시한다.

## 5. 계측 절차

### 기준 B — 리소스 계측 대상과 방법

측정 대상 프로세스는 엔진별로 실행 전 탐지해 PID·역할·접근 가능 여부를 기록한다. 프로세스 이름만으로 같은 프로세스를 중복 합산하지 않는다.

| 엔진 | 기본 측정 대상 | 합산 규칙 |
|---|---|---|
| 몽땅검색 | `kfind` 파일명 검색 서비스 프로세스, 필요 시 `ktm` 서비스 프로세스 | 역할별 PID 집합의 합계를 엔진 합계로 보고한다. `ktm`은 화면 경로가 호출하는지 확인된 경우 별도 항목으로 포함하며, 미확인 시 제외하고 미확인 상태를 기록한다. |
| Everything | `Everything.exe` 서비스 프로세스와 UI 프로세스 | 같은 PID가 서비스/UI 양쪽 역할이면 한 번만 센다. 서로 다른 PID는 각각과 합계를 기록한다. |

벤치마크 도구 자체 프로세스는 검색 엔진 자원 합계에서 제외한다. 도구 오버헤드 측정이 가능하면 `harness`로 별도 표기한다. 검색 도구의 하위 프로세스가 발견되면 자동 포함하지 말고 PID·포함 여부·이유를 기록한다.

기본 자원 지표는 다음과 같다.

- **메모리:** Working Set과 Private Bytes를 바이트 단위로 샘플링한다. 실행 전체 기준으로 유휴 기준선, 검색 중 최대, 검색 후 값을 저장한다.
- **CPU:** `GetProcessTimes`의 프로세스 커널·사용자 CPU 시간 누적값 차이를 질의 윈도우별로 구한다. CPU 시간 합계(밀리초)와 `(CPU 시간 합계 / 경과 시간 / 논리 프로세서 수) × 100` 코어 대비 평균 사용률을 보고한다.
- **디스크 I/O:** `GetProcessIoCounters`의 Read/Write Transfer Count와 Read/Write Transfer Bytes 차이를 질의 윈도우별로 기록한다. 이는 프로세스 I/O 카운터이며 물리 디스크 장치의 실제 I/O와 같다고 단정하지 않는다.
- **핸들·스레드:** 프로세스별 샘플값과 질의 구간 최대값을 기록한다.
- **색인 저장 크기:** 확인된 색인 파일의 총 바이트 크기를 기록한다. 위치/파일을 접근할 수 없거나 구성이 불명확하면 `unavailable`과 사유를 남긴다. 경로 원문은 저장하지 않는다.
- **질의당 비용:** 질의 전 유휴 기준선 대비 검색 중 최대 Private Bytes 증가량 및 프로세스 CPU 시간 합계를 성공 질의 수로 나눈 값을 산출한다. 질의가 실패·시간 초과된 경우 분모와 실패 수를 따로 밝혀 왜곡을 방지한다.

Windows 구현은 `GetProcessMemoryInfo`, `GetProcessTimes`, `GetProcessIoCounters` 및 필요한 성능 카운터를 후보로 한다. API 선택, 지원 OS, 권한 동작은 구현 전 확정하지 않았으며 미확인이다. 현재 사용자 권한에서 열 수 없는 다른 사용자·서비스 프로세스는 관리자 권한 상승을 자동 요구하지 않고 해당 프로세스/지표를 `unavailable`로 표시한다. 관리자 여부와 접근 실패 사유를 기록한다.

제안 샘플링 주기는 50ms이며 설정과 실제 간격을 결과에 기록한다. 수집은 소수의 대상 PID만 대상으로 하고, 파일 경로 열거·고빈도 UI 갱신을 피한다. 샘플러 자체 CPU 시간을 별도 측정할 수 있으면 기록한다. 50ms 샘플링도 저지연 질의보다 길 수 있어 순간 피크를 놓치거나 스케줄링에 영향을 줄 수 있으므로, 샘플링은 속도 측정과 동일 조건에서 수행하고 측정 부하는 한계로 보고한다.

리소스 윈도우는 엔진별로 워밍업을 마친 뒤, 질의 요청 직전부터 응답·결과 수신이 끝날 때까지로 정의한다. 질의가 직렬 실행되므로 그 구간의 프로세스 카운터 delta를 해당 질의에 귀속한다. 실행 전 검색이 없는 유휴 구간을 제안 기본 N=10초 측정해 프로세스별 기준선을 잡고, 검색 후에도 같은 길이의 유휴 구간을 측정한다. 실행 전체의 유휴 기준선·검색 중 최대·검색 후 상태를 구분한다. 질의 간 대기에는 이전 작업의 CPU/IO가 남을 수 있으므로 안정화 대기와 구간 겹침 검사를 기록하고, 구분할 수 없는 값은 질의 비용에 배분하지 않고 미확인으로 둔다.

색인 구축·갱신 자원 비용은 기본 측정에서 제외한다. 선택 설정을 켠 경우에만 색인 없는 초기 구축 1회 및 기존 색인 갱신을 서로 구분한 별도 절차로 측정하며, 걸린 시간·CPU·디스크 I/O·최대 메모리와 색인 크기 전후값을 기록한다. 반복 가능성 및 색인 초기 상태를 보장할 수 없으면 참고 실험으로 표시한다.

속도와 자원을 한 화면에서 요약할 후보 종합 지표는 `질의당 지연(ms) × 질의당 CPU 시간(ms)`이다. 응답 지연과 CPU 점유를 함께 보지만 메모리·I/O 비용을 반영하지 않으며, 지연이 짧고 CPU 병렬 사용이 많은 경우의 해석이 단순하지 않다. 따라서 합격 점수로 쓰지 않고 원 지표를 함께 제공한다. 대안으로 초당 완료 질의 수와 평균/최대 메모리를 나란히 표시할 수 있으나 질의 세트·결과량에 민감하다.

### 실행 전 상태

1. 사용자가 질의 세트, 반복 횟수, 결과 상한, 시간 제한, 원문 포함 여부를 확인한다.
2. `names_status`에서 kfind 파일명 색인이 `ready`인지, 빌드/갱신 중인지, 마지막 색인 시각·파일 규모·오류를 확인한다. 구현된 필드의 정확한 이름은 실제 응답에 맞춰 기록한다.
3. Everything 어댑터에서 색인 상태를 확인할 수 있으면 기록한다. 확인할 수 없는 상태는 `unknown`으로 둔다. 검색 도중 색인 재구성/갱신이 확인되면 해당 실행을 중단 또는 무효 표시한다.
4. 측정 시점에 두 색인이 모두 사용 가능하고 갱신 중이 아님을 확인한다. 동기화할 수 없는 범위는 결과에 차이로 기록하며 완료된 것으로 가장하지 않는다.
5. 실행 상태는 `preflight → warming → measuring → summarizing → completed`로 명시한다. 사용자 취소는 어느 실행 단계에서든 `cancelling → cancelled`; 오류/시간 초과는 질의별 실패를 기록하고 실행 지속/중단 정책을 적용한다.

### 반복과 시간 경계

제안 기본값은 엔진별 워밍업 2회, 질의별 웜 반복 10회, 결과 상한 1,000건이다. 사용자는 반복·상한을 바꿀 수 있고 결과에 실제 값을 기록한다. 콜드 실행은 각 엔진/질의에서 해당 프로세스·색인 캐시 조건이 차갑다고 보장할 수 있을 때만 별도 표기한다. OS 캐시 전체를 비우거나 Everything을 강제로 재시작하지 않는다. 보장할 수 없는 첫 호출은 `first_observed`라 부르고 콜드 측정으로 간주하지 않는다.

측정 구간을 고정한다:

- **왕복 지연(기본):** 백엔드가 요청을 보내기 직전부터 전체 응답과 지정 결과 상한을 수신·파싱할 때까지. 두 엔진 모두 같은 결과 범위와 경계 사용.
- **첫 결과 시간(선택):** 요청 송신 시작부터 첫 결과 항목을 관측할 때까지. 어댑터가 스트리밍/부분 결과를 제공하지 않으면 `unsupported`.
- **건수 전용(선택):** 건수만 반환하는 완료 시점까지. 양쪽 모두 동등하게 지원할 때만 비교.
- **내부 엔진 시간:** kfind 응답의 `ms` 등 제공되는 내부 시간은 보조값. Everything에 동일 경계 내부 시간이 없을 수 있으므로 왕복 지연과 혼합하지 않는다.

모든 질의에서 양쪽 동일한 `top N`을 사용하고 상한 도달 여부를 기록한다. `es.exe`는 프로세스 시작부터 종료/응답 파싱까지 포함한다. 빈 질의 기준선은 오버헤드 참고치이며 기본 통계에서 차감하지 않는다. 리소스 샘플러는 앞 절의 대상 프로세스와 윈도우를 사용하고, 속도 지연과 같은 질의 ID·반복 번호에 연결한다. 측정 중 CPU·디스크 부하를 낮추기 위해 직렬 실행, 짧은 실행 단위, 진행 표시, 취소, CPU/디스크 상태 메모를 제공한다. 백그라운드 부하를 완전히 통제할 수 없으므로 실행 환경 기록을 남긴다.

### 결과 품질 비교와 통계

전체 결과 수가 양쪽에서 정확히 계산 가능할 때 그 수를 비교한다. 제한된 목록에서는 상위 N의 정규화된 경로 집합에 대한 일치율(교집합/합집합, 두 집합이 모두 비면 1.0)을 계산하고, 순위 일치율은 별도 지표로 둔다. 경로 대소문자·구분자·정규화 규칙을 명시한다. 경로 원문은 저장하지 않는다. 서로 다른 질의 의미/정렬 때문에 상위 순위 차이가 정확도 차이라는 뜻은 아님을 보고서에 설명한다.

각 비교 가능한 질의·엔진에 대해 원시 반복값을 보존하고 p50, p90, p95, p99, 최소, 최대, 평균, 표준편차를 계산한다. p99는 표본 10개에서 안정적이지 않으므로 낮은 표본 수 경고를 붙인다. 타임아웃/오류는 임의로 최댓값 치환하지 않고 실패 건수와 시간 제한을 별도 기재한다. 제외 규칙은 사전 고정한다: 워밍업 제외, 측정 중 명백한 시스템 오류만 실패 표기, 이상치는 원본에서 삭제하지 않는다. 요약 통계는 이상치 포함/제외 선택 여부를 기록하고 기본값은 포함이다.

## 6. 결과 저장 형식

사용자 데이터 폴더의 `benchmarks/` 아래 실행별 JSON 한 개와 CSV 요약 한 개를 저장한다. 경로의 실제 사용자 데이터 루트는 설치 구성에서 확인한다. 파일명 제안: `search-bench-YYYYMMDD-HHmmss-<run_id>.json` 및 동일 접두어 `.csv`. 보존 정책은 제안 기본 30회 또는 총 용량 상한 중 먼저 도달하는 쪽이며, 오래된 파일 자동 삭제는 사용자 확인/명시 설정 없이 실행하지 않는다(초기 구현은 자동 삭제 대신 보존 상한 경고).

## 7. 분석과 피드백

`BENCH4` 분석기는 하나 이상의 스키마 지원 JSON을 읽고 동일한 질의 해시/세트 버전으로 묶는다. 마크다운 리포트는 다음을 포함한다:

- 실행 환경·도구 버전·색인 상태와 비교 유효성 경고
- Everything 존재/미설치, 어댑터/측정 경계와 시간 제한
- 범주·문자 길이·결과 수 구간별 kfind/Everything p50·p95 비교 및 비율
- kfind가 느린 질의, 결과 수가 큰 구간, 0건/희귀 질의 성능
- 속도는 빠르지만 CPU·메모리·디스크 I/O를 많이 쓰는 질의/구간
- 질의 반복 또는 검색 후 유휴 구간에서 Private Bytes가 계속 증가하는 추세(누수 의심 후보; 누수 확정 아님)
- 유휴 상주 메모리·CPU·I/O 비용 비교와 검색 중 피크/검색 후 회복 여부
- 질의당 CPU 시간·메모리 증가량과 종합 지표 후보를 함께 보되 원 지표 및 종합 지표의 한계를 표시
- 건수·상위 N 집합/순위 일치율, 동등성 미확인 문법 목록
- 실패/시간 초과·표본 부족·색인 갱신·시스템 부하 경고
- 같은 조건의 여러 실행 회귀 비교와 변경 전후 차이
- 데이터 한계와 재현 절차

회귀 비교는 같은 기기·어댑터·질의 세트 버전·결과 상한·색인 상태·반복 설정끼리 먼저 묶는다. 반복 3회 미만이거나 p95 표본이 부족하면 회귀 확정 대신 관찰 대상으로 표시한다. 제안 규칙: 동일 질의 범주에서 kfind p50이 기준선보다 20% 이상 느려지고 최소 5개 비교 질의·3회 실행에서 재현되면 TODO 후보를 만든다. 이는 경보용 휴리스틱이지 성능 합격선이 아니다. 사용자/개발자가 원인과 개선 가설을 확인한 뒤 별도 작업 항목으로 수용한다. 원시 파일을 외부로 자동 전송하지 않는다.

## 8. 앱 연결 설계

### 메뉴와 화면

새 메뉴 이름은 **검색 벤치마크**로 제안한다. 개발자 모드에서만 나타나는 workspace 내부 화면으로, 질의 세트 선택, 반복·상한·시간 제한, 개인정보 옵션, Everything 탐지 상태, 색인 준비 상태, 시작/취소, 현재 단계·질의 진행률, 결과 요약표, 저장 파일 열기/폴더 열기를 제공한다. 결과 요약에는 속도 지연 분포·결과 건수·상위 N 일치율과 함께 메모리(유휴/검색 최대/검색 후), CPU 시간·평균 사용률, 디스크 I/O, 핸들·스레드 수를 막대 또는 표로 표시한다. 측정 대상 프로세스의 역할과 포함 여부를 보여주고, 접근 권한 부족·프로세스 미발견·API 미지원은 지표별 사유를 안내한다. 실행 중 취소는 백엔드에 전달하고, 완료·취소·오류를 구분한다.

탭 12·13은 설정·사용 방법으로 고정 사용되고 14는 아웃라이너이므로, 그 번호를 단순 재사용하지 않는다. 현재 `kTabCount=15`인 탭 체계를 확장한다면 **15를 새 내부 탭 번호**로 제안하되 개발자 전용 탭의 `labels` 인덱싱, 탭 생성 배열, 선택 검증, 접근성/키 테스트를 모두 확인한다. 탭 15를 일반 탭 목록에서 숨기고 개발자 모드일 때만 노출하는 구조가 필요하다.

`hidden_tabs`와 '쓸 메뉴 고르기'에서 개발자 전용 메뉴를 숨기거나 다시 보이게 할 수 있는지, 개발자 모드가 꺼질 때 현재 선택 화면을 어디로 돌릴지 명시해야 한다. 메뉴 선택 설정이 보이지 않는 탭을 잘못 활성화하지 않도록 처리한다. Dock이 같은 shell 인덱스를 쓰는지 조사 후 사이드바와 Dock 모두 같은 개발자 노출 정책을 적용한다. 두 메뉴 목록 관계는 현 코드만으로 완전히 확인되지 않았다.

### 백엔드 경로

웹 UI에서 `dart:io`로 프로세스를 실행하지 않는다. Flutter는 기존 백엔드 API로 질의 세트/설정 조회, 사전 점검, 실행, 취소, 진행 조회, 결과 목록/파일 열기를 요청한다. Python 서비스가 `developer_mode`를 검증한 후 Rust `qms_bench` CLI를 자식 프로세스로 실행한다. Python은 표준 입력 JSON 요청 또는 인수/JSON 응답 계약, 표준 출력의 기계 판독 진행 이벤트, 종료 코드, 취소 신호를 중계한다. `subprocess`에는 짧은 폴링/취소 가능한 관리가 필요하며 UI를 막지 않는다.

`qms_bench`는 kfind 파이프에 파일명 질의를 보내고 Everything 어댑터에 같은 질의를 보내며, `benchmarks/` 파일을 생성한다. 다만 결과 파일 위치/쓰기 권한은 Python이 결정·전달하고 CLI는 그 루트 내부만 쓰도록 제한한다. PDF 편집·아웃라이너와 같은 리소스 번들 후보 경로를 사용하고 누락 시 정확한 `ENGINE_MISSING` 상태를 반환한다. 외부 프로세스 인수로 사용자 원문 질의를 노출하지 말고 표준 입력이나 보호된 파이프로 전달한다.

## 11. 미확인 항목

- Everything 설치 버전/실행 여부, `es.exe`, SDK DLL 위치, IPC 및 HTTP 설정 상태는 실측하지 않았다.
- `kfind names`의 현재 인덱스 크기·파일 수·질의 응답 실제 분포, 반환 순서의 안정성은 벤치마크하지 않았다.
- `names_status`의 구체 JSON 필드와 색인 완료 시각 표현을 조사해 문서에 고정하지 않았다.
- `ktm_service.py`에서 화면 질의가 `names_query`를 어떻게 호출하는지 상세 호출 함수, 실제 결과 상한은 구현 시 재추적해야 한다.
- 앱의 사용자 데이터 루트, Dock과 '쓸 메뉴 고르기'의 탭 목록 소비 방식은 미확인이다.
- `scripts/perf_baseline_pc.py`의 본 과제 적용 가능성, CPU/RAM/드라이브/관리자 메타 획득 API는 분석하지 않았다.
- Everything의 설치·재배포·SDK 사용 조건은 검토하지 않았다. 이 문서에서 설치/배포를 제안하지 않는다.

## 12. PM 결정 (2026-11-19, 실제 PC 확인 반영)

- **이 PC 확인 결과**: Everything이 설치돼 실행 중이다(`C:\Program Files\Everything\Everything.exe` 2.2MB, 색인 DB `%LOCALAPPDATA%\Everything\Everything.db` 약 114MB). `es.exe`와 SDK DLL(`Everything64.dll`)은 **없다**. 따라서 4절 권고 보류를 풀고 다음으로 확정한다.
- **1차 연결 = Everything IPC 직접 구현(WM_COPYDATA, SDK와 같은 프로토콜)**: 실행 중인 Everything 창(클래스 `EVERYTHING`)에 쿼리 메시지(`EVERYTHING_IPC_COPYDATA_QUERY2W`)를 보내고 응답 창으로 결과 목록(`EVERYTHING_IPC_LIST2`)을 받는다. 외부 파일·DLL·설치가 필요 없고 프로세스 시작 비용이 측정에 섞이지 않아 공정하다. 응답 대기·타임아웃·취소·인코딩은 어댑터가 처리하고, 건수만 받는 질의(최대 결과 0)와 상위 N 질의를 구분한다.
- **2차(폴백)**: `es.exe`가 PATH나 알려진 경로에 있으면 사용(시작 비용 보정 표기). **3차**: 사용자가 켜 둔 HTTP 서버가 감지되면 사용. 셋 다 안 되면 `everything.status`에 사유를 적고 몽땅검색 단독 측정.
- **IPC 구현 검증 원칙**: 프로토콜 구조체 레이아웃은 SDK 헤더 지식에 근거하므로 가짜 서버(시험용 창)로 시험하고, **실제 Everything 응답은 설치된 인스턴스로 한 번 확인**한다. 실제 Everything에 질의를 보내는 시험은 읽기 전용이고 사용자 PC에 영향이 없다. IPC가 이 Everything 버전에서 응답하지 않으면 추측으로 우회하지 말고 보고한다.
