# PARALLEL0 한/글 2프로세스 측정 결과

## 측정 범위와 환경

ALLQA 문서 4개를 `all` 모드로 1회씩 순차 처리하고, 같은 문서 사본을 문서별 Python 프로세스 2개에서 동시 처리했다. 측정 당시 원본 픽스처 해시는 전후 동일했다. 실행 중 저장소의 제품 엔진 코드는 바꾸지 않았다. 측정 결과물은 저장소 밖에 두었다.

| 항목 | 값 |
|---|---:|
| 한/글 버전 | 2020 계열, 실행 보고서 앱 버전 2.2.93 |
| CPU | 4 물리 코어 / 8 논리 프로세서 |
| 물리 메모리 | 24,409 MiB |
| 반복 횟수 | 각 방식 1회 |
| 처리 모드 / 병렬 상한 | `all` / 프로세스 2개 |

## 측정값

| 지표 | 순차 1프로세스 | 2프로세스 동시 | 해석 |
|---|---:|---:|---|
| 전체 경과 시간 | 135.355초 | 93.857초 | 병렬이 30.6% 짧음 |
| 최대 한/글 프로세스 메모리 합 | 93.2 MiB | 143.7 MiB | 동시 방식에서 54.2% 증가 |
| 관측 구간 최대 프로세스 CPU 합 | 223.2% | 284.4% | 논리 프로세서 8개 기준 각각 약 27.9%, 35.6%; 순간 샘플 최대치 |
| 문서별 실행 시간 | 아래 표 | 아래 표 | 문서 1개 단위로는 병렬 레인의 시간이 모두 더 길었음 |
| 타임아웃 / 멈춤 감지 | 0건 | 0건 | 문서별 타임아웃 900초 |
| COM 잠금 충돌 | 0건 | 0건 | 전체 측정 동안 지정 잠금을 유지했고 타 프로브 충돌은 없었음 |

| 문서 | 순차 시간 | 2프로세스 레인 시간 | 처리 오류 |
|---|---:|---:|---|
| `txt_short` | 29.359초 | 31.854초 | 없음 |
| `hwp_reference` | 73.575초 | 93.796초 | 없음 |
| `hwpx_table` | 6.325초 | 7.151초 | 양쪽 모두 한/글 문서 열기 실패, 결과 없음 |
| `hwpx_continuation` | 26.075초 | 32.354초 | 없음 |

`allqa_compare` 결과, 처리 결과가 생성된 세 문서(`txt_short`, `hwp_reference`, `hwpx_continuation`)는 텍스트 XML 해시와 정규화 서식 해시가 각각 일치했다. `hwpx_table`은 순차·병렬 모두 열기 단계에서 실패해 결과 동일성을 측정할 수 없다. 이 공통 실패를 병렬화로 인한 오류라고 판단할 근거는 없다. 사용자 문서 원본은 사용하지 않았다.

CPU 수치는 HWP 프로세스들의 `psutil` CPU 사용률을 합산한 샘플 최댓값이다. 프로세스별 완료 시간은 서로 겹칠 수 있으므로 합계를 전체 벽시계 시간으로 오해하지 않아야 한다. 이번 측정에서는 샘플 구간별 동시 프로세스 최댓값을 별도 저장하지 않았다. 측정 산출물에 관측된 한/글 PID는 순차 4개, 병렬 4개였으며, PID 수는 최대 동시 개수를 뜻하지 않는다.

## 동시 실행 관련 확인 사실과 미확인

| 주제 | 확인된 사실 | 미확인 / 결과 |
|---|---|---|
| 새 COM 인스턴스 | `com_driver.py`는 독립 생성 시 `DispatchEx`를 먼저 시도하고, 실패하면 `Dispatch`로 재시도한다. 이 시험도 별도 프로세스에서 기존 `smoke_engine_pc.py` 파이프라인을 실행했다. | 각 호출이 실제로 완전히 분리된 한/글 인스턴스를 얻었는지는 제품 런타임의 PID 귀속을 기록하지 않아 미확인이다. |
| 보안 모듈 등록 | 이 측정에서 보안 모듈 등록 충돌 메시지는 관측되지 않았다. | 보안 모듈의 등록 방식·스레드/프로세스 간 동작은 확인하지 않았다. |
| 세션·단일 인스턴스 | 병렬 레인에서 정상 결과 3개가 생성됐고 2프로세스 작업이 끝났다. | 같은 Windows 사용자 세션에서 한/글이 다중 인스턴스를 공식 지원하는지, 단일 인스턴스 제한이 있는지는 확인하지 않았다. |
| 파일 잠금 | 병렬 작업은 문서별 입력 사본과 출력 디렉터리를 분리했다. 잠금 충돌은 기록되지 않았다. | 한/글의 내부 잠금 및 동일 문서 경로 경쟁은 이 구성에서 시험하지 않았다. |
| 클립보드·창 포커스 | `docfit_engine`·`docfit_core`에서 `SendKeys`, Win32 창 활성화, 클립보드 API 호출을 찾지 못했다. `docfit_engine/context.py`의 `activate()`는 실행 컨텍스트 상태를 설정하는 메서드다. | 한/글 및 외부 보안 모듈의 전역 클립보드 동작은 확인하지 않았다. |

## 결론 및 적용 조건

이번 단일 표본에서는 문서 4개 전체를 2개 작업 프로세스로 배치했을 때 벽시계 시간이 줄었지만, 개별 문서 시간은 모두 늘었고 한/글 메모리 사용량도 증가했다. 따라서 대량 일괄 작업에서 총 처리량을 높일 가능성은 보였으나, 안정성과 재현성을 확정하기에는 근거가 부족하다. 4코어/8논리 프로세서, 약 24 GiB 메모리에서만 측정했으며 다른 문서 수·크기·코어·메모리 조건은 측정하지 않았다. 이득이 시작되는 문서 수나 최소 메모리 조건도 `UNMEASURED`다.

이번 결과만으로 제품에 병렬 적용을 권고하지 않는다. 특히 공통 열기 실패를 해결하지 않은 채 확대하면 안 되며, 보안 모듈·인스턴스 분리·파일 잠금 조건을 확인한 추가 측정이 필요하다. 이 카드는 1회 측정만 수행했다.

## 재현 스크립트

`scripts/parallel_probe.py`는 ALLQA 세트 중 2~4개 문서를 선택해 순차 레인과 2프로세스 레인을 각 1회 처리하고 `allqa_compare.py`를 호출한다. COM 잠금은 부모 측정 프로세스가 두 레인 전체 동안 보유한다. 결과·사본 폴더는 호출자가 저장소 외부 경로로 지정한다.
