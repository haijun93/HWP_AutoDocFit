# SPLIT0 측정 결과 — 자간 단계 병렬 분할 (2026-11-24)

## 판정

**구현 비권고.** V0 쪽 범위 분할은 2개 입력에서 실행됐지만 순차 결과와 동일하지 않았다. 9쪽 합성 문서에서는 148개 병합 단위 중 59개가 두 작업자 결과에서 모두 바뀌었고, 병합 후 내어쓰기·쪽 맞춤까지 적용해도 순차 기준선과 73/149 문단의 XML 서식·줄 배치가 달랐다. 3쪽 ALLQA `txt_long`도 병합 후 5개 문단 차이가 남았다. 측정한 자간 하위 단계만 보아도 9쪽 문서는 총 절감 상한이 2.7초, `txt_long`은 오히려 9.3초 느렸다(병합 시간 제외). 준비와 후속 단계를 포함한 실제 파이프라인 시간은 각각 순차보다 17.1%, 18.1% 길었다.

V1 보고서 단위 분할은 측정하지 못했다. 실행 문서에 보고서 제목 표가 없어 제목 표 경계를 세지 못했으며, 네 개의 일반 텍스트 제목을 보고서 경계로 간주하지 않았다. 따라서 보고서 단위 분할의 효과를 이 결과로 추정하지 않는다.

## 실행 조건

- 한/글 2020 COM, 지정된 Python 3.15 환경에서 실행했다.
- 각 COM 작업 묶음은 요청된 COM 잠금을 잡고 실행했다. 병렬 구간 측정에서는 두 한/글 프로세스만 서로 겹쳤다. 다른 시험·빌드는 측정 중 실행하지 않았다.
- 원본 입력은 저장소 픽스처 또는 그 픽스처를 반복해 만든 합성 텍스트였다. 사용자 문서는 쓰지 않았다.
- 각 문서는 준비 1회, 전체 순차 기준선 1회, 가능한 경우 범위 작업자 2회, 병합 후속 확인 1회씩 실행했다. 조건을 바꿔 반복하지 않았다.
- 합성 문서는 `ai_answer_mapo_pots.txt` 내용을 네 번 반복하고 `보고서 1`~`보고서 4` 텍스트를 앞에 붙였다. 준비본은 9쪽이었다. 이 표제는 제목 표가 아니므로 V1 검증 자료로 쓰지 않았다.
- 최초 오프라인 병합은 표 안에 중첩된 문단 노드를 개별 교체하려다 실패했다. 문단 병합 단위를 바깥 문단(표 포함)으로 고친 뒤 저장된 한/글 결과는 재측정하지 않고 다시 병합했다. 수정 후 합성 HWPX 시험 4건이 통과했고, 저장된 병합본은 후속 COM 단계에서 다시 열렸다.

시간은 파이프라인 측정치다. 범위 작업자 시간에는 한/글 시작·문서 열기·저장 과정이 포함된다. 구간 병렬 경과는 외부 실행 폴더의 시작·완료 시각으로 확인했다. XML 병합 시간은 별도 계측하지 않았다.

## 병합·결과 동일성

병합 프로토타입은 준비본을 기준으로 작업자 출력의 바뀐 문단을 골라 문단 XML을 가져오고, 참조 중인 `charPr`·`paraPr` 정의를 합친다. 충돌하는 정의는 새 ID를 부여하고 문단의 참조를 바꾼다. 표와 그 셀 내부 문단은 바깥 문단 단위로 함께 취급했다. 문단 개수가 다르면 병합을 거부한다.

| 비교 | 9쪽 합성본 | `txt_long` |
|---|---:|---:|
| 준비본의 charPr 정의 수 | 19 | — |
| 작업자1 / 작업자2가 추가한 charPr ID | 19–32 / 19–30 | — |
| 새 ID 범위 교집합 | 19–30 (12개 ID) | 개별 범위는 미기록 |
| 병합 중 재매핑한 charPr 정의 | 27 | 5 |
| 병합 직후 바뀐 문단 수(순차 기준선 대비) | 135/149 | 38개 |
| 내어쓰기·쪽 맞춤 후 바뀐 문단 수 | 73/149 | 5개 |
| 본문 텍스트 해시 | 동일 | 동일 |
| 정규화 서식·배치 해시 | **불일치** | **불일치** |

정규화 비교는 `scripts/allqa_compare.py`의 HWPX 비교 규칙을 사용했다. 문단별 차이 위치는 `scripts/analyze_hwpx_diff.py`로 확인했다. 합성본은 자간 외에 문단 모양과 줄 배치도 달랐다. `txt_long` 후속 결과는 차이가 38개에서 5개로 줄었지만 0이 되지는 않았다.

두 결과의 ID 충돌은 단순 병합으로 해결할 수 있었지만, ID 재매핑만으로 페이지 범위가 겹쳐 바뀐 문단의 의미를 판별할 수 없었다. 특히 합성본에서는 변경 소유가 작업자1 전용 72, 작업자2 전용 0, 양쪽 변경 59, 무변경 17로 분류됐다. 이는 페이지 범위 분할과 문단별 병합 선택이 안정적으로 일치하지 않았다는 신호다.

## 시간 이득 상한

순차 기준선에서 V0와 같은 자간·줄 병합 단계만 합산했다. 이 계산은 병합 비용을 0초로 두고도 얻을 수 있는 최대치다.

| 입력 | 순차 동일 단계 합 | 병렬 작업자 중 최장 | 총 절감 상한(병합 전) | 전체 순차 대비 |
|---|---:|---:|---:|---:|
| 9쪽 합성본 | 277.0초 | 274.2초 | 약 2.7초 | 0.3% |
| `txt_long` | 61.3초 | 70.6초 | **절감 없음; 9.3초 증가** | — |

준비·구간 작업·후속 단계를 더한 관측 총시간은 합성본 약 1,106.7초, `txt_long` 약 286.9초다. 각 순차 전체 처리보다 각각 17.1%, 18.1% 길다. 이 값에는 별도 병합 스크립트 계측 시간이 포함되지 않았다. `hwp_reference`는 한 쪽이라 비교할 분할 이득이 없다.

## V1·경계·남은 확인

- 측정 대상으로 고른 ALLQA 문서는 `txt_long`과 `hwp_reference`이며, 두 문서의 제목 표 기준 보고서 경계 수를 조사하지 않았다. 네 개의 일반 텍스트 제목이 있는 합성본도 제목 표 경계를 만들지 않았다. 따라서 다중 보고서 입력의 존재 여부, 보고서 제목 표 검출, 보고서 새 쪽 유지, 보고서별 쪽 맞춤 독립성, V1 구간 시간·충돌·동일성은 **미측정**이다.
- `hwp_reference`는 준비본 기준 1쪽이어서 V1의 의미 여부도 확인할 수 없었다.
- 합성본의 9쪽 전반·후반 분할에서 경계 문단과 쪽이 이동한 뒤의 문단 귀속을 직접 눈으로 확인하지 않았다. 해당 결과는 XML 소유 판정만 사용했다.
- 한/글 화면의 시각적 검수는 하지 않았다. 저장 성공, HWPX 파싱, 텍스트 해시, XML 정규화 비교로 판단했다.
- 측정용 스크립트는 `scripts/split0_run.py`, `scripts/split0_worker.py`, `scripts/split0_merge.py`, `scripts/split0_followup.py`다. 합성 HWPX 병합 시험은 4건 통과했다.

## 최종 권고

**비권고.** 현재 V0 결과는 시간 이득이 측정 오차보다 작거나 음수였고, 두 입력 모두 순차 결과와 달랐다. 후속 단계를 거쳐도 차이가 남았다. 보고서 단위 V1의 유효 자료도 없으므로 제품 구현으로 진행하지 않는다.
