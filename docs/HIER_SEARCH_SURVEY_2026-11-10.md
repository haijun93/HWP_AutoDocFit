# 문서 목차·위계 검색 사례 조사 및 적용 설계

작성·웹 확인: 2026-11-10. 기준 코드: `github/alpha` `2b7ec241`, `docfit_core/hierarchy_search.py`, `document_structure.py`, TODO의 검색 고도화 6개 항목.

이 문서는 설계 적합성 비교다. 제품 간 성능 순위를 제시하지 않으며, 공급자가 제시하는 벤치마크 수치를 우리 문서에서 재현한 결과로 취급하지 않는다. 공개 문서의 현재 내용에 대한 확인이며, 해당 내용이 과거 특정 배포판에도 존재했는지는 미확인이다. 외부 SDK·모델 설치나 사용자 문서 업로드는 하지 않았다.

## 1. 공식 사례와 적용 범위

### PageIndex: 문서를 탐색 가능한 트리로 표현

PageIndex는 문서 구조를 활용하는 추론 기반 검색을 소개한다. 현재 README는 로컬 모드의 텍스트 PDF 색인·저장과 클라우드 모드를 구분하며, 로컬 레이아웃 기반 트리 추출과 모델을 통한 요약·검색을 설명한다. **로컬 색인·저장이 곧 완전한 오프라인 검색을 뜻하지 않는다.** 공식 예시는 모델 API 자격 증명을 사용하는 경로를 포함한다. 완전한 폐쇄망에서의 모델·SDK 조합과 Windows 한/글 문서 처리 지원은 미확인이다. [공식 저장소](https://github.com/VectifyAI/PageIndex), [MIT LICENSE](https://raw.githubusercontent.com/VectifyAI/PageIndex/main/LICENSE).

우리 적용 판단: 트리 노드 ID·제목·페이지 범위를 보존하고 검색 결과에서 해당 경로를 복원하는 설계를 참고한다. 기본 검색에 LLM 호출이나 PageIndex Cloud를 도입하지 않는다. 후보 생성 전에 트리 가지를 강하게 잘라 버리면 잘못된 위계 판정으로 정답 문단이 누락될 수 있으므로, 본문 후보를 확보한 다음 상위 문맥을 확장한다.

### Docling: 제목·번호·서체·레이아웃의 증거 결합

Docling 공식 문서는 PDF 제목의 깊이를 북마크, 개요 번호, 제목 글꼴로 추정하는 선택적 heading hierarchy 복원을 설명한다. 레이아웃 모델이 제목임을 알아내는 것과 깊이를 결정하는 것을 구분한다. 모델 사전 확보와 로컬 경로 지정으로 오프라인 사용이 가능하며, 원격 서비스 사용은 명시적으로 활성화해야 한다. 라이브러리는 MIT이지만 모델·OCR 구성의 이용 조건은 각각 확인해야 한다. [고급 옵션](https://docling-project.github.io/docling/usage/advanced_options/), [MIT LICENSE](https://raw.githubusercontent.com/docling-project/docling/main/LICENSE).

우리 적용 판단: □/ㅇ/-·로마자·숫자·가나다를 하나의 증거로 취급하고 문단 스타일·들여쓰기·앞뒤 역할을 함께 본다. 기존 Rust 위계 엔진의 확정 결과가 있으면 이를 우선한다. 새 추정과 기존 결과의 차이는 진단으로 남긴다. Docling 의존성과 모델은 이번 작업에 추가하지 않는다. HWP/HWPX 및 kordoc의 탭·불완전 내어쓰기에서 Docling이 기존 엔진보다 잘 복원하는지는 미확인이다.

### LlamaIndex: 작은 후보에서 부모 문맥으로 확장

Auto Merging Retriever 공식 예시는 모든 계층 노드를 docstore에 두고 잎 노드로 검색한 뒤 여러 자식 검색 결과를 부모로 합치는 흐름을 제시한다. 예제에는 벡터 색인과 외부 모델 설정이 포함되어 있으므로 그대로 실행하면 오프라인이라고 보장할 수 없다. 프레임워크 소스는 MIT이다. [공식 예제](https://developers.llamaindex.ai/python/framework/integrations/retrievers/auto_merging_retriever/), [MIT LICENSE](https://raw.githubusercontent.com/run-llama/llama_index/main/LICENSE).

우리 적용 판단: 외부 프레임워크를 설치하지 않고 기존 BM25 후보에서 부모·자식 참조와 상위 제목 문맥을 제공한다. 서로 다른 표·장에 속한 자식을 무조건 하나의 긴 본문으로 합치지 않는다. 검색한 문단과 문맥으로 덧붙인 문단을 구별하고 원래 일치 위치를 유지한다. 부모 문맥 추가가 점수·순위를 바꾸는 경우 평가 결과에 원인을 기록한다.

### Azure: 레이아웃 제목과 본문을 별도 필드로 투영

Azure AI Search의 Document Layout skill은 Document Intelligence 레이아웃 모델을 호출하여 제목과 본문을 Markdown 구조로 만들고, Text Split과 index projection으로 청크 및 부모·자식 매핑을 구성한다. 임베딩은 결합 가능한 별도 단계다. 이 문서의 구성은 Azure 서비스·리소스를 전제로 한다. [공식 구조 인식 청킹 문서](https://learn.microsoft.com/en-us/azure/search/search-how-to-semantic-chunking).

우리 적용 판단: 제목 경로와 본문, 원본 위치, 부모 ID를 별도 필드로 저장한다. 청크 크기를 제한하더라도 표의 소속과 상위 제목을 잃지 않는 원칙을 참고한다. Azure 서비스 자체를 배포 가능한 오픈소스 라이선스로 취급하지 않는다. 해당 서비스의 완전한 오프라인 동등 실행과 우리 기관의 계약상 이용 가능 여부는 미확인이다. 기본 경로에 클라우드 API를 넣지 않는다.

### Google: 구조 트리와 조상 제목을 포함하는 청크

Google Document AI Layout Parser는 문서 구조 트리와 표·제목·본문 관계를 보존하고, 조상 제목을 문맥에 포함한 청크를 설명한다. 공식 빠른 시작은 Google Cloud 프로젝트와 Document AI API 호출을 사용한다. 포맷별 제약으로 DOCX 중첩 표, PPTX 숨김 슬라이드 등이 명시되어 있다. [공식 개념·포맷 제약](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk), [공식 API 빠른 시작](https://docs.cloud.google.com/document-ai/docs/layout-parse-quickstart).

우리 적용 판단: 페이지·표는 논리 제목 트리와 별도의 위치 관계로 함께 보존한다. 표 안 제목을 일반 본문의 상위 제목으로 자동 승격시키지 않는다. 클라우드 서비스를 로컬 라이브러리처럼 재배포할 수 있다고 판단하지 않는다. 완전한 오프라인 실행, 한국어 공문서 특화 정확도, HWP/HWPX 직접 입력은 미확인이다.

## 3. 기존 색인·메타데이터·선택적 의미 검색 연동 설계

기준 구현은 `build_index()`와 `search()`의 오프라인 BM25-lite + 부모 경로다. 기존 응답 필드를 유지하면서 노드 모델·일치어·위치·관계 필드를 추가한다. 등록·파일 변경 시 분석 결과를 정규화하고 검색 시 저장된 인덱스만 읽는다. 파일 변경 판정은 기존 등록 계층의 책임이며, 검색 함수가 사용자 문서를 다시 열어 확인하지 않는다.

| 구성 | 담당할 데이터·단계 | 경계·주의 | 이번 범위 |
|---|---|---|---|
| 기존 Python BM25-lite | 현재 토큰·검색 응답 호환, 후보 생성 기준 | 한국어 형태소·동의어 재현율 한계, 기존 순위 변경 추적 필요 | 실행 기반 유지 |
| 기존 Rust 본문 색인 / Tantivy | 본문 후보 ID·점수, 기존 문단 level·원본 위치 재사용 | 문서 ID+문단 위치로 정규화 노드에 조인; 반환되지 않은 페이지를 추정하지 않음 | 이미 제공된 문단 메타데이터를 받는 경계; 별도 Rust 브랜치 병합 여부는 구현·결과 문서에서 명시 |
| SQLite 메타데이터 | document/node ID, parent ID, 페이지·표·경로, revision·해시 | 전문색인 갱신과 revision을 맞춰 오래된 관계 혼합 방지 | 연동 설계; 영속 저장 신규 도입 여부는 구현 범위에 따름 |
| 선택적 벡터 색인 | 어휘가 다른 질의의 추가 후보 생성 | 모델·메모리·색인 비용, 별도 라이선스·한국어 품질·오프라인 배포 검증 필요 | 설계·비교만; 무거운 의존성 추가 금지 |

검색 결합은 ① 기존 색인/BM25 후보 생성 ② 해당 후보의 상위 문맥 확장 ③ 어휘 일치·원래 점수·구조 문맥으로 재정렬의 순서다. 벡터를 나중에 도입하더라도 ①의 추가 후보 공급원으로 두고 같은 문서·노드 ID로 중복 제거한다. BM25와 벡터 점수는 척도가 달라 그대로 더하지 않고 검증된 순위 결합을 별도 평가해야 한다. 이 제안은 이번 작업에서 의미 검색을 실행했다는 뜻이 아니다.

## 4. 검증과 미확인 사항

- 동일 문서·정답 집합에서 일반 전문검색과 위계검색의 Recall@k·MRR·문맥 정확도·색인 시간·검색 지연·메모리를 기록한다. 작은 회귀 fixture의 수치는 실문서 성능 순위나 대규모 처리 보장이 아니다.
- 목차 없는 PDF, 번호 오류, 표 안 제목, `<hp:tab>`, 불완전 내어쓰기는 별도 사례로 둔다. 파싱된 작은 fixture와 실제 바이너리 문서/Windows COM 종단 시험을 구별한다.
- 페이지·표 위치가 없는 입력에는 미확인을 반환한다. 논리 문단 번호를 실제 인쇄 페이지로 꾸미지 않는다. 원문 기호나 사용자 문서는 수정하지 않는다.
- 이 조사에서 각 제품을 설치·실행하거나 동일 데이터로 비교하지 않았다. 우리 데이터의 품질·지연·메모리, 모든 입력 포맷의 실제 복원, 클라우드 계약·데이터 보존 조건의 세부 감사는 미확인이다.
- 외부 클라우드 검색·모델 API는 기본 검색 경로로 채택하지 않는다. 출처 확인을 위한 공개 웹 열람과 사용자 문서를 외부로 보내는 동작을 구별한다.
