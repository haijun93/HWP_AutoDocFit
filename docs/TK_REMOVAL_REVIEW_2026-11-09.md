# `_tk()` 프리징 구조의 근본 해결 — Tk 전면 제거(Flutter 전환) 타당성 검토 (2026-11-09)

> 코드 읽기와 줄 수·호출 수 측정으로 작성했다(`origin/main`). **Windows 실행·프리징 재현·성능 측정은 하지 않았다.** 공수는 근거 있는 추정이며 실측이 아니다.

## 1. 결론
- **"Tk를 Flutter로 옮긴다"는 표현보다 "숨은 Tk 백엔드를 없애고 Tk 없는 Python 백엔드로 옮긴다"가 정확하다.** 숨은 Tk는 화면이 아니라 **모든 API 호출을 한 줄로 세워 처리하는 단일 스레드 + 상태 보관소**이고, 한/글 COM 제어는 Flutter(Dart)가 아니라 Python에 남는다.
- **프리징의 구조적 원인**은 Tk 자체보다 "**모든 API 호출이 Tk 스레드 한 곳을 통과하고, 그 위에서 무거운 일(한/글 COM 실행, HWPX 분석, 파일 I/O)까지 돈다**"는 점이다. 그래서 한 호출이 막히면 화면 전체가 최대 120초 멈춘다.
- **권장: 전면 제거를 한 번에 하지 말고 4단계로 진행**한다. 1~2단계(Tk 우회·전용 스레드 분리·짧은 대기)만으로 프리징 대부분을 줄일 수 있을 것으로 본다(추정). 전면 제거(3~4단계)는 이미 시작된 "네이티브 시제품 전환 계획"과 합쳐 진행한다.

## 2. 현재 구조 (측정)
| 항목 | 값 |
|---|---|
| `desktop_web_ui.py` | 3,721줄, **`self._tk(` 호출 91곳 / 80개 메서드** |
| `self.gui.*` 참조 | 186회(서로 다른 속성·메서드 55개) |
| 레거시 GUI `docfit_ui/legacy.py` | 5,802줄, 메서드 255개, Tk 변수(`StringVar` 등) 선언 75개, tk 관련 참조 488회 |
| `_tk()` 동작 | 요청을 큐에 넣고 숨은 Tk 스레드가 `root.after(0, run)`으로 실행, **기본 대기 120초**(`timeout=120`) |
| `tkinter`를 가져오는 파일 | `hwp-auto-docfit.py`, `docfit_core/abbreviation_dialog.py`, `hwp-auto-docfit-reset.py` 3개뿐 |
| 서식·자간·쪽 배치 엔진(`docfit_engine/`) | **Tk 변수를 읽지 않음**(Tk 변수 `.get()` 0건) — 엔진은 이미 Tk에서 독립 |

### `_tk()`를 쓰는 80개 메서드의 종류(코드 읽기 분류, 근사)
| 종류 | 개수 | 예 | 의미 |
|---|---|---|---|
| Tk 위젯·변수를 직접 건드림 | 15 | `add_paths`, `set_mode`, `set_range`, `open_stages`, `request_close` … | 상태를 Tk 변수에서 읽고 쓴다 → **Tk 없는 상태 객체로 교체 필요** |
| `gui` 상태·메서드만 사용 | 57 | `get_state`, `set_option`, `table_template`, `kclip_window`, `format_profile`, `hwp_bulk`, `_timemachine_service`, `_table_units_command` … | 대부분 **서비스를 부르는 일**인데도 Tk 스레드 위에서 돈다 → **우회 가능성이 큼** |
| `gui`를 쓰지 않음 | 8 | `get_settings`, `get_pending_dialog`, `open_source_file`, `start_zero_click` … | **지금 당장 `_tk()` 없이 실행 가능** |
| 부가 경로 | — | 27개 편집 메서드는 호출 전마다 `_tk(self._cancel_pending_drop)`를 한 번 더 거친다(`_cancel_before_edit`) | 호출 1번에 Tk 왕복이 2번 |

### 프리징을 일으키기 쉬운 구체 사례(코드 확인)
- `table_template`: **서비스 전체(`TableTemplateService`)가 `_tk(...)` 안에서 실행**된다(`learn`은 HWPX 분석 포함).
- `_table_units_hwp`: 표 단위 한/글 복사가 **독립 한/글 COM 인스턴스를 만들고** 보안 모듈을 등록한다(`_table_units_command`가 `_tk` 안). 한/글이 느리거나 응답이 없으면 **그 시간 동안 다른 모든 호출이 줄을 선다.**
- 같은 줄 서기 때문에 몽땅클립보드·타임머신·자료함 등 **서로 무관한 기능도 한 기능의 지연에 함께 멈춘다.**

## 4. 단계별 제안
| 단계 | 내용 | 효과 | 추정 공수* |
|---|---|---|---|
| **0 즉시 완화** | ① `gui`를 쓰지 않는 호출 8개와 `_cancel_before_edit`의 Tk 왕복 제거 ② `_tk` 대기를 짧게(예: 5초) 하고 초과 시 "바쁨" 응답을 즉시 돌려 화면이 120초 멈추지 않게 ③ 프리징 오류추적(TODO)으로 실제 지연 지점 측정 | 가장 작은 변경으로 최악의 120초 멈춤 제거·원인 계측 | 약 1~2주 |
| **1 서비스 분리** | 상태가 필요 없는 서비스(`table_template`, `kclip_window`, `format_gallery`, 타임머신·파일이름·자료함·노트북·문서 도구 등 약 50개)를 `_tk` 밖으로 옮겨 **전용 작업 스레드(풀)** 에서 실행, 서비스별 잠금 | 서로 무관한 기능이 서로를 막지 않음 | 약 2~3주 |
| **2 한/글 COM 전용 스레드** | 한/글 COM 호출(표 단위 복사, 변환, 문서 처리)을 **STA 전용 스레드 + 작업 큐**로 모으고 호출 쪽은 대기 대신 이벤트로 결과를 받음, 한/글 무응답 감지·강제 종료 | 한/글 지연이 UI를 막지 못함 | 약 3~4주 |
| **3 상태·오케스트레이션 이전** | Tk 변수 75개와 `gui` 상태(파일 목록·모드·옵션·진행)를 `AppState`+`jobs`로 옮기고 `작업시작/중단/진행 큐`를 Tk 없이 구현, `_tk()`와 숨은 Tk 제거 | `_tk()` 소멸, 근본 해결 | 약 4~6주 |
| **4 레거시 정리** | `legacy.py`(5,802줄)·Tk 폴백·`tkinterdnd2` 제거 여부 결정, 문서·시험 정리 | 코드 약 6천 줄 감소, 의존성 감소 | 약 1~2주 |
\* 단일 개발자 + AI 에이전트 협업 기준의 거친 추정. 실측·계획 검증 없음. 1~2단계만으로도 프리징 상당 부분이 사라질 것으로 **추정**하나 Windows 계측 전에는 단정할 수 없다.

## 5. 위험·유의
1. **Windows·한/글 실기 검증이 필수**: COM·STA 스레드 동작은 Linux에서 시험할 수 없다. 단계마다 실기 확인을 계획에 넣어야 한다.
2. **회귀 범위가 크다**: `_tk()` 80개 메서드와 이를 호출하는 Flutter 화면 전체, Python 시험 약 4만 줄 중 `gui`를 쓰는 시험이 영향을 받는다.
3. **Tk 폴백(비상 경로) 제거는 정책 결정**: HANDOVER는 "런타임 비상 Tk 경로는 유지"라고 적고 있다. 4단계에서 유지·폐기를 사용자가 정해야 한다.
4. **Flutter(Dart)로 한/글 제어를 옮기는 것은 비권장**: COM 자동화는 Python에 두고 화면만 Flutter로 두는 현 구조가 맞다(앞선 Tauri·Rust 전환 검토와 같은 결론).
5. **동시성 새 위험**: Tk 단일 스레드가 주던 암묵적 직렬화가 사라지므로, 상태를 바꾸는 호출(파일 목록·옵션)은 명시적 잠금·순서 보장이 필요하다.

## 6. 권장 순서와 결정 요청
1. **먼저 0단계**(Tk 왕복 제거·짧은 대기·오류추적 계측)를 진행하고, 계측으로 프리징의 실제 지점을 확인한다.
2. 이어 **1·2단계**(서비스 분리, COM 전용 스레드)로 프리징 구조를 없앤다.
3. **3·4단계(Tk 완전 제거)** 는 네이티브 전환 계획과 합쳐 별도 과제로 일정화한다.

사용자 결정 필요: ① 0단계 즉시 착수 여부 ② Tk 폴백(비상 경로) 유지 여부 ③ 3·4단계를 이번 분기 과제로 할지.
