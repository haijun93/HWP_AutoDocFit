# 팀 운영 규칙 (2026-11-12 사용자 확정)

총괄과 모든 워커(Claude·Codex·Gemini·맥 워커)가 따른다. 다른 문서와 다르면 이 문서와 사용자 최신 지시가 우선한다.

## 0. 작업의 대원칙 (2026-11-12 사용자 지시, 항상 준수)
> "Find all of the implicit state machines in my app. Make the best decision that will elevate all three: the user experience (UX), developer experience (DX), and agent experience (AX) always, without breaking anything."

- 앱 안의 **암묵적 상태 기계**(여러 변수·플래그·호출 순서에 흩어져 있어 "지금 어떤 상태인지"가 코드에 드러나지 않는 흐름: 작업 실행·중단·종료, 색인 중·재색인, 업데이트, 한/글 연결, 화면 전환, 워커 카드 진행 등)를 찾아 드러낸다.
- 결정할 때마다 **사용자 경험(UX)·개발자 경험(DX)·에이전트 경험(AX) 셋을 모두** 올리는 쪽을 고른다. 하나를 올리려고 다른 것을 낮추지 않는다.
- **아무것도 깨뜨리지 않는다.** 기존 동작·시험·결과 문서를 유지하고, 바뀌어야 하면 사용자 결정을 받는다.
- 카드를 쓸 때: 건드리는 코드에 암묵적 상태가 있으면 상태 이름·전이·불가능한 전이를 먼저 적게 하고, 상태를 한곳에서 읽을 수 있게 만든다(화면에는 진행 상태 표시, 코드에는 명시적 상태 값, 에이전트에게는 읽을 수 있는 상태 파일·로그).

- 쉬는 워커가 없게 하되 같은 파일을 두 워커에게 동시에 맡기지 않는다.

## 2. 총괄이 직접 하는 일과 하지 않는 일
- 직접 한다: 과제 쪼개기, 카드·합격 기준 쓰기, 워커가 물어 온 결정, 결과 판정(시험·측정 직접 실행), 병합·게시, 사용자 보고, 몇 줄짜리 수정.
- 하지 않는다: 넓은 코드 읽기, 로그 훑기, 긴 구현, 전수 대조.
- 토큰 절약: 워커 결과는 보고서 파일로 받고 끝부분과 시험 결과만 읽는다. 재전송된 알림에는 한 줄로만 답한다. 진행 보고는 30분 단위.
- 총괄이 쓴 카드도 검증 대상이다. 첫 카드 결과로 지시의 부작용을 확인한 뒤 같은 종류의 카드를 더 띄운다.

## 3. 카드 규칙
- 카드는 30줄 이내. 작업 폴더·브랜치, 고칠 파일, 완료 조건, 금지 사항을 적는다. 카드 경로는 절대 경로로 넘긴다.
- 고정 꼬리: 보고는 한국어, 실제 숫자, 모르면 모른다고 쓴다. 로컬 커밋만 하고 푸시·태그는 총괄이 한다. 기존 시험은 고치지 않는다(고쳐야 하면 되돌리고 보고). 편법(빈 반환·주석 처리) 금지. 임시 파일은 E:/docfit-tmp 아래에 만들고 작업 폴더 안에는 만들지 않는다.
- 어려운 과제는 "조사 먼저 → 하나 고치고 시험 → 커밋"을 되풀이하게 나눈다.
- 워커가 실패하면 같은 카드를 그대로 다시 돌리지 않고 쪼개거나 더 강한 워커로 올린다. 같은 카드 재실행은 1회까지.

## 4. 긴 작업 절차
- 시작 전에 결과물 위치와 합격 기준을 먼저 적는다.
- 범위는 숫자로 밝힌다. "전체"라고 말하기 전에 대상 수, 뺀 것, 보지 않은 것을 건수로 적는다.
- 바꾸기 전에 기준선 수치를 잡고 실패한 시도도 기록한다.
- 원본을 바꾸면 그것을 읽는 쪽(화면, 색인, README, 릴리스 노트, TODO)까지 맞춘다.
- 상태는 reports/PM-HANDOVER.md와 TODO.md에 적어 다른 세션이 이어받을 수 있게 한다.

## 5. 판정과 검증
- 합격은 총괄이 직접 돌린 시험·측정으로만 낸다. 워커 보고 숫자는 "워커 보고"라고 구분해 전달한다.
- 숫자로 좋아진 것만 main에 넣고 효과가 없으면 기록만 남긴다.
- 속도 개선은 결과 문서가 변경 전과 다르면 채택하지 않는다.
- 측정은 1회만, 측정 중에는 다른 시험·빌드를 돌리지 않는다. 한/글 COM 시험은 잠금 파일(C:\HWP_AUTODOCFIT\.com-test.lock)을 잡고 한 번에 하나만 한다. 판정용 전체 시험은 워커가 쉴 때 돌린다.
- 기준을 낮춰 통과시키지 않는다. 측정 도구가 틀렸으면 도구를 고쳤다고 밝힌다.
- 사용자에게 나가는 글(릴리스 노트, README)은 다른 워커 한 곳의 검토를 거친다. 코드 병합에는 이 절차를 붙이지 않는다.

## 6. 저장소·게시 규칙
- GitLab(origin)은 별도 명령 때까지 건드리지 않는다. 푸시는 GitHub에만 한다.
- 알파·감마 버전은 없다. 기능 브랜치에서 개발해 시험 통과 후 main에 병합한다.
- 태그·릴리스는 사용자 승인이 있을 때만 한다. 사용자가 시험 중인 버전은 확인 전에 태그하지 않는다.
- 사용자 문서 원본은 고치지 않고 사본으로 시험한다. XML은 defusedxml만 쓴다.
- Rust 전환은 측정에서 그 모듈이 전체 시간의 큰 몫이고 원인이 계산량일 때만 한다. 한/글 COM 호출부는 Python을 유지한다.

## 7. 새 기능을 시작하는 절차
- 큰 새 기능은 코드 전에 조사 문서(무엇을·왜, 확정된 결정, 선행 사례, 확인 필요 사항)와 계획(단계, 넣는 것·빼는 것, 승인 지점)을 먼저 쓴다.
- 사용자가 방향을 이미 지시한 과제는 승인 대기 없이 진행하고, 사용자 영향이 있는 선택(순위 규칙, 자동 동작, 릴리스)만 결정을 받는다. 답이 없으면 되돌리기 쉬운 쪽으로 간다.
- 작은 수정과 순차 작업(병합, 게시, 설정)은 문서 없이 바로 한다.
