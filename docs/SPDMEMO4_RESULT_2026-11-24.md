# SPDMEMO4 결과 — 긴 문단 본문 자간 COM 호출

## 판정

긴 문단의 본문 자간 단계는 글자마다 HWP COM으로 범위를 선택하고 문자별 자간·장평 정보를 읽는 선형 비용이 주원인이다. 100~800자 단일 문단 실측은 글자 수에 대체로 비례했고 제곱형 호출 곡선은 관찰되지 않았다. 기존 줄 기억은 첫 편집 때 기억을 모두 비운 뒤 같은 줄의 나머지 검사를 캐시하지 않는 점을 확인했다.

편집 직후 기존 기억을 즉시 비우고, 편집 뒤 새로 읽은 위치 결과는 다음 편집 전까지 다시 사용하도록 확장했다. 전체 보고서에서 호출이 1.25%, 시간이 1.66% 줄었고 HWPX 본문·서식 결과는 기준선과 같았다. `DOCFIT_SPACING_MEMO=verify` 전체 실행 불일치 0을 확인한 뒤 `reuse` 결과를 비교했다. 자간 기억을 끄려면 `DOCFIT_SPACING_MEMO=off`를 지정한다.

## 측정 조건

- 작업 브랜치 `feature/SPDMEMO4`, `github/main` 기준 커밋 `1284db55`; Git 원격 접근·푸시 없음.
- Windows 한/글 2020, 사용자가 지정한 venv315 Python 3.15.2.
- 모든 COM 실행은 필수 COM 잠금 아래 순차 실행. 문서별 제한 1,200초. 입력은 HANG1 합성 TXT의 외부 사본이다.
- 보고서형 fixture SHA-256은 `f6b123bacdbb66296dceb1123c3e4e228424d423770acd785437fa79aed471af`; 측정 전후 원본·사본 해시는 같았다.
- 첫 계측 시험은 호출 위치 경로를 매 COM 호출마다 정규화해 1,008초가 걸렸다. 경로 정규화를 파일별 캐시로 변경한 뒤 재측정했고 아래 기준선 851.7초를 사용했다. 이는 HANG1의 847.5초와 0.5% 차이다.

## 기준선 호출 위치 상위 5곳

기준선 본문 자간 단계는 352,420회, 798.3초(COM 내부 760.6초)였다. 상위 지점의 호출 수는 5곳 합계 224,130회로 본문 단계의 63.6%다.

| 순위 | 파일:줄 · 함수 | 호출 | 단계 호출 비율 | 해석 |
|---:|---|---:|---:|---|
| 1 | `docfit_engine/spacing.py:917` · `<genexpr>` | 63,000 | 17.9% | 문자별 자간 슬롯 읽기 |
| 2 | `docfit_engine/spacing.py:920` · `<genexpr>` | 63,000 | 17.9% | 문자별 장평 슬롯 읽기 |
| 3 | `docfit_engine/formatter_utils.py:561` · `hwp_run` | 48,690 | 13.8% | 한/글 액션 실행 |
| 4 | `docfit_engine/spacing.py:458` · `단어모드_범위선택` | 24,720 | 7.0% | 선택 전 위치 지정 |
| 5 | `docfit_engine/spacing.py:459` · `단어모드_범위선택` | 24,720 | 7.0% | 선택 범위 설정 |

자간·장평 혼합 서식 보존을 위해 `단어모드_서식보관`은 문자를 하나씩 선택하고 값을 읽는다. 같은 단어·줄 후보를 반복해서 시험할 때 이 문자별 조회가 누적된다. `최소_성공단계_탐색`은 이미 작은 단계 선형 검사 뒤 이분 탐색을 사용한다. 따라서 전체 문단 위치 후보를 단순 이분 탐색으로 바꾸는 것보다, 편집 후 동일 위치 재조회와 문자별 서식 읽기가 더 직접적인 원인이다.

## 문단 길이 곡선

HANG1 보고서형 fixture의 첫 본문 문장에서 잘라 만든 단일 문단을 `mode=spacing`으로 각각 한 번 측정했다. 시간에는 변환·저장 등이 포함되며 COM 횟수는 `본문 자간·단어 분리 조정` 단계다.

| 문단 문자 수 | 본문 단계 COM 호출 | 본문 단계 시간 | 호출/문자 |
|---:|---:|---:|---:|
| 100 | 2,364 | 2.30초 | 23.6 |
| 200 | 6,496 | 7.21초 | 32.5 |
| 400 | 14,434 | 19.80초 | 36.1 |
| 800 | 30,616 | 47.56초 | 38.3 |

100→800자는 길이 8배, 호출 12.95배다. 네 점 로그 회귀의 지수는 1.22로 측정됐다. 짧은 입력의 초기·줄바꿈 비용을 포함한 단일 실행이라 복잡도 증명은 아니지만, 긴 구간의 400→800자는 길이와 호출이 2배 안팎으로 증가해 제곱형 증가와 다르다. 전체 보고서형 입력은 9,500자에서 본문 단계 352,420회, 약 37.1회/자였다.

## 반복 읽기와 기억 검증

기존 기본 `reuse` 기준선에서 줄 기억 로그는 157개였다. 편집 전 반복 위치 조회 4,428건 가운데 2,386건(53.9%)은 값이 바뀌지 않아 기억 적중했다. 다만 첫 편집이 발생하면 기억을 비우고 이후에는 새 값을 기억하지 않아, 편집 뒤 같은 줄을 다시 확인하는 읽기는 계속 한/글에 왕복했다.

이를 보완해 모든 편집 때마다 세대 기억을 지우고, 편집 뒤 첫 실제 조회부터 새 값을 축적하도록 바꿨다. `verify`는 읽기를 생략하지 않고 캐시된 결과와 매번 비교한다. 전체 보고서 문서에서 줄 기억 로그 157개 모두 불일치 0, 진단 불일치 0이었다. 그 다음 `reuse` 측정에서 기억 적중은 2,596건이었고 본문 COM 호출은 352,420→348,016회(-4,404, -1.25%)였다. 조회 하나가 생략하는 COM 수는 위치·분기에 따라 달라 조회 적중률과 COM 호출 감소율은 같지 않다.

## 기존 ALLQA 6건 결과 비교

`scripts/allqa_run.py`를 `DOCFIT_SPACING_MEMO=off`와 `reuse`로 각 6건 순차 실행하고 `scripts/allqa_compare.py`를 사용했다.

- 저장 성공 5건: `txt_short`, `txt_long`, `hwp_reference`, `hwpx_continuation`, `hwpx_shapes`. 전후 문단 변경 0, 본문 텍스트 XML 동일, 원시·정규화 서식 XML 동일.
- `hwpx_table`: 전후 모두 같은 종료 코드 1, 결과 저장 실패. 기존 SPDMEMO 문서에서도 양 모드에서 관찰된 동일 실패다.
- 비교 실행의 총 COM 호출은 154,212→140,294회였다. 이 합계에는 확장 전부터 있던 캐시 효과도 포함되므로, 이번 변경만의 호출 감소량은 전체 보고서 전후 비교(-4,404회)를 기준으로 본다.
- `allqa_compare.py`의 원본 텍스트 보존 플래그는 `txt_short`, `txt_long`, `hwp_reference`에서 양쪽 모두 FAIL로 표시했다. 그러나 전후 저장 HWPX 직접 대조는 세 문서 모두 텍스트·서식 해시가 같고 문단 변경 0이다. 이 플래그는 사전 존재하던 원본 형식별 대조 한계로 보고, 전후 HWPX 동일성은 직접 해시 비교로 확인했다.

## 시험과 남은 제한

- 계측·줄 기억·경계 기억·HANG1 재현 대상 시험: 23개 통과. 전체 `python -m unittest discover -s tests`: **3,584개 실행, OK, 28개 건너뜀(849.531초)**.
- 전체 unittest 종료 때 `tests/__init__.py` 임시 샌드박스 정리 콜백이 잠긴 `timeline-content.sqlite` 때문에 `PermissionError`를 출력했다. unittest 결과는 OK이며 HANG1 기존 전체시험에서도 보고된 동일한 종료 정리 경고다.
- 네 길이 곡선은 각 1회이며 합성 단일 문단 기준이다. 대규모 서식 혼합 문단의 성능 곡선은 측정하지 않았다.
- HANG1 전체 보고서 입력은 원본 텍스트 보존, 4쪽, 15문단 완료를 확인했다. ALLQA의 `hwpx_table` 실패 원인은 이 작업 범위에서 조사하지 않았다.
