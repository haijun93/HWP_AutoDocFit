# SCANSPEED1 — 앱 안의 문서뷰·사진뷰 검색 속도 (2026-11-26)

사용자 보고: win32 창에서는 검색이 빠른데 앱 안의 화면에서는 매우 느리다.

## 원인

| 구분 | 확인한 내용 |
|---|---|
| 공통 | 앱 경로는 검색 결과를 모두 모은 뒤 한 번에 넘겨, 저장된 목록이 없으면 끝날 때까지 화면이 비어 있었다. win32 창은 klib 출력을 읽는 대로 보여 준다. |
| 사진 | 사진 한 장마다 DB 연결·커밋을 한 번씩 했고, 목록 표시가 이 작업이 끝날 때까지 기다렸다. |
| 사진 | 기본 루트는 소문자 표기인데 DB는 실제 대소문자로 저장해, 바뀌지 않은 사진도 **검색할 때마다** EXIF를 다시 읽고 저장했다(수정 전 두 번째 검색이 첫 검색과 같은 시간: 1만 장 178초). |
| 사진 | 목록·이름/태그 검색에서 파일마다 stat·썸네일 키 계산·캐시 파일 읽기를 했다. |
| 문서 | 행마다 썸네일 키(SHA-256) 계산, 저장 목록은 행마다 `is_file`, 전체 목록을 응답 하나(5만 개에 15.5MB)로 전달했다. |
| klib 호출 | 앱은 `루트 × 예약 폴더 이름` 제외 인자를 추가로 넘겼다. klib은 예약 폴더를 스스로 건너뛰므로 중복이었다(단독 효과는 따로 재지 않음). |

## 바꾼 것

- `scan_progress` 에 `since` 를 주면 새 행만 한 번에 최대 4,000개 돌려주고, 최종 결과의 전체 목록은 뺀다. `since` 없이 부르면 이전과 같다. 데스크톱(`desktop_web_ui`)과 `application_service` 는 모두 서비스의 `command` 를 그대로 부르므로 두 경로에 함께 적용된다.
- klib·검색 서비스(kfind) 응답을 읽는 대로 행을 내보낸다. 겹치는 루트의 같은 파일은 한 번만 보낸다.
- 화면은 저장된 목록이 없을 때 새 행을 이어 붙인다(격자 가상화 유지). 이름순 정렬은 끝난 뒤 한 번만 한다. 목록 위에 진행 띠와 취소 단추를 둔다.
- 사진은 먼저 목록을 보여 준 뒤 DB 저장·EXIF 읽기를 한다. DB는 500장씩 한 트랜잭션으로 저장하고, 바뀌지 않은 사진은 다시 읽지 않는다. 끝나면 선택·검색 결과를 유지한 채 DB 목록(촬영일 반영)으로 바꾼다.
- 문서·사진 목록의 썸네일 키 계산을 없앴다(`thumb_key` 는 빈 값, 썸네일 요청 때 계산). 파일 존재 확인은 폴더를 한 번씩만 훑는다.
- 저장 목록 확인은 배경 검색을 시작하기 전에 한다(함께 돌면 파이썬 실행 잠금을 다툼).
- 저장 목록 쓰기는 `json.dumps` 로 바꿨다.
- 문서뷰를 다시 열었을 때 검색이 이미 돌고 있으면 오류 대신 그 검색을 이어서 보여 준다.

동작 차이: 첫 검색 중에는 찾은 순서로 보인다. 검색 중 사진의 날짜는 DB 값, 없으면 수정 시각이며 끝나면 촬영일로 바뀐다. 검색을 취소해도 보이던 목록은 남는다(아직 DB에 저장하지 않은 사진은 이름·태그 검색에 나오지 않는다).

## 측정

`scripts/bench_library_scan.py` 로 쟀다. 화면과 같은 순서로 서비스를 부르고(120ms 간격), 브리지 전달은 응답의 JSON 변환·해석 시간으로 대신했다. 실제 웹 브리지·설치본의 시간은 아니다. 단위는 초.

### 문서(합성 PDF, 다른 시험이 없을 때 같은 폴더를 번갈아 2회)

| 개수 | 실행 | 첫 항목 전 → 후 | 전체 완료 전 → 후 |
|---|---|---|---|
| 1만 | 첫 검색 | 0.56~0.68 → 0.14~0.15 | 0.56~0.68 → 0.42~0.44 |
| 1만 | 저장 목록 있음 | 0.70~0.75 → 0.16~0.17 | 0.88~0.95 → 0.61 |
| 5만 | 첫 검색 | 3.1~4.6 → 0.14~0.15 | 3.1~4.6 → 1.8~2.0 |
| 5만 | 저장 목록 있음 | 4.9~5.1 → 0.85~0.99 | 5.3~5.5 → 2.6~2.7 |
| 5만 | 다시 검색 | 2.5 → 0.14~0.15 | 2.5 → 1.7~1.8 |

- win32 방식(klib 출력만 읽음): 첫 줄 0.03, 전체 1만 0.08~0.14 / 5만 0.34~0.58.
- 5만 개에서 모든 행이 화면 쪽에 도착한 시점은 약 1.5.
- 가장 큰 응답 크기(5만 개 첫 검색): 15.5MB → 1.0MB. 저장 목록은 여전히 13MB를 한 번에 준다.

### 사진(EXIF가 있는 작은 합성 JPEG)

| 개수 | 실행 | 첫 항목 전 → 후 | 전체 완료 전 → 후 |
|---|---|---|---|
| 1만 | 첫 검색 | 209 → 0.13 | 209 → 50 |
| 1만 | 저장 목록 있음 | 0.25 → 0.70 | 176 → 3.9 |
| 1만 | 다시 검색 | 178 → 0.44 | 178 → 3.7 |
| 5만 | 첫 검색 | 1,040 → 0.13 | 1,040 → 103 |
| 5만 | 저장 목록 있음 | 미측정 → 0.75 | 미측정 → 5.1 |
| 5만 | 다시 검색 | 미측정 → 0.51 | 미측정 → 6.0 |

- 새로 만든 파일이라 첫 검색의 완료 시간에는 파일을 처음 여는 비용(백신 검사 등)이 들어 있다. 파일을 미리 한 번 읽은 1만 장 재측정에서는 첫 항목 0.14, 모든 행 도착 1.2, 완료 11.5였다(수정 후만).
- 1만 장 "저장 목록 있음" 의 첫 표시는 0.25 → 0.70 인 측정과 0.25 인 재측정이 있었다.
- 이름 검색(100건): 0.03~0.07 → 0.06~0.09. 전체가 걸리는 검색: 1만 0.96 → 0.20~0.39, 5만 4.6 → 0.60.

### 화면 구성(Flutter 시험 환경, 수정 후, 응답 JSON 변환·해석 포함)

| 개수 | 문서 목록 | 사진 목록 | 사진 검색 결과 |
|---|---|---|---|
| 1만 | 0.81 | 0.82 | 0.63 |
| 5만 | 1.43 | 1.80 | 1.06 |

한 번에 모든 묶음을 처리한 합계다(첫 묶음만의 시간은 이보다 짧다). 수정 전 화면 시간은 재지 않았다.

### 실제 드라이브(1회, 수정 후, 개수·시간만, klib 엔진)

| 대상 | 개수 | 첫 항목 | 모든 행 도착 | 완료 |
|---|---|---|---|---|
| 문서 | 65,533 | 0.13 | 14.9 | 23.8 |
| 사진 | 187,147 | 0.12 | 22.8 | 1,682 (28분, 첫 EXIF 정리 포함) |

- 같은 범위의 klib 단독 전체 시간은 문서 44.4, 사진 24.6이었다. 문서 쪽 klib을 먼저 돌려 디스크 캐시가 없던 상태라 앱 값과 직접 비교할 수 없다.
- 실제 드라이브의 수정 전 값은 재지 않았다. 임시 DB·캐시는 측정 뒤 자동으로 지웠다.

## 남은 문제

- 설치본 실기 확인(첫 검색 중 선택·취소·파일 작업·오른쪽 메뉴, 실제 브리지 전달 시간)이 남았다.
- 검색 서비스(kfind) 엔진 경로의 시간은 재지 않았다.
- 사진의 첫 EXIF 정리는 사진이 많으면 오래 걸린다(위 28분). 목록은 보이지만 진행 띠 문구는 계속 "사진 검색 중" 이고, 끝나기 전에 앱을 닫으면 저장 목록이 남지 않는다(이미 저장한 묶음은 다시 읽지 않는다).
- 저장 목록의 첫 전달, 사진 검색이 끝난 뒤의 `list_by_date`, 전체가 걸리는 검색은 여전히 한 응답이다(실제 사진에서 57MB).
- 사진뷰의 새로고침 단추와 폴더·카메라·위치 보기는 끝날 때까지 대기 화면이다.
