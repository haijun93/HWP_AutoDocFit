# UNIFIED1 — 몽땅검색 통합 검색 1단계 결과

기준 `github/main`의 `8b18b99d`, 작업 브랜치 `feature/UNIFIED1`. `unified_search` 기본 false를 유지하고, 켠 경우에만 ktm의 검색 요청 하나에서 파일명 → 위계 → 본문을 스트리밍하는 경로를 구현했다. 로컬 커밋만 하며 푸시·태그·병합·배포·설치본 교체는 하지 않는다.

## 구현과 계약

- `ktm/src/backend/unified.rs`: 세 단의 순차 상태·완료·오류·취소 및 결과 합성을 관리한다. 단별 최대 200 후보에서 중복을 제거한 뒤 출력 상한 20·20·40을 적용한다. 상위 단의 표시 상한 밖 후보도 하위 단에 중복 표시하지 않는다. 최대 80행이며 설정의 총상한도 적용한다.
- 대표 행에는 선택된 단 하나만 `match_kinds`로 남긴다. 파일명 자체, 위계/문단 위치, 기존 발췌/미리보기를 근거로 쓴다. 경로 대소문자·슬래시·점 경로·확장 경로 접두사 및 경로 없는 doc_id 별칭을 합친다. 같은 이름의 다른 폴더 문서는 유지한다.
- `window.rs`: 기존 worker/Condvar와 세대별 취소를 재사용한다. 설정을 켜면 All 작업 하나를 큐에 넣고 backend의 누적 스냅숏을 받는다. 각 스냅숏을 실제 그려 빠른 후속 응답에 파일명 첫 화면이 합쳐지지 않게 한다. 선택 문서도 유지한다. 한 단 실패 후 다른 단이 성공해도 오류를 보존하며, 실패한 단도 완료 처리한다.
- `settings.rs`: `unified_search=false`; 구 설정 역직렬화와 저장 왕복 시험을 추가했다. **설정 JSON에서 true로 켜고 ktm을 다시 시작한다.** 설정 화면의 새 토글은 이번 범위에 넣지 않았다. false면 기존 세 작업·합성 경로를 유지한다.
- 연관 검색은 현재 브랜치의 `names_query` → `search_groups`, 본문/위계 `search_groups_by`를 그대로 사용한다. `;` 묶음 일부가 이름, 나머지가 본문에만 있는 것을 합쳐 일치로 만들지 않는다. 파일명 날짜 조건을 이름 낱말로 보내지 않도록 분리하고, `ext:hwp;pdf`를 공통 파서 앞에서 보호한다.
- 새 상주 스레드·타이머·이름 색인 복제는 없다. 요청 종료 시 최대 600 후보 세션을 해제한다. 측정 예제의 kfind-names 의존성은 dev-dependency라 ktm 배포 바이너리에는 들어가지 않는다.

## 기존 호출 흐름과 이번 기준선

기존 경로는 `Effect::Search(All)` → Pending.search의 Names(20)·Hierarchy(20)·Body(40) → worker의 세 질의 → `Reply::Search` → UI `combine_results` → GDI다. 파일명은 서비스 파이프, 위계·본문은 기본 mmap이며, 위계는 본문과 같은 집합을 위계 순으로 정렬한다. 이름·위계·본문이 빠르게 모두 도착하면 첫 그림에 합쳐진다. 기존 합성은 같은 문서의 모든 일치 종류를 병기한다.

이번 같은 합성 1천 건, release, 단일 측정 프로그램 실행에서 각 질의 7표본을 수집했다. 아래는 transport·GDI를 뺀 p50이다. 기존 UI와 같은 20·20·40 질의를 기존 합성에 연결한 기준선이다.

| 질의 | 파일명 계산 | 위계 mmap | 본문 mmap | 기존 전체 합성 | 새 파일명 스냅숏 | 새 전체 합성 |
|---|---:|---:|---:|---:|---:|---:|
| 예산집행 | 0.040ms | 0.748ms | 0.757ms | 1.770ms | 0.123ms | 2.724ms |
| 2026; 공사 계약 | 0.025ms | 0.445ms | 0.436ms | 0.932ms | 0.029ms | 0.945ms |

새 경로는 후보를 단별 200건까지 받아 중복 제거 후 빈자리를 채운다. 첫 질의는 기존 61행 → 새 80행으로 늘어 계산 시간이 약 0.954ms 증가했다. 두 번째는 양쪽 4행이다. 동일 결과량에서 빨라졌다는 주장이나 Everything보다 빠르다는 판정은 하지 않는다.

## 실제 격리 ktm 창 측정

같은 코퍼스·같은 release ktm에서 false/true 프로필을 순차 실행했다. 파일명은 실제 kfind-names 엔진을 쓰는 격리 시험 파이프, 위계·본문은 실제 mmap·합성 SQLite 문단 표다. 설치된 서비스/SID 권한 검증을 대신하지 않는다. 빌드·시험이 없는 상태에서 한 번 실행했다. 실제 캡처를 이미지 도구로 열어 검색 칩·이름/위계 배지·발췌·한글 표시를 확인했다.

| 질의 | 기존 완료 GDI | 새 파일명 첫 GDI | 새 전체 완료 GDI | 입력부터 탐침 완료(기존 / 새) |
|---|---:|---:|---:|---:|
| 예산집행 | 63.979ms | 28.294ms | 54.832ms | 65.605 / 66.632ms |
| 2026; 공사 계약 | 32.958ms | 18.122ms | 44.112ms | 40.990 / 52.068ms |

GDI 계측 시작점은 기존 ktm과 같은 **검색 큐 등록 시각**이다. EDIT 입력 처리 전체를 포함한 외부 탐침 시각과 같지 않다. 마지막 열은 SetWindowText 직전부터 전체 결과·그림 및 해당 메시지 펌프가 끝날 때까지다. **입력부터 파일명 첫 표시까지의 엄밀한 외부 시각은 이번 탐침에서 분리하지 못했다.** 위 첫 GDI 수치만으로도 16ms를 초과하므로 목표 달성으로 판정하지 않는다. 적은 결과의 전체 그림은 약 11.15ms 느려졌으며 기본 활성화·승격 근거로 삼지 않는다.

| 숨긴 창 대기 2초 | 기존 | 새 |
|---|---:|---:|
| 개인 바이트(시작=끝) | 3,489,792B | 3,620,864B |
| 개인 작업 집합(시작=끝) | 2,834,432B | 2,854,912B |
| CPU 시간 증가 | 0.0ms | 0.0ms |

새 개인 작업 집합은 약 2.72MiB로 5MB 안이며, 기존 대비 증가 20,480B다. 개인 바이트 증가는 131,072B다. 60초 대기·대량 실색인 메모리·장시간 누수는 확인하지 않았다.

## 합성 결과 검증

seed `20261124`로 파일명이 있는 실제 합성 TXT 1,000개를 새 폴더에 만들고, kfind-core 색인·문서 표·원문 문단 표·kfind-names 색인을 함께 생성했다. 사용자 문서는 사용하지 않았다.

- `예산집행`: 손으로 계산 가능한 독립 기대값과 **80/80의 집합·순서·단 배정**이 일치했다. 이름 20, 위계 20, 본문 40이며 문서 중복 0이다. 상위 단 후보의 표시 상한 뒤에 숨은 문서가 하위 단에 다시 나타나지 않는 것도 확인했다.
- `2026; 공사 계약`: 서로 다른 문단의 두 묶음 교집합 **4/4**, 이름 1·위계 3, 한 묶음만 있는 제어 문서 2개 제외, 순서·중복 차이 0이다.
- 없는 낱말 및 세 번째 없는 묶음은 빈 집합이다. UI 탐침도 위 두 질의의 문서 순서를 독립 기대값과 다시 대조해 **2/2 일치**했다.
- 별도 단위 시험은 역순 도착·대소문자/슬래시/점 경로/UNC·ID 별칭·동명 다른 폴더·익명 행·단별/총상한·파일명 발행 뒤 본문 요청·부분 실패/전체 실패 완료·취소 전/후/단 사이·설정 기본값과 왕복·기간/확장자/인용 묶음을 확인했다.

예비 시험에서 새 코퍼스의 공백 AND를 붙여쓴 질의의 인접 일치와 같게 가정한 기대값, 원천 앞 8행의 발췌가 중복 제거 후에도 앞 8행일 거라는 기대값, core가 반환하는 묶음 앞 공백의 처리 차이가 드러났다. 코퍼스 질의를 실제 붙여쓴 검색 조건으로 명확히 하고, 발췌를 아직 읽지 않은 행은 기존 위치 근거를 확인하며, 새 응답 묶음의 표시 공백을 정규화했다. 확장자 세미콜론 문제는 어댑터를 고쳤다. 기존 시험이나 원천 엔진의 검색 기준은 수정하지 않았다.

## 필수 시험

변경한 소스·예제·시험은 모두 `ktm` 크레이트에 속한다. 다른 크레이트의 코드는 변경하지 않았다. 로컬 MinGW를 PATH 앞에 두고 카드 전용 CARGO_TARGET_DIR 환경변수 하나를 사용했다. 저장소 설정에 PC 전용 경로를 추가하지 않았다.

`cargo test --manifest-path ktm/Cargo.toml --no-fail-fast` — 종료 코드 0. 모든 test result 줄:

```text
test result: ok. 266 passed; 0 failed; 1 ignored; 0 measured; 0 filtered out; finished in 1.57s
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 8.01s
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

총 270 통과·기존 수동 벤치마크 1 제외. `cargo build --release --manifest-path ktm/Cargo.toml --bin ktm --example unified_bench`도 종료 코드 0이다. ktm SHA-256: `07994B92B630D361BD6616E125E63CF94AB2520C221D17F4FFFE934D5B4B01E8`.

전체 Python `python -m unittest discover -s tests`는 실행 중이다. 끝나면 실제 Ran/OK 또는 실패 줄과 원인을 이 절에 기록한다. 지정 Python 3.15 가상환경을 사용하며 별도 프로세스에서 한/글 COM 활성화를 차단했다. 이번 변경 대상이 아닌 klib는 SEMI2에서 검증한 기존 release 실행 파일을 KLIB_EXE로 지정했다(SHA-256 `6F122D935B8AD00C83FCE7ECD850E356136EBE11ACBCDE52E2DE652FE4FC215B`). 이번 브랜치에서 klib를 새로 빌드한 결과는 아니다.

Flutter 변경은 없으므로 flutter analyze·flutter test는 실행하지 않았다. XML 파싱을 새로 추가하지 않았고 본체 Python 파일의 CRLF는 변경하지 않았다.

## 확인하지 못한 것·후속 범위

- **16ms 첫 표시 목표 미달**, 입력 직전부터 첫 파일명 GDI까지의 엄밀한 외부 탐침은 미확인. 적은 결과의 전체 GDI 지연은 기존보다 증가했다. 기본값 false를 유지한다.
- 단별 200 후보 밖까지 포함한 **전역 단 배정·전수 집합·페이지 처리**는 미구현이다. 현재 계약은 반환 후보 창 안의 최고 단 우선이다. 이것을 전체 색인의 모든 문서에 대한 최고 단 판정으로 표현하지 않는다.
- 위계는 제목만의 검색이 아니라 기존 위계기반 본문검색이다. 같은 문서가 위계 후보 200건 안에 있으면 본문 단에 재등장하지 않는다.
- 기존 UI 요약의 “파일명 매치”는 이름이 있는 행을 세므로 선택된 이름 단 행 수와 다를 수 있다. 이번에는 각 행의 단 배지를 확인했다. 요약 집계 개선은 남았다.
- 현재 파이프 전용 본문 API는 전체 위계 순위 질의를 지원하지 않는다. 새 경로도 그 오류를 보존하고 다른 단을 계속 표시한다. 1글자·고급 AnyTerm/Exact와 모든 scope 조합의 실제 UI 전수 검증은 하지 않았다.
- 요청한 SEMI2 문서는 기준 브랜치에 없어 다른 로컬 작업 폴더에서 읽었다. 그 보고서의 새 `names_related`와 Python `related_groups` 옵션은 이 브랜치에 병합되지 않았다. 현재 분기의 기존 묶음 검색을 연결했으며 SEMI2 병합을 대신하지 않는다.
- 사용자 문서·한/글 COM·설치된 서비스·실제 드라이브 전체 색인·심볼릭 링크/하드링크 파일 ID·맥·앱 본화면 2단계는 확인하지 않았다. 존재하던 COM 잠금 파일은 건드리지 않았고 한/글 COM 시험을 실행하지 않았다.
- Everything·Docufinder 같은 PC 비교는 요청대로 실행하지 않고 설계에 측정 방법만 제안했다.
