# DOCK1 설계 — 하단 Dock 메뉴바와 단독 기능 창

작성일: 2026-11-18  
상태: 설계 문서. 코드·설정 변경 없음.

## 1. 범위와 결정

기존 사이드바를 대체하는 전면 개편이 아니라, 사용자가 **현재 사이드바**와 **하단 Dock** 표시 방식을 설정에서 선택하는 병행 구조를 제안한다. 기본값은 기존 사이드바다. 메뉴 아이콘을 누르면 해당 기능만 담은 창을 연다. Rust Win32 UI를 기본으로 하고, 복잡한 캔버스 편집기처럼 Rust 이식 비용과 동등성 위험이 큰 일부 화면만 Flutter 단독 창으로 유지한다.

이 문서는 Dock의 위치·입력·수명과 이식 우선순위를 정한다. 공용 Rust UI 부품, 엔진 전환 및 단계별 화면 이식의 공통 절차는 [RUSTALL1 계획](RUSTALL1_PLAN_2026-11-13.md)을 재사용한다. 아웃라이너 엔진 계약은 [OUTLINER 설계](OUTLINER_DESIGN_2026-11-18.md)를 참조한다. 기존 사이드바의 전체 화면 목록·기능 상세는 반복하지 않는다.

## 2. Dock 창

### 배치와 표시

- Dock은 앱 본창과 별개인 **플로팅 메뉴 창**이며, 기본 위치는 작업표시줄에 가장 가까운 가장자리의 안쪽이다. 작업표시줄이 아래면 `SPI_GETWORKAREA` 하단을 기준으로 띄우고, 위·좌·우에 있으면 그 가장자리에 붙인다. 자동 숨김 상태에서는 현재 작업 영역 가장자리 기준으로 놓는다.
- 세로 방향 가장자리에서는 Dock 막대의 긴 축을 화면 중앙에 두고 방향만 회전하거나 세로 레이아웃을 쓴다. 정확한 세로 모양은 DOCK2에서 화면 목업으로 결정한다.
- 기본 배치는 주 모니터다. 설정에서 주 모니터 또는 포인터가 있는 모니터를 고른다. 주 모니터 값은 Windows 디스플레이 설정의 기본 화면을 따른다.
- 작업 영역·작업표시줄·모니터 배치·DPI 변경 메시지(`WM_SETTINGCHANGE`, `WM_DISPLAYCHANGE`, `WM_DPICHANGED`)를 받으면 재배치하고 DPI별 크기를 다시 계산한다. 모니터를 잃거나 포인터 모니터를 결정할 수 없으면 주 모니터로 폴백한다.
- 사용자가 창을 드래그해 옮길 수 없게 한다. OS의 작업표시줄 자동 숨김과 Dock이 함께 켜졌을 때의 가장자리 충돌은 실제 Windows 조합 시험으로 확인한다.
- 둥근 반투명 막대에 메뉴 아이콘을 배치하고, 마우스 근접 확대는 인접 아이콘으로 퍼지는 짧은 보간 애니메이션으로 표현한다. 실행 중인 기능에는 아이콘 아래 작은 점을 표시한다. 마우스·키보드가 없는 접근성 모드에서는 확대 대신 포커스 테두리와 이름을 보여 준다.
- **항상 보임이 기본이다**(사용자 확정 2026-11-18: 작업표시줄 바로 위 정중앙에 '고정'). 자동 숨김은 설정에서 고르는 옵션이며 그때는 아래 규칙을 따른다. 자동 숨김 옵션: 포인터가 Dock 영역 또는 창으로 이동하면 나타나고, 바깥 클릭·비활성 후 짧은 지연 뒤 숨긴다.  지연 시간과 확대 최대 비율은 미측정이며 DOCK2 시안에서 정한다.
- 창은 `WS_EX_TOOLWINDOW`를 가진 최상위 레이어드 창으로 제안한다. `SetLayeredWindowAttributes`의 전체 알파와 GDI 이중 버퍼를 기본으로 삼고, 반투명 픽셀 가장자리 품질이 부족한 경우에만 `UpdateLayeredWindow`를 검토한다. Dock은 정지 화면과 소수 아이콘을 그리므로 기존 `kagent/src/popup.rs`의 GDI 방식이 저자원·적은 의존성에 맞는다. Direct2D는 이 화면에는 도입하지 않는다.
- Dock은 일반 창보다 위에 있지만 전체 화면 게임·프레젠테이션 등 foreground 창이 전체 화면이면 숨긴다. `WS_EX_TOPMOST`만 사용해 전체 화면 앱 위에 계속 노출하지 않는다. 전체 화면 판별과 복귀 시 재표시 시점은 Windows 실기 시험 항목이다.
- 아이콘은 앱에 포함된 소형 PNG 또는 기존 아이콘 자산을 DPI별 크기로 메모리 캐시한다. 새 벡터 렌더러는 만들지 않는다. 고대비 모드에서 시스템 색·테두리·이름 표시를 적용한다. 모든 아이콘은 UI Automation 이름/호출 패턴과 키보드 포커스를 제공한다.

### 상주 자원 목표

| 지표 | 설계 목표 | 기준 / 상태 |
|---|---:|---|
| 유휴 CPU | 평균 0%, 간헐적 메시지 처리 외 지속 소비 없음 | kagent의 과거 기록이 0%; Dock 실측 미확인 |
| 추가 메모리 | private working set 8 MiB 이하 | 신규 목표, 실측 미확인 |
| 입력 반응 | 이미 떠 있는 Dock 클릭부터 기능 창 표시 요청까지 100 ms 이내 | 목표, Flutter cold start는 별도 예산 |
| 애니메이션 | 포인터가 아이콘 사이 이동할 때만, 최대 120 ms | 목표, 미측정 |

정지 중 타이머나 프레임 루프를 돌리지 않는다. 마우스 이동 중에만 타이머를 켜고 완료 즉시 중단한다. 수치는 DOCK2에서 동일 PC·동일 측정 방식의 기준선과 함께 재평가한다.

**Flutter 유지 후보의 실행 조건:** 메뉴를 선택하면 Flutter 호스트를 `--standalone-tab=<tab-id>` 인자로 띄우고 해당 화면만 구성한다. 다이어그램·마인드맵은 기존 WebView2 편집기를 그 Flutter 창 안에서 연다. 표그림판과 붙임사진 편집은 첫 Rust 이식에서 제외해 Flutter 창으로 남기고, 동등성·자원 측정 후 개별 전환을 결정한다. 퀵 몽땅검색/파일명 변경/아웃라이너를 첫 2–3개 대상으로 권한다. 5번 사진 편집과 12·13번 개발자 화면은 메뉴 설정 노출 여부 및 정확한 탭 내용이 사용자 빌드에서 달라질 수 있어 구현 전에 화면 계약을 확인한다.

각 기능 창은 생성 시 해당 기능의 서비스/엔진만 연결하며, 닫힐 때 창 자원을 해제한다. 재클릭은 기존 창을 앞으로 가져오고, 다시 누르면 토글로 숨김을 허용한다. 편집 중 미저장 상태가 있으면 토글은 숨김만 수행하고 데이터 폐기를 유발하지 않는다. 프로세스 내부의 Rust 창은 단일 앱 프로세스의 창 레지스트리를 공유한다. Flutter 필수 화면은 이미 실행 중인 단독 Flutter 프로세스에 IPC로 탭 포커스를 요청하거나 없으면 새로 실행한다.

Flutter cold start와 메모리의 DOCK 전용 예산은 미확인이다. 독립 실행 시 전체 앱과 비교해 시작 시간·private working set을 따로 측정하고, 재사용 가능한 Flutter 호스트를 하나로 제한한다. Flutter 창은 닫으면 마지막 단독 창 종료 시 프로세스를 정리한다. 시작 실패는 Dock으로 오류를 돌려 선택한 기능의 Flutter 창을 한 번 재시도하고, 실패 시 사이드바 복귀 안내를 제공한다.

## 4. 메뉴 설정과 화면 모드 전환

### 설정 계약

설정에 **메뉴 표시 방식** 선택 항목을 둔다: `사이드바` 또는 `하단 Dock`. 기본값은 `사이드바`이며 기존 설치의 설정 키가 없을 때도 이 값으로 해석한다. 새 값은 기존 사용자 설정 JSON(현재 `hidden_tabs`와 같은 설정 전달·저장 경로)에 저장한다. 정확한 설정 파일 경로와 Rust/Dart 간 키 이름은 현재 지정 자료에서 미확인이다. 구현 전 설정 API의 실제 저장 위치를 추적한다.

`hidden_tabs`를 유일한 숨김 메뉴 원본으로 재사용한다. 기존 “쓸 메뉴 고르기” 설정 화면은 양쪽 모드에서 같은 집합을 읽고 쓴다. 문서편집(0)은 현재처럼 항상 표시한다. 현재 코드에서 12·13은 숨김 저장 정규화 대상에서 제외되므로, 개발자 모드 메뉴는 기존 표시 조건을 그대로 따른다. Dock 아이콘 순서는 기존 탭 번호 순서로 시작하며 사용자 정렬 기능은 이번 설계 범위 밖이다.

### 재시작 없는 전환

전환은 재시작 없이 가능하도록 제안한다. Flutter 앱이 현재 소유자이므로 다음 순서로 수행한다.

1. 사용자가 Dock을 고르면 `menu_display_mode=dock`을 저장한다.
2. Flutter가 Dock 상주 exe를 실행하고 준비 응답(명명된 파이프 JSON)을 기다린다. Dock이 준비되기 전에는 사이드바를 숨기지 않는다.
3. 준비 응답 성공 후 Flutter는 사이드바를 숨기고 Dock 표시를 확인한다.
4. 실행 실패, 시간 초과 또는 준비 응답 누락이면 저장값을 `sidebar`로 되돌리고 사이드바를 다시 표시한다. 사용자에게 폴백 이유를 보여 준다.
5. 사용자가 사이드바를 고르면 Flutter가 사이드바를 먼저 표시한 뒤 Dock에 숨김/종료를 요청하고 설정을 저장한다. Dock이 응답하지 않아도 사이드바는 유지한다.

앱 재시작 후 저장값이 `dock`인데 Dock exe가 없거나 기동에 실패하면 Flutter 사이드바를 즉시 표시하고 저장값을 `sidebar`로 복구한다. 기존 기본값은 바뀌지 않는다. 프로세스 비정상 종료 시 앱 시작 복구 경로도 동일하게 사이드바를 우선한다.

## 5. 창 간 상태·홈 이동

Rust 창과 Dock 사이의 제어 메시지는 기존 명명된 파이프 JSON 계약을 재사용한다(문자열 요청/응답, 시간 초과 처리). `show_menu`, `hide_menu`, `open_tab`, `focus_home`, `get_state` 같은 명령 이름은 제안이며 기존 구현 계약으로 확인된 것은 아니다. 설정, `hidden_tabs`, 실행 중 창 목록의 진실 원천은 앱 상태 서비스 한 곳으로 두고, 창은 변경 이벤트를 구독한다. 파일 경로나 문서 본문은 명령에 필요할 때만 전달하고 로그에 남기지 않는다.

[폐기 2026-11-19: 사용자 결정으로 홈 버튼 전체를 철회했다. 이 절의 홈 버튼 내용은 더 이상 적용하지 않는다.] 모든 메뉴 기능 화면 왼쪽 위에 홈 버튼을 둔다. 기존 Flutter 화면에는 `WorkspaceTabScope.goHome` 경로가 있지만 모든 단독 화면의 현재 배치가 같은지는 미확인이다. Dock 단독 실행에서도 동작을 명시적으로 맞춘다.

- **Rust 네이티브 창:** 왼쪽 상단 제목줄/화면 툴바 안에 집 모양 아이콘과 “홈” UIA 이름을 둔다. 클릭·Enter는 이미 열린 앱 첫 화면 창을 전면화한다. 창이 없으면 메인 Flutter 호스트를 기본 홈 화면으로 실행한다. Dock 자체를 홈 화면으로 오인하지 않도록 한다.
- **Flutter 단독 창:** 콘텐츠 상단 왼쪽에 기존 테마와 맞는 집 아이콘 단추를 둔다. 호출은 `focus_home` IPC다. 홈 화면이 있으면 앞으로 가져오고, 없으면 기본 Flutter 앱 인자로 새로 띄운다. Flutter 창은 해당 기능만 보이도록 유지하며 홈 클릭 시 기능 창을 닫을지 유지할지는 설정/미저장 상태 계약으로 구현 카드에서 확정한다. 기본 제안은 기능 창을 유지하고 홈 창을 앞으로 가져오는 것이다.

창 재사용/토글과 포커스 반환은 모드에 관계없이 같은 동작으로 맞춘다. 홈 프로세스가 비정상 종료됐을 때의 재시작 횟수 제한은 미확인으로, DOCK2에서 장애 복구 정책을 정한다.

## 6. 상주 프로세스와 기존 Rust 도구

Dock exe는 트레이·독 창·창 라우팅만 담당하는 작은 Rust Win32 프로세스로 둔다. 앱 설정의 “로그인 시 시작” 옵션을 재사용하고, 사용자가 Dock 모드를 선택했을 때만 로그인 자동 시작을 활성화한다. 현재 앱의 자동 시작 저장 위치/등록 방식은 이번 조사 범위에서 미확인이다. Windows 시작 앱/Run 키 등 실제 사용 중인 기존 경로를 먼저 확인해 중복 등록하지 않는다.

단일 인스턴스는 이름 있는 뮤텍스로 보장한다. 두 번째 실행은 새 Dock을 띄우지 않고 기존 프로세스에 활성화·설정 갱신 명령을 전달한다. 예외 종료는 다음 실행에서 상태를 다시 읽어 복구한다. 재시작 루프는 두 번 연속 실패 시 멈추고 사이드바 폴백을 유지한다. 업데이트 시 실행 중 exe를 덮어쓰지 말고 부모 런처/업데이트 도우미가 새 버전을 검증한 뒤 프로세스를 교체한다. Dock 업데이트 경로와 서명 체계는 미확인이다.

기존 `kagent`, `ktm`, `kvf`는 Dock에 합치지 않고 별도 실행 파일·프로세스로 유지한다.

- `kagent/src/popup.rs`는 Dock의 GDI·Win32 상호작용 기준으로 삼되, 클립보드 저장소와 기능 수명은 독립시킨다.
- `ktm/src`는 Rust 검색 기능과 자체 창이 있으므로 7번 몽땅검색 아이콘이 기존 ktm 창을 호출/전면화하는 연동을 우선 조사한다. 코어를 재사용하고 UI를 합치는지는 중복 상태·의존성 검토 뒤 정한다.
- `kvf/`의 트레이와 가상 폴더 창은 기존 사용자 경로를 보존한다. Dock 메뉴 항목에 중복 노출할 필요가 있는지는 현재 탭 인벤토리에서 확정되지 않아 미확인이다.

분리 근거는 각 exe가 이미 상주/단독 실행 수명과 트레이/창 동작을 가질 수 있고, Dock 장애가 클립보드·가상 폴더의 기존 동작까지 중단시키지 않게 하기 위해서다. 실제 시작·단축키·트레이 등록 지점은 소스 전수 조사를 하지 않았으므로 구체적인 핫키 목록과 재사용 설정 키는 미확인이다. 통합 카드 전에 각 앱의 시작·종료·단축키·트레이 명령을 코드로 추적한다.

## 7. 단계별 구현 및 검증 계획

### DOCK2 — 골격과 설정 전환

- 창 위치 산출, 다중 모니터/DPI/작업 영역 변경 대응, 레이어드 GDI 창, 자동 숨김·항상 표시, 확대 포인터 상태, UIA 이름, 단일 인스턴스·JSON 파이프를 만든다.
- 앱 설정에 사이드바/Dock 모드와 기존 `hidden_tabs` 공유를 연결한다. 준비 응답 기반 전환 및 자동 폴백을 구현한다.
- 시험: `ktm/src/view_dump.rs` 방식의 순수 레이아웃 덤프/골든 검사로 모니터·방향·DPI별 사각형과 메뉴 배치를 비교한다. 실제 GUI 시험은 작업표시줄 아래/위/좌/우, 자동 숨김, 100–200% DPI, 1·2 모니터에서 수행한다. 이번 설계 작업에서는 실행 시험하지 않는다.
- 자원 측정 스크립트는 Dock PID의 CPU 시간 delta와 private working set을 60초 유휴 및 100회 hover/click에서 기록한다. 수집 주기 1초, 창이 숨겨진 상태도 별도로 잰다. 결과에 Windows 빌드·모니터·DPI를 함께 저장한다.

### DOCK3 — 첫 기능 창 2–3개

- 권장 첫 대상: 몽땅검색(ktm 재사용), 파일명 일괄변경, 아웃라이너(OUTLINER2 완료 후). 실제 화면 계약/서비스 준비 상태가 다르면 문서뷰 또는 표템플릿으로 교체한다.
- 창별 단독 실행, 재클릭 포커스/토글, 상태 보존, 기존 결과와 비교를 만든다.
- 시험: 기존 엔진 결과 동일성, 창 생성·재사용·닫기 수명, UI 레이아웃 덤프 및 골든, 메뉴 키보드/UIA 검사, 20회 연속 열기·닫기. COM 기능은 필요한 경우에만 전용 COM 잠금을 준수하는 시험 카드에서 다룬다.
- 자원 측정: Dock 단독 유휴, Dock+Rust 창 1개, 창 닫은 뒤, 기존 Flutter 전체 앱과 각각 비교한다. 첫 표시 시간은 Dock 클릭부터 첫 유효 프레임까지 30회 중앙값/P95, private working set은 프로세스별·총합을 기록한다.

### DOCK4 — 나머지 기능 및 Flutter 예외

- 작은 목록·설정·검색 화면부터 Rust로 옮긴다. 각 화면은 RUSTALL1의 화면 동등성 검증·필요 시 GDI/Direct2D 선택 기준을 따른다.
- 다이어그램·마인드맵·표그림판·붙임사진 편집은 Flutter/WebView2 단독 창 후보로 남겨 창 수명·시작 지연·엔진 메모리를 별도 측정한다.
- 시험: 메뉴별 기존 기능과 입력·저장 결과 대조, 앱 재시작 전후 모드 보존, exe 누락·기동 실패·파이프 시간 초과 폴백, 전체 화면 진입/복귀, 다중 모니터 분리·재결합. Flutter 창이 없는 상태에서 Rust 기능만 실행될 때 상주 메모리 목표 충족을 확인한다.
- 되돌리기: `menu_display_mode=sidebar` 설정 하나로 기존 Flutter 사이드바 경로를 즉시 복구한다. Dock exe 제거/오류 시에도 이 값을 자동 선택하며, Rust/Flutter 화면 전환은 기능별 설정 플래그로 단계적으로 되돌릴 수 있게 한다. 기존 사이드바는 모든 Dock 단계의 복구 경로로 유지한다.
