# KC1 공용 검색 엔진 kfind-core — 본구현 1단계 (2026-11-12)

작업: `feature/instant-search`, 크레이트 `kfind/core/`(이름 `kfind-core`, 라이브러리). IS-S1 시제품 B(`kfind/engine-bench`, fst + roaring)를 앱이 쓸 수 있는 라이브러리로 옮겼다. **앱 연결(Python·Flutter·서비스·klib)은 하지 않았다.** 시제품 크레이트는 그대로 두었다(비교 기준).
원자료: [JSON](KC1_KFIND_CORE_RAW_2026-11-12.json). 표기: **확인** = 이번에 시험·측정으로 본 것, **미확인** = 보지 않은 것.

## 1. 비교형(정규화) 규칙 — 규칙 버전 1

Rust `kfind_core::fold`와 Python 기준 구현 `kfind/core/tools/fold_ref.py`가 글자 단위로 같아야 한다.

1. **NFC** 정규화(조합형 첫가끝 자모 → 완성형. 호환 자모 `ㅇㅖㅅ`은 합치지 않는다).
2. **casefold**(Python `str.casefold`: `ß→ss`, `ς→σ`, 전각 영문 소문자화 등).
3. **글자·숫자만 남김**(Python `str.isalnum`). 공백·문장부호·기호·결합 기호는 빠진다 → "예산 집행"과 "예산집행"이 같은 비교형(Q5).
4. 낱말 구분 공백 = 유니코드 White_Space 25자(Rust `char::is_whitespace`). Python `str.split()`은 U+001C~001F도 공백으로 보아 쓰지 않는다.
5. 검색 낱말은 비교형 2글자 이상만(Q8). 짧아서 뺀 낱말은 결과의 `dropped`로 알려 준다. 같은 낱말은 한 번만.

두 언어의 유니코드 표가 달라 생기는 차이를 없애려고 2·3은 Rust 표준 라이브러리(`to_lowercase`·`is_alphanumeric`)를 쓰지 않고 **Python 3.14(유니코드 16.0.0)에서 뽑은 고정표** `src/fold_table.rs`(남기는 글자 구간 770개, casefold 1,500여 항목)를 쓴다. 예: `Ⓐ`는 Rust `is_alphanumeric`으로는 글자지만 Python `isalnum`으로는 아니다 → 고정표에 따라 뺀다. NFC는 `unicode-normalization 0.1.26`(Unicode-3.0, 사용자 승인).

- 규칙을 바꾸면 `FOLD_RULE_VERSION`(Python `fold_ref.py`와 Rust 고정표 양쪽)을 올린다. 색인 파일 머리글에 규칙 버전이 들어 있어 다른 버전의 색인은 `Error::RuleVersion`으로 열기를 거부하고, 호출하는 쪽이 `Writer::create`로 비우고 다시 색인한다(자동 재색인의 엔진 쪽 절반. 앱 쪽 연결은 다음 단계).
- 다른 유니코드 판의 Python에서는 16.0 뒤에 새로 배정된 글자만 달라질 수 있다(시험은 그 경우 생성 파일 비교만 건너뛴다).
- 시험 표: `kfind/core/tests/data/fold_cases.tsv` 32줄(완성형·조합형·호환 자모·결합 문자·ß·시그마·전각·원 문자·날짜·개조식 기호 등). Rust `tests/fold_cases.rs`와 Python `tests/test_kfind_core_rules.py`가 같은 표를 읽는다.
- 다시 만들기: `python -X utf8 kfind/core/tools/gen_fold_table.py`(`--check`는 비교만).

## 2. 질의 규칙

1. 검색어를 공백으로 낱말로 나누고 비교형으로 바꾼다(1절).
2. **문장 일치**(Q3): 한 문장의 비교형에 모든 낱말이 들어 있으면 일치. 순서 무관.
3. **붙여 쓴 검색어 넓게 찾기**(사용자 결정): 4글자 이상 낱말 `w`가 조각 `p1…pk`로 나뉘면, `w`가 그대로 들어 있거나 **모든 조각이 같은 문장에** 있으면 그 낱말은 일치.
4. **붙어 있는 일치**: 모든 낱말이 나누지 않은 그대로 들어 있는 문장. 비교형은 공백을 지우므로 "예산 집행 계획"도 "예산집행"의 붙어 있는 일치다(이웃한 낱말). "예산 편성과 집행"은 넓은 일치일 뿐이다.
5. **문서 순위**(Q4 + 붙어 있는 일치 우선): ① 붙어 있는 일치 문장이 하나라도 있는 문서 ② 일치 문장 중 가장 높은 위계(순위 값이 작은 것) ③ 일치 문장 수 ④ 날짜 최신 ⑤ 문서 ID 오름차순.
6. 상위 N건(기본 20)은 문서 전체를 쌓았다가 고르지 않고 모으는 동안 앞선 N건만 쥔다. 전체 개수·일치 문장 수는 함께 돌려준다.

### 붙여 쓴 검색어 나누기: 색인 낱말로 가장 길게 vs 2글자씩 (실측 후 결정)

- **색인 낱말(기본, `SplitMode::DictLongest`)**: 색인의 살아 있는 문장에 어절로 나온 낱말(비교형 2글자 이상)만 조각이 될 수 있다. 앞에서부터 가장 긴 낱말을 고르고 끝까지 안 나뉘면 더 짧은 낱말로 물러난다. 조각은 낱말 전체보다 짧아야 한다. 고른 조각이 또 색인 낱말들로 나뉘면 더 나눈다("예산집행계획" → "예산집행"+"계획" → "예산"+"집행"+"계획"). 끝까지 나뉘지 않으면 나누지 않는다.
- **2글자씩(`SplitMode::Bigram`)**: 앞에서부터 2글자씩, 홀수면 마지막이 3글자.

| 비교(확인) | 색인 낱말 | 2글자씩 |
|---|---|---|
| 합성 3만 문서 "예산집행" 일치 문장/문서 | 182,784 / 29,959(붙어 있는 일치 문서 1,964) | 같음 |
| 같은 질의 상위 20 p50 / p95 | 4.08 / 5.38ms | 3.70 / 7.15ms |
| 합성 3만 문서 "예산집행계획" 일치 문장/문서 | 65,608 / 26,829(붙어 있는 일치 4) | 같음 |
| 같은 질의 상위 20 p50 / p95 | 2.69 / 3.48ms | 2.44 / 3.58ms |
| 대조 표 54개 검색어 중 나눈 검색어 수 | 20 | 30 |
| 낱말이 아닌 것을 나눔 | 없음 | `budget`→`bu+dg+et`, `2026`→`20+26`, `프로그램`→`프로+그램`, `가나다라`→`가나+다라` |
| 조사가 붙은 검색어 "시설을관리" | `시설을+관리` 4문장 | `시설+을관리` 5문장(뜻 없는 조각 "을관리"로 한 문장 더) |
| 입력 중간 상태 "예산집행계" | 나누지 않음(28문장) | `예산+집행계` 30문장 |

**결정: 색인 낱말로 가장 길게 나누기를 기본값으로 한다.** 합성 자료(낱말이 모두 2글자)에서는 결과 수가 같고 지연 차이는 측정 흔들림 안이다. 차이는 낱말 길이가 섞인 대조 표에서 난다: 2글자씩은 낱말이 아닌 조각을 만들어 영문·숫자·3글자 낱말에서 뜻 없는 일치가 늘고, 입력 중간마다 결과가 흔들린다. 색인 낱말 방식은 사전 조회가 낱말당 수 µs(3만 문서 해석 2~6µs, 확인)라 속도 손해가 없다. `SearchOptions.split`로 세 방법(끔·색인 낱말·2글자)을 고를 수 있다.

바뀐 결과(사용자 결정에 따른 것): 시제품에서 3만 문서 "예산집행"은 2,031문장/1,964문서였고, 새 규칙에서는 182,784문장/29,959문서를 찾되 그 1,964문서가 앞에 온다. 지연은 0.3ms → 4ms대로 는다(띄어 쓴 "예산 집행" 질의 3.5ms와 같은 수준).

## 3. 색인 형식 — 형식 버전 1

폴더 하나 = 색인 하나.

| 파일 | 내용 | 바뀌는가 |
|---|---|---|
| `seg-<번호>.kfs` | 조각(세그먼트): 머리글(형식·규칙 버전, 문장·문서 수, 구역 표, 본문 해시) + 비트맵(POST) + 조각 사전(DICT, fst) + 문장 비교형(TEXT) + 문장→문서·문단·위계 표 + 문서 표(ID u64, 날짜 i64, 첫 문장, 문장 수) | **안 바뀜**. 새 내용은 항상 새 번호의 새 파일 |
| `MANIFEST.kfm` | 지금 유효한 조각 목록, 조각마다 "지운 문장" roaring 비트맵, 세대 번호, 전체 해시 | 커밋 때마다 **임시 파일 → fsync → rename**으로 교체 |
| `LOCK` | 쓰는 쪽 하나만 보장하는 잠금 파일 | — |

- 조각 사전 열쇠: 비교형 2·3글자 조각의 UTF-8 → 문장 비트맵. `0x00 + 낱말` → 그 낱말이 어절로 나온 문장 비트맵(나누기용 낱말 사전. 삭제된 문서의 낱말은 "지운 문장"과 비교해 죽은 것으로 본다).
- 2·3글자 낱말은 비트맵 하나가 정답. 4글자 이상은 3글자 조각 비트맵 교집합(후보) 뒤 비교형 원문에서 `memchr::memmem`으로 확인(시제품과 같음).
- 안전 저장: 조각은 `seg-….kfs.tmp`에 다 쓰고 fsync한 뒤 제 이름으로 rename. 목록 파일도 같은 방식. 쓰다 죽어도 남는 것은 임시 파일이나 목록에 오르지 못한 조각뿐이고, 읽는 쪽은 무시하며 다음에 쓰는 쪽이 열 때 지운다(확인: `leftovers_of_an_interrupted_write…`).
- 읽기는 mmap. 매핑하는 파일(조각)은 바뀌지 않고, 교체되는 파일(목록)은 매핑하지 않고 통째로 읽는다 → **다른 프로세스가 읽는 중에 커밋·합치기가 일어나도 이미 연 세대는 그대로 유효**(확인: 처음 세대를 쥔 읽는 쪽이 증분 갱신·배경 합치기·정리 뒤에도 대조 표 162줄 전부 일치). 합쳐진 옛 조각 파일은 Windows에서 매핑 중이면 지워지지 않아 다음 커밋 때 다시 지운다.
- 읽는 쪽이 목록을 읽고 조각을 여는 사이 조각이 합쳐져 사라지면 새 목록으로 다시 시도한다(5회).
- 무결성: 머리글 해시와 구역 크기는 열 때 확인. 본문 전체 해시(FNV-1a 64)는 `Index::verify()`로 확인(파일 크기에 비례해 느려 열 때는 하지 않는다).

## 4. 증분 갱신과 합치기

쓰는 쪽(`Writer`) 상태 — 코드에 그대로 드러나 있다.

| 상태 | 뜻 | 읽는 쪽에 보이는가 |
|---|---|---|
| 대기(pending) | `add_document`·`delete_document`가 메모리에 반영 | 아니오 |
| 커밋(`commit`) | 대기 문서를 새 조각으로 쓰고 목록 교체, 세대 +1 | 예(`Index::reload`) |
| 합치는 중(`plan_merge` 뒤) | 목록 스냅숏으로 `MergeJob`을 만들어 다른 스레드에서 `run` — 쓰는 쪽은 그동안 추가·삭제·커밋 가능 | 아직 |
| 합치기 반영(`apply_merge`) | 합치는 동안 지워진 문장을 새 조각 번호로 옮겨 적고 커밋 | 예 |

- 문서 수정 = 옛 문장을 "지운 문장" 비트맵에 넣고 새 조각에 다시 넣기. 질의는 조각별 결과에서 지운 문장을 뺀다. 한 문서는 항상 조각 하나에만 살아 있다.
- 대기 문장이 20만(기본)을 넘으면 스스로 커밋한다(메모리 상한).
- 합치기는 비트맵을 다시 만들지 않고 문장 번호만 옮긴다(조각 사전들을 fst 합집합으로 훑음). 정책(`MergePolicy`): 조각 수 > 8이면 합치고, 지운 문장 비율 > 30%인 조각은 다시 쓴다. 합치기는 한 번에 하나.
- 불가능한 전이: 합치는 중 또 `plan_merge`(None), 다른 합치기의 결과로 `apply_merge`(`Error::Invalid`), 두 번째 `Writer`(`Error::Locked`).

## 5. 견고성

- **패닉 격리**: 공개 진입점(`Index::open`·`search`·`match_sentences`·`resolve`·`reload`·`verify`, `Writer::open`·`add_document`·`commit`·`apply_merge`, `MergeJob::run`)은 `kfind_core::guard`(= `catch_unwind`) 안에서 돌아 패닉이 `Error::Panic`으로 돌아온다. `Cargo.toml`에 `panic = "unwind"`를 명시. `add_document`는 비교형 만들기를 먼저 끝낸 뒤에만 상태를 바꿔, 한 문서의 패닉이 대기 상태를 망가뜨리지 않는다. FFI·파이프 계층은 같은 `guard`를 쓰면 된다.
- **질의 시간 한도·취소**: `SearchOptions.time_limit`(기본 2초)과 `cancel`(AtomicBool). 원문 확인 반복문은 1,024문장마다, 문서 모으기는 문서가 바뀔 때마다 확인한다. 넘으면 `Error::Timeout`/`Error::Cancelled`이고 색인 상태는 그대로다.
- **깨진 파일**: 잘림·쓰레기·한 바이트 바뀜·버전 다름·조각 없음이 모두 오류 값으로 돌아온다(프로세스가 죽지 않음).
- 이번 단계에 **없는 것**(견고성 요건 1·2의 프로세스 쪽): 문서 추출·색인을 별도 작업 프로세스로 돌리기, 메모리·건수 상한으로 프로세스 갈아 끼우기, 엔진 밖 감시 스레드의 강제 끊기. 엔진 안 시간 한도는 협조적 확인이라 엔진 코드가 확인 지점 없이 멈추는 경우는 못 끊는다 → 서비스 계층(다음 단계)에서 한다.

## 7. 성능(IS-S1과 같은 합성 자료, seed 7)

조건: Windows 11 10.0.26300, rustc 1.99.1(windows-gnu, release·LTO), 판정용 측정 1회, 반복 20회, nearest-rank p95. 시제품 B도 같은 때 같은 PC에서 다시 쟀다. **측정 중 다른 워커의 프로세스(`find`)가 CPU를 쓰고 있어 p95 흔들림이 크다.** 색인 위치: 시제품은 E:(이동식 디스크), 새 엔진은 C: 임시 폴더(질의는 mmap이라 디스크 영향이 거의 없다). 방법은 "끔"(시제품과 같은 규칙)으로 비교했다.

판정(있는 그대로):
- **상위 20**: 10개 중 대부분 ±0.4ms 안. "예산"(문장 40%)이 +1.4ms(5.05 → 6.41), 3,000문서 3·4낱말이 +0.1~0.3ms. 이 실행에서는 **회귀가 0이라고 말할 수 없다**. 같은 날 앞선 실행(최종 코드 직전)에서는 3만 문서 상위 20 p50이 예산 5.82/시제품 5.05, 예산을 1.67/1.72, 예산 집행 3.15/3.06, 3낱말 2.18/2.17로 나왔다 — 실행마다 ±15% 정도 흔들린다.
- **전체**: 문서가 많은 질의에서 0.7~1.5ms 느리다(예: 4낱말 2.29 → 3.82). 원인(추정): 문서마다 64비트 ID·날짜를 싣고 5단 순위로 정렬하며 문서별 결과 구조를 만든다(시제품은 문서 번호 u32·3단 순위). 시제품의 "전체"에는 문장 번호 목록 만들기가 들어 있어 하는 일이 같지는 않다.
- 계획 §3 목표(백엔드): `top` 50ms, `complete` 150ms(3,000문서), 800ms(3만 문서) — 모든 질의가 14ms 안으로 **달성**.
- 조각 6개(합치기 전) 상태도 조각 1개와 같은 수준이다.
- 질의 프로세스 최대 개인 메모리 1.2MB(3,000문서) / 5.0MB(3만 문서), 색인 열기 0.6ms.

속도를 맞추려고 한 일(실패한 시도 포함): 처음 구현은 문서별 모으기에서 문장마다 문서 표를 확인해 3만 문서 "예산" 상위 20이 11.9ms였다(시제품 5.7ms). ① 한 문서의 문장이 이어져 있다는 점을 써서 문서가 바뀔 때만 문서 표를 읽기(7.8ms) ② 표를 날것 조각으로 한 번만 꺼내기(7.2ms) ③ 일치 수·위계를 지역 변수에 모으기(6.1ms) ④ 상위 N건만 쥐는 수집기 + 붙어 있는 일치를 나란히 훑기(5.8ms) ⑤ 미리보기 문장을 비트맵 구간 훑기로. 네 단계 모두 결과는 대조 표와 같다.

## 9. 공개 API 요약

```rust
let mut w = Writer::open(dir, WriterOptions::default())?;          // 쓰는 쪽은 하나

w.commit()?;                                                        // 세대 +1
if let Some(job) = w.plan_merge(&MergePolicy::default()) {          // 배경 합치기
    let out = std::thread::spawn(move || job.run()).join().unwrap()?;
    w.apply_merge(out)?;
}
let mut index = Index::open(dir)?;                                  // 읽는 쪽은 여럿
let r = index.search("예산집행 계획", &SearchOptions::default())?;   // 상위 20, 붙어 있는 일치 우선

```
문서 ID(u64)·날짜(i64)·문단 번호·위계 순위(u8, 작을수록 높음)는 호출하는 쪽이 정한다. 문장 나누기는 엔진 밖(계획 S5 `sentence.rs`)이다.

## 10. 남은 문제·확인 못 한 것

- **속도**: 7절대로 문서가 많은 질의의 "전체"가 시제품보다 0.7~1.5ms 느리고, "예산" 상위 20이 이 실행에서 +1.4ms였다. 조용한 PC에서 다시 재야 회귀 여부를 확정할 수 있다. 줄일 여지: 순위 열쇠를 한 값으로 묶기, 위계별 비트맵 분리로 상위 20을 일찍 끝내기.
- **합성 자료 한계**(IS-S1과 같음): 낱말 24개·조각 약 8천 개·문단 = 문장·위계와 날짜가 모두 같다. 위계·날짜 순위와 낱말 길이가 섞인 경우는 작은 대조 표(140문서)로만 확인했다. 실제 문서(조각 수십만)에서의 지연·낱말 사전 크기·나누기 품질은 **미확인**.
- 붙여 쓴 검색어 나누기는 색인 낱말에 달려 있다: "예산"이 어절로 한 번도 안 나오고 "예산을"만 있으면 "예산집행"은 나뉘지 않는다(붙어 있는 일치만). 실제 문서에서 얼마나 생기는지 미확인.
- 디스크: 비교형 원문 사본을 줄이는 일(IS-S1의 숙제)은 하지 않았다. 3만 문서 316MB.
- 합치기 정책은 단순하다(조각 수·삭제 비율). 큰 색인에서 전체 다시 쓰기 5.7초/120만 문장 — 크기별 단계 합치기는 하지 않았다.
- 문서 1개 커밋 193ms(계획의 "문서 하나 갱신 50ms"는 한 번의 측정으로는 미달, 100개 묶음은 49ms). fsync 비용이 대부분으로 보이나(추정) 나눠 재지 않았다.
- 낱말 비트맵 캐시·앞 결과 좁히기(IS-QCACHE), 거르개(`ext:`·`path:`·날짜), `"구문"`, `-제외`, 위계 경로 붙이기, 다중 스레드 질의, 입력 흉내 측정은 이번 범위가 아니라 하지 않았다.
- 견고성 요건 1·2의 프로세스 격리·감시 스레드는 서비스 계층 몫으로 남겼다(5절).
- 다른 프로세스가 읽는 중 교체는 같은 프로세스의 스레드·별도 `Index` 인스턴스로 시험했다. **실제로 프로세스 둘을 띄운 시험은 하지 않았다**(파일 공유·mmap 동작은 프로세스 경계와 무관하게 같은 OS 호출이지만 미확인으로 둔다).
- 전원이 꺼지는 수준의 내구성(rename 뒤 폴더 항목 flush)은 Windows에서 따로 확인하지 않았다.
- clippy는 이 도구 모음에 설치되어 있지 않아 돌리지 못했다. 빌드 경고는 0.
- `HANDOVER.md`에는 이 크레이트를 적지 않았다(다른 워커와 겹칠 수 있어 총괄 병합 때 한 줄 추가 필요).
