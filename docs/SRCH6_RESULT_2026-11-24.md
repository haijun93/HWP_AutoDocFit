# SRCH6 결과 — warm 지연·순위 개선과 맥 빌드 가능성

검증 진행 중인 중간 기록이다. 최종 시험 결과를 뒤에 보완한다.

- 기준: `feature/SRCH5`의 `3f65771d`, 작업: `feature/SRCH6`. 처음 작업 폴더가 가리키던 다른 커밋은 미커밋 변경이 없는 것을 확인한 뒤 지정 기준으로 맞췄다.
- Windows x64·Python 3.15.2·로컬 MinGW release. 합성 생성 시드 `20261124`. 한/글 COM·사용자 문서·GitLab·푸시는 사용하지 않았다.
- 기본 `sqlite` 동작과 Python API 구현은 변경하지 않았다. Rust 선택 모드의 `search-content`에만 새 선택·순위 정책을 적용했다. 공용 자료함 `search`/`search_box`와 `hierarchy::search::aggregate` 정책은 유지했다. 스키마는 v5 그대로다.

## 지연 원인과 변경

SRCH5는 reader와 writer를 이미 재사용했다. 병목은 최종 응답 20건을 만들기 전에 400개 문서의 저장 필드·breadcrumb·일치 위치·snippet을 전부 복원하는 데 있었다. 1천 문서 `행정`에서 후보 8,000문단 중 400문서·4,605위치를 복원했다. 5천 문서에서는 FAST 경로 사전을 매 질의마다 다시 문자열로 푸는 집계 비용도 컸다. JSONL 직렬화와 Python 변환은 주된 병목이 아니었다.

변경한 흐름은 후보 검색 → FAST 문서 집계 → 발생 수 순위 → roots/날짜/페이지 선택 → 선택 문서만 복원 → JSONL → Python 변환이다. 문서 단위 AND의 교차 집합 단계에서는 경로만 읽고 본문·위치를 복원하지 않는다. 반환 문서의 후보 내 일치 위치를 임의로 잘라 속도를 맞추지 않았다.

경로 사전 캐시는 최대 16,384개, 저장 문단 캐시는 최대 4,096개이며 reader 세대가 바뀌면 비운다. 저장 필드는 세그먼트/문단 주소, 경로는 세그먼트/사전 번호를 키로 한다. 문서 AND의 단어별 경로 집합도 최대 16개(집합당 기존 상한 5,000파일) 재사용한다. 이 집합은 reader 세대 또는 동의어 그룹이 바뀌면 무효화한다. 스냅샷이 바뀌면 같은 주소를 재사용할 수 없게 했고 갱신·삭제·재시작·동의어 변경 회귀 시험을 추가했다. roots·날짜 선택은 요청마다 수행하며 완성된 검색 응답을 캐시하지 않는다. 색인 뒤에는 집합 캐시가 다시 차므로 그 첫 요청은 warm 캐시 적중 수치와 다르다.

`profile:true` 요청에만 `_profile` 진단 필드를 더한다. 일반 응답에는 없다. Tantivy 단계는 파싱·동의어 준비·FAST 열 열기까지 포함하며, 저장/위치 단계는 저장 필드·breadcrumb·snippet을 포함한다. 세부 breadcrumb·snippet·stored 시간은 그 단계의 부분집합이다. 직렬화 시간은 같은 응답을 한 번 직렬화한 표본이며, Python 변환은 클라이언트 전체 시간에서 `_request` 시간을 뺀 값이다. 따라서 단계별 중앙값을 합산해 전체 중앙값으로 해석하면 안 된다.

다음은 같은 합성 파일·같은 v5 인덱스를 두 실행 파일로 읽은 진단 계측(각 warm 7회 중앙값, ms)이다. 변경 전 실행 파일은 기준 소스에 계측만 추가해 보존했다. 변경 후 인덱스 재요청은 지문 일치로 생략됐다.

|---|---:|---:|---:|---:|---:|---:|
| 1천 `행정` | 2.73→2.25 | 12.00→1.50 | 111.57→3.61 | 0.65→0.39 | 0.36→0.25 | 140.36→12.48 |
| 1천 AND | 2.37→2.26 | 10.41→1.60 | 77.17→3.27 | 0.51→0.36 | 0.62→0.32 | 97.97→12.52 |
| 5천 `행정` | 6.55→6.69 | 29.75→3.82 | 32.99→1.73 | 0.21→0.32 | 0.24→0.28 | 76.24→20.09 |
| 5천 phrase | 15.36→12.39 | 32.83→2.78 | 40.25→1.63 | 0.23→0.19 | 0.88→0.36 | 95.28→21.63 |

1천 `행정`은 20문서·336위치만 복원하고, 5천은 20문서·126위치를 복원했다. 변경 후 warm stored 읽기는 캐시 적중이며, 5천 `행정`의 stored 조회 0.031ms·breadcrumb 0.023ms·snippet 1.360ms·새 발생 수 정렬 1.169ms였다. 반환 문서가 순위 개선으로 달라져 위치 수 차이 전부를 순수 최적화 효과로 볼 수는 없다. 과복원 제거와 경로 재사용이 큰 비용 감소를 설명한다.

원시 표본: [변경 전 프로파일](SRCH6_PROFILE_BEFORE_2026-11-24.json), [변경 후 프로파일](SRCH6_PROFILE_AFTER_2026-11-24.json). 진단을 켠 계측과 아래 진단을 끈 정식 벤치 수치를 구분한다.

추가로 실제 `hierarchy=True` 문서 AND도 확인했다. 위치 복원만 줄인 첫 구현은 5단어에서 47~75ms로 목표를 넘었다. 단어별 교차 집합을 매번 다시 검색하는 비용이 원인이어서 집합 캐시를 추가했다. 추가 최적화·검증은 20분 안에 마쳤다. 최종 warm 7회 중앙값은 다음과 같다.

| 규모 | 2단어: SRCH5→최종(ms) | 5단어: SRCH5→복원/경로 캐시만→최종(ms) |
|---|---:|---:|
| 1천 | 334.00→25.48 | 820.68→47.47→16.81 |
| 5천 | 602.00→19.67 | 1573.42→75.30→20.95 |

[위계 모드 전후 원시 표본](SRCH6_HIERARCHY_PROFILE_2026-11-24.json)의 `before`, `after`, `after_paths_cache`는 각각 SRCH5·첫 최적화·최종 구현이다. 이 진단도 합성 조건 한 번이며 더 긴 질의·캐시 용량 초과·색인 직후의 지연을 보장하는 값은 아니다.

## 동일 조건 성능 재측정

`scripts/search_bench.py --sizes 1000 5000 --time-limit-minutes 20`을 backend별로 순차 실행했다. SRCH5와 생성기·시드·파일당 문단 분포·배치 250건·응답 limit 20·warm 5회·변경 1%를 맞췄다. 질의 순서는 짧은 키워드 / 긴 AND / AND / phrase이며 기존 벤치처럼 `hierarchy=False`다. SRCH5 행은 과거 기록이고 SRCH6 행끼리는 이번 같은 조건 재측정이다. 다른 시험·빌드와 성능 측정을 겹치지 않았다. 각 조건 한 번 측정했으며 cold는 질의 유형별 첫 요청으로 OS cold-cache를 뜻하지 않는다.

이번 Rust 벤치의 8개 warm 중앙값은 모두 30ms 이하이며, SRCH5 대비 짧은 키워드는 1천 약 7.3배·5천 약 4.2배 빨라졌다. 5천 phrase는 SQLite 19.946ms보다 Rust 27.594ms가 느리므로 모든 유형에서 SQLite보다 빠르다는 뜻은 아니다. 첫 짧은 질의는 25.967/50.253ms여서 warm 성과를 첫 질의에도 적용하지 않는다. 5천 초기 색인은 과거 38.301→45.499초로 변동해 색인 개선을 주장하지 않는다. 이번 코드는 쓰기 경로·저장 스키마를 바꾸지 않았다. 문서 AND 집합 캐시를 추가한 뒤 최종 Rust 벤치·집합 대조·품질 평가를 재실행했으며 표와 JSON은 그 최종 결과다. 초기 구현의 중간 벤치 수치는 채택하지 않았다.

이번 같은 조건에서 5천 Rust 초기 색인은 SQLite의 10.4%, 디스크는 14.3%였다. SQLite adapter에는 `changed`가 없으므로 원시 JSON의 미변경 재색인 수 10/50은 실제 재색인 수로 해석할 수 없다. 표에는 구분 미지원으로 표시했다. 두 backend의 생성·시험 자료는 같은 NTFS 볼륨에서 만들었고 과거 SRCH5의 순간 시스템 부하까지 재현한 비교는 아니다. 이 RSS는 기존 벤치(`hierarchy=False`)의 값이며 문서 AND 집합 캐시를 최대 용량까지 채운 메모리는 따로 측정하지 않았다.

색인 중 요청은 여전히 JSONL 단일 프로세스·Python 요청 잠금 때문에 writer commit/reload를 기다린다. warm 지연 개선이 검색/색인 동시 실행 분리를 해결한 것은 아니다. 원시 결과는 [Rust 벤치](SRCH6_BENCH_RUST_2026-11-24.json), [SQLite 벤치](SRCH6_BENCH_SQLITE_2026-11-24.json)에 기록한다.

## 순위 원인·평가

기존 집계는 위계 수준 → 일치 문단 수 → 최신 수정 시각 → BM25 순이었다. 본문 한 문단에 질의어가 여러 번 있어도 문단 수는 1이고, BM25는 길이를 정규화한다. 같은 위계·문단 수에서는 뒤에 만든 단발성 distractor가 고밀도 정답보다 먼저 나올 수 있었다. 제목 boost 2.5만으로 이 집계 순서를 뒤집을 수 없었다.

Rust 선택 모드만 위계 수준 → 가중 발생 수 → BM25 → 최신 → 경로 순으로 정렬한다. 발생 수는 stored 본문을 전부 읽지 않고 postings의 term_freq에서 모은다. 수준 1 제목 8·수준 2 제목 4·그 밖 위계 2·본문 1의 가중치를 둔다. 두 글자 한글 질의에서는 실제 토큰 발생 수, 긴 어절에서는 bigram 발생 수 근사값이다. 문서 AND의 교집합은 모든 단어로 구하되 대표 순위/위치는 기존처럼 첫 단어의 후보를 사용한다. 이 한계도 실제 사용자 평가에서 확인해야 한다.

평가를 기존 3질의/120문서에서 **18질의/405문서**로 확장했다. 기존 3개를 보존하고 제목 일치·본문 밀도·위계 깊이·AND·phrase를 각 3개 추가했다. 질의마다 정답 4개와 단발성 참고 문서, AND 단일어·phrase 비연속 음성 대조군을 뒀다. 파일 이름에는 질의어를 넣지 않았다. 정답 내부 순서 일치율은 기대 정답 4개의 6쌍 중 순서를 지킨 비율이다. Recall@10은 상위 10개에 든 정답 비율, MRR은 첫 정답 순위의 역수다.

| 유형(각 3질의) | 질의 | SQLite Recall@10 / MRR / 순서 | Rust 전 Recall@10 / MRR / 순서 | Rust 후 Recall@10 / MRR / 순서 |
|---|---|---|---|---|
| 기존 제목·밀도 | 행정 절차, 예산 편성, 안전 점검 | 1 / 1 / 1 | 1 / 1 / 0.3889 | 1 / 1 / 1 |
| 제목 | 주민 상담, 도시 녹화, 복지 연계 | 1 / 1 / 1 | 1 / 1 / 0.6111 | 1 / 1 / 1 |
| 밀도 | 교통 조사, 문화 행사, 체육 시설 | 0.75 / 1 / 1 | 0 / 0.0732 / 0.6667 | 0.75 / 1 / 1 |
| 위계 깊이 | 재난 대응, 청년 창업, 보육 서비스 | 1 / 1 / 1 | 1 / 1 / 1 | 1 / 1 / 1 |
| AND | 공원 정비, 도로 보수, 환경 보전 | 0.75 / 1 / 1 | 0 / 0.0714 / 0.5555 | 0.75 / 1 / 1 |
| phrase | "디지털 역량", "자원 순환", "건강 증진" | 0.75 / 1 / 1 | 0 / 0.0816 / 0.7778 | 0.75 / 1 / 1 |
| 전체 평균(18질의) | — | **0.875 / 1 / 1** | **0.500 / 0.5377 / 0.6667** | **0.875 / 1 / 1** |

밀도·AND·phrase의 4번째 정답은 참고 문서와 발생 수가 같아 두 backend 모두 상위 10 밖에 놓이는 경우다. 순서 1.00은 정답을 모두 상위 10에 넣었다는 뜻이 아니다. 세부 순위와 breadcrumb는 [변경 전 품질](SRCH6_QUALITY_BEFORE_2026-11-24.json), [변경 후 품질](SRCH6_QUALITY_AFTER_2026-11-24.json)에 있다.

합성 정답은 사람이 실제 업무 질의로 판정한 정답이 아니다. 반복 횟수·표제·위계 깊이를 생성기가 정하고 같은 신호를 개선했으므로 이 결과는 실제 문서 검색 품질의 독립 검증이 될 수 없다. 신호가 같은 참고 자료의 우열도 사람이 판정하지 않았다.

## 결과 집합

확장 품질 코퍼스의 18개 질의는 변경 전/후 모두 SQLite와 전체 결과 집합이 일치했다. 순위 변경 후 1천 문서의 기존 4유형도 자료함을 100문서씩 나눠 API 상한 안에서 전체 수집했다.

| 유형 | SQLite / Rust 문서 수 | 전체 집합 일치 | 상위 20 겹침 |
|---|---:|---:|---:|
| 키워드 | 1000 / 1000 | 100% | 1/20 |
| AND | 994 / 994 | 100% | 1/20 |
| phrase | 1000 / 1000 | 100% | 0/20 |
| 문서 위계 AND | 1000 / 1000 | 100% | 1/20 |

[집합 대조 원시 결과](SRCH6_MATCH_2026-11-24.json). 전체 집합 일치와 상위 20 순위 일치는 다른 지표다. 무작위 코퍼스에서는 임의 순위가 달라 상위 20 겹침이 여전히 낮다. 기존 최대 10,000 후보 문단·문서 AND 단어별 5,000파일 상한을 넘는 데이터의 완전한 결과 집합은 이번 검증으로 보장하지 않는다. 5천 전체 집합 재대조는 확인 못 함(5천 성능만 측정).

## 맥·시험·판정

Windows 전용 의존과 경로·잠금·서비스 결합을 [맥 가능성 설계](SRCH6_MAC_FEASIBILITY_2026-11-24.md)에 목록화했다. `windows-sys`만 `[target.'cfg(windows)'.dependencies]`로 옮겼고 Windows release는 성공했다. 실제 맥 빌드 성공 여부는 **확인 못 함**이며 후속 맥 카드가 필요하다.

- Windows release 성공. 첫 개선 빌드의 `Postings` trait import 위치 오류는 고친 뒤 빌드했다. 기존 deprecated·dead-code 경고는 남았다.
- 관련 Python 시험 최종 26개 OK. 새 회귀 시험은 제목/밀도 순위·페이지/roots·profile 응답·캐시 갱신/삭제/재시작·동의어 변경·실시간 날짜 필터·문단 분산 AND/phrase·평가 유형/지표를 다룬다.
- 전체 cargo 시험 실행 중, Python 전체 시험 대기. 최종 결과를 여기에 보완한다.

**기본 backend 승격은 보류한다.** warm·합성 품질의 목표는 개선했으나, 실제 사용자 판정 정답·실제 한글/OCR·페이지/표 좌표·설치본·폐쇄망·맥 빌드는 이 카드에서 확인하지 않았다. 큰 코퍼스의 후보 상한과 검색/색인 직렬화도 남아 있다. SQLite 기본값을 유지하며 공개 배포·태그·푸시는 하지 않는다.
