# RUSTSIDE1 계획 — 사이드바 + 메뉴별 창 (2026-11-26)

사용자 채택: "앱 실행시 사이드 바만 런청된다. 사이드메뉴 중 하나를 선택하면 해당 메뉴의 실행화면ui가 분리되어 창이 열린다."
이번 단계의 결과와 실측은 `docs/RUSTSIDE1_RESULT_2026-11-26.md`. 이 문서는 **다음에 할 일**이다. 아래 설계는 아직 구현하지 않았다.

## 0. 지금 구조

- `sidebar.exe`(`dock` 크레이트): Python 없이 뜨는 메뉴 창. 누르면 메뉴마다 창 1개.
- Rust 창이 있는 메뉴: 파일명 일괄변경·몽땅검색·문서뷰·사진뷰·파일변환·아웃라이너·설정.
- 나머지: 기존 앱을 `--screen N`으로 메뉴 하나만 담아 연다(창마다 Python+Tk+WebView2 프로세스 1개).

상태(메뉴별, `dock/src/sidebar.rs`):

| 상태 | 전이 |
|---|---|
| closed | 누름 → launching. 밖에서 연 창을 발견 → open |
| launching | 창 발견 → open. 비정상 종료·90초 초과 → closed(안내). **다시 눌러도 새로 실행하지 않음** |
| open | 창 사라짐 → closed. 누름 → 앞으로(새로 실행하지 않음) |

`--state-file`로 이 상태를 JSON으로 읽을 수 있다.

## 1. 화면별 Rust 전환 순서

기준: (가) 한/글 COM이 필요 없는가, (나) Rust 코어가 이미 있는가, (다) 앱 창이 뜨는 시간을 줄이는 효과.

| 순서 | 메뉴 | 현재 | 할 일 |
|---|---|---|---|
| 1 | 이미 Rust 창이 있는 7개 | Rust 창(앱에서는 `*_ui` 설정 기본값이 `flutter`인 것이 있음) | **기존 화면과 기능 대조**(이번에 하지 않음). 차이가 0이 될 때까지 기본 전환 금지 |
| 2 | 가상 폴더, 업무자료함 | Flutter + `klib`(Rust) | 화면만 Win32로. 업무자료함의 문서 추출 경로 확인 |
| 3 | PDF 편집 | Flutter + `pdf_edit_core` | 쪽 미리보기·편집 화면 Win32. 코어 범위 확인 필요 |
| 4 | 표템플릿 | Flutter + Python | 목록·미리보기는 Rust, 한/글로 복사하는 경로만 남김 |
| 5 | 표그림판, 붙임사진 편집, 마인드맵 | Flutter | 그리기 캔버스. 가장 큰 화면 작업이라 뒤에 둔다 |
| 6 | 문서편집 | Flutter + Tk 엔진 + COM | 마지막. 화면을 옮겨도 COM 필수부는 화면 없는 Python 뒷단으로 남는다 |
| 예외 | 다이어그램 | 웹 편집기 | 팀 규칙(필수 예외)대로 웹 화면 유지 |
| 보류 | 검색 벤치마크 | 개발자 전용 | 필요할 때 |

한 메뉴를 옮길 때마다: 결과 차이 0 확인 → `native(id)` 표에 한 줄 추가 → `--screen` 대신 열기 유지(파일이 없으면 앱 화면).

## 2. 창 간 파일 전달 설계

현재: 전용 창에서 "PDF 편집으로 보내기" 같은 다른 화면 전달은 **막고 안내**한다.

설계:

1. 전달 요청은 한 형식: `{"menu": N, "paths": [...]}`. 보내는 창은 "그 메뉴 열기 + 파일"만 말하고 대상의 상태를 알지 않는다.
2. 받는 쪽 대기함: `%LOCALAPPDATA%/HWP_AutoDocFit/open_requests/screen-N/*.json`. 쓰는 방식은 `docfit_app/instance_files.py`의 임시 파일→이름 바꾸기(원자적)를 그대로 쓴다.
3. 보내는 순서: 요청 파일을 먼저 쓴다 → 창이 있으면 앞으로 → 없으면 `--screen N` 실행. 받는 창은 시작할 때와 주기적으로 자기 대기함만 비운다. 창이 늦게 떠도 요청이 남는다.
4. Rust 창: 같은 대기함을 읽는 방식으로 통일한다. 변환 창이 이미 쓰는 파이프(`convert_open`)는 옮길 때까지 유지.
5. 검증: 받는 쪽에서 파일 존재·형식·개수 상한을 다시 확인한다. 경로만 전달하고 원본은 고치지 않는다. 오래된 요청(예: 10분)은 버린다.
6. 탐색기 "열기": 지금은 보통 앱이 받는다. 기본 전환 때 `--screen 0`의 대기함으로 보낸다.

불가능해야 할 전이: 같은 요청을 두 번 처리(처리 전 파일 이름 바꾸기로 선점), 대상 창이 없는데 보냈다고 알리기.

## 3. 종료·설치 안전

지금 한 것:
- 사이드바를 닫아도 열린 창은 독립 프로세스라 남는다.
- 각 창의 닫기 확인은 기존 그대로.
- 설치 중 `sidebar.exe`를 종료한다(`installer/setup.iss`).
- 전용 창은 업데이트 확인·알림을 하지 않는다.
- 전용 창끼리 작업 상태 파일·설정 저장·한/글 PID 등록이 겹치지 않게 했다.

남은 일:
- 설치 프로그램(`CloseApplications=force`)과 `taskkill`은 여러 작업 창의 **저장 안 한 편집을 잃게 할 수 있다**. 설치 전에 열린 작업 창을 알리고, 창마다 닫기 요청(확인 창 포함)을 먼저 보내야 한다.
- 전용 창의 설정 화면에서 수동 업데이트를 누르는 경로를 막거나 "모든 창 닫기" 절차를 붙인다.
- 두 창에서 동시에 한/글 작업을 할 때의 실제 동작(COM 잠금, 보안 모듈 등록) 시험. 필요하면 작업 단위 전역 잠금.
- 설정을 한 창에서 바꿔도 이미 열린 다른 창은 다시 켜야 반영한다. 설정 파일 변경 감시 추가.
- 전용 창 비정상 종료 시 그 메뉴의 한/글 프로세스 정리 범위 확인.

## 4. 상주 작업의 주인

보통 앱이 시작할 때 하던 일을 전용 창은 하지 않는다(여러 창이 겹쳐 하면 충돌). 사이드바만 쓰면 **아무도 하지 않는다**:
몽땅클립보드 앱 서비스 파이프(엑셀 표 '목표 결과'·사진 편집 열기), kagent·kvf·ktm 갱신, 업데이트 확인, 탐색기 우클릭 메뉴 갱신, 변환 파이프, 검색 색인 사전 준비.
기본 전환 전에 화면 없는 작은 주인 하나(사이드바가 시작할 때 한 번 부르는 점검 + 파이프는 해당 창)로 옮긴다.

## 5. 기본 전환 조건 (모두 만족 + 사용자 승인)

1. Rust 창 7개의 기능 대조에서 차이 0, 또는 사용자가 차이를 승인.
2. 설치본에서 실행→사이드바 조작 가능 시간이 탐색기 새 창과 같거나 빠름(같은 도구 `scripts/measure_sidebar.py`).
3. 설치본에서 앱 화면 메뉴의 창·**내용 표시** 시간이 기존 방식보다 느리지 않음. 느리면 미리 띄워 두기 등을 검토. 창 여러 개의 메모리 실측.
4. 2절(파일 전달)·3절(설치 안전)·4절(상주 작업) 완료.
5. 문서편집 창에서 빠진 새 문서·작업 로그·사용 방법·몽땅클립보드 진입점 마련.
6. 설정 화면에 실행 방식(`launch_mode`)과 자동 숨김 선택 추가.
7. 최대화한 창의 왼쪽을 사이드바가 가리는 문제 결정(자동 숨김 기본값 또는 작업 영역 예약).
8. 설치·업데이트·제거 시험, 다중 모니터·125%/150% 화면 확인, 키보드·화면 읽기 확인.

되돌리기: `launch_mode`를 지우거나 `--full-app`으로 실행하면 기존 앱이다.
