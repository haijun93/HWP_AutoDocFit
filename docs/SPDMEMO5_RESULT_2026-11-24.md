# SPDMEMO5 결과 — 본문 자간 문자별 서식 조회

## 판정

코드 변경은 보류했다. 한/글 2020의 `HAction.GetDefault('CharShape', HCharShape.HSet)`는 여러 글자를 선택해도 혼합 자간을 알리는 값이나 상태를 주지 않고, 선택 첫 글자의 서식값을 반환했다. 대표 글자 한 번만 읽으면 혼합 서식의 원래 값을 잃으므로 기본 재사용 경로로 쓸 수 없다.

사용자가 정한 불일치 0 안전 관문을 통과할 근거가 없어 `DOCFIT_SPACING_FMT=verify`/`reuse` 구현 및 전체 ALLQA 검증은 진행하지 않았다. 동일한 이유로 새 방식의 전후 속도·ALLQA 동일성 수치는 없다. 확인하지 않은 항목을 통과로 간주하지 않았다.

## 확인한 조건

- 기준 커밋: `811ebd2d` (`feature/SPDMEMO4` 후속); 작업 브랜치 `feature/SPDMEMO5`.
- 저장소 코드에서 사용자 원본은 열지 않았다. SPDMEMO4 보고서형 합성 TXT 입력의 생성 결과 사본을 읽기 전용으로 열었다. 혼합 시험은 열려 있는 COM 문서의 메모리에서 한 글자만 바꾸고 저장하지 않았다.
- 모든 COM 실행은 `C:/HWP_AUTODOCFIT/.com-test.lock` 아래 순차 실행했다. 기준선 문서 실행은 13분 50초가량 걸렸고 20분 제한 내 완료했다.
- `단어모드_서식보관`은 본문 범위를 정한 뒤 위치를 한 글자씩 이동해 각 문자를 선택하고 자간 7개·장평 7개 슬롯을 읽는다. 실패 복원을 위한 문자별 값과 연속 run이 필요해 혼합 구간은 현행 경로를 유지해야 한다.
- 함수의 선택 범위 값에 혼합 표시가 있는지는 확인하지 못했다. 아래 COM 실험으로는 혼합 표시가 없음을 확인했다.

## 혼합 서식 COM 확인

보고서형 결과 사본 첫 문단 22자 범위에서 첫 글자 기준 슬롯은 자간 `0`, 장평 `100`이었다. 같은 문단의 한 글자에 메모리상 자간 `-10`을 적용하고, 22자 범위를 선택해 같은 `GetDefault`를 호출했다. 범위 조회는 자간 `0`을 반환했고 문자별 조회 결과에는 `-10`과 `0`이 함께 있었다. 즉 범위 조회만으로 혼합 여부를 탐지할 수 없으며 대표값 재사용은 안전하지 않다. 시험은 원본 파일에 저장하지 않았다.

문서 XML의 `charPr` run 정보가 이 런타임 문서와 모든 입력 형식에서 신뢰 가능한지, COM 범위 조회 외에 혼합을 알려 주는 별도 API가 있는지는 조사하지 않았다.

## 기준선 실측

보고서형 합성 TXT 사본을 `spacing` 모드로 계측했다.

| 항목 | 기준선 |
|---|---:|
| 전체 시간 | 830.8초 |
| 본문 자간·단어 분리 조정 | 810.8초 / COM 346,910회 |
| 전체 COM | 350,413회 / 790.9초 |
| 본문 자간 단계의 Python 시간 | 35.8초 |

이번에는 새 경로가 구현되지 않아 전후 비교 및 5% 개선 기준 판정은 할 수 없다. 위 기준선은 SPDMEMO4의 보고서형 입력 측정과 실행 조건이 조금 다르므로 그 보고서의 수치와 직접 증감률을 계산하지 않았다.

## 시험 및 남은 확인

- `tests.test_spacing_memo`: 7개 통과.
- `DOCFIT_SPACING_FMT=verify`로 ALLQA 6건 및 보고서형 입력을 실행하지 않았다. 대표값의 혼합 오독이 확인되어 불일치 0 전제조건을 만족시킬 수 없기 때문이다.
- ALLQA 6건의 SPDMEMO5 전후 `allqa_compare` 동일성은 미측정이다.
- 추후 재개하려면 입력 형식 전반에서 문자 run의 동일 서식을 안전하게 판정하는 신뢰 가능한 문서 XML/COM 근거를 먼저 확보해야 한다. 근거가 없다면 문자별 보관 경로를 유지한다.
