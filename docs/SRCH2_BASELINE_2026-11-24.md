# SRCH2 SQLite 검색 기준선

측정일: 2026-11-24  
브랜치 기준: `feature/SRCH1B` 커밋 `7fe33d98`에서 시작한 `feature/SRCH2`  
측정 backend: `SqliteBackend` → 기존 `ContentSearchIndex`  
환경: Windows x64, Python 3.15.2, 재현 시드 `20261124`

## 측정 조건

`scripts/search_bench.py`를 한 번 실행했다. 임시 폴더에 `.txt` 합성 문서를 만들고, 문서마다 20~50개 한국어 합성 문단을 기록했다. 본문에는 장 번호, `1.`·`(1)`·`가.` 계층 번호와 `□`·`○`·`-`·`※` 항목 기호를 섞었다. 코퍼스 생성과 SQLite 초기 색인은 순차 실행했다. 이후 문서 1%를 바꿔 증분 색인하면서 동시에 SQLite 검색을 반복했다.

질의 지연의 `첫 질의`는 색인 직후 같은 프로세스에서 그 질의 종류를 처음 수행한 값이다. OS 파일 캐시를 비우거나 프로세스를 재시작하지 않았으므로 디스크까지 차가운 cold-start 측정은 아니다. `반복 중앙값`은 같은 질의를 이어서 5회 실행한 중앙값이다. 최대 RSS는 측정 프로세스의 Windows working set peak이고, 인덱스 크기는 SQLite DB 및 부속 파일의 합계다.

## 목표 수치

SRCH1 설계 문서에는 초기 색인, 검색 지연, 메모리, 디스크 크기의 수치 합격 목표가 정해져 있지 않다. 따라서 아래 값은 성능 목표가 아니라 비교용 기준선이다. 코퍼스 크기는 1천·1만 건을 기준으로 제안했으며, 10만 건은 이번 측정 범위에서 제외했다.

| 항목 | 목표 수치 | 실제 측정값 |
|---|---:|---:|
| 합성 코퍼스 | 1천·1만 문서, 문서당 20~50문단 | 1천 건 완료. 1만 건은 아래 측정 제한으로 미완료. |
| 초기 색인 시간 | 정해진 목표 없음 | 1천 건: **53.345초**. 1만 건: **확인 못 함**(18분 총 제한으로 색인 중 중단). |
| 증분 색인 | 문서 1% 변경, 시간 목표 없음 | 1천 건 중 10건: **5.377초**. 1만 건: **확인 못 함**. |
| 짧은 질의 `행정` | 지연 목표 없음 | 첫 질의 **917.062ms**, 반복 중앙값 **19.559ms** (5회). |
| 긴 질의 `행정 정책 문서 안전 지원` | 지연 목표 없음 | 첫 질의 **803.532ms**, 반복 중앙값 **9.446ms** (5회). |
| AND 질의 `행정 정책` | 지연 목표 없음 | 첫 질의 **846.652ms**, 반복 중앙값 **15.644ms** (5회). |
| phrase 질의 `"행정 절차 지원"` | 지연 목표 없음 | 첫 질의 **729.973ms**, 반복 중앙값 **14.958ms** (5회). |
| 색인 중 검색 | 지연 목표 없음 | 1천 건 코퍼스에서 1% 증분 색인과 동시 검색 **8회**. 중앙값 **965.111ms**, 최댓값 **1,239.072ms**, 오류 0건. |
| 최대 RSS | 목표 없음 | 1천 건 완료 측정 중 **88,199,168 bytes (84.1 MiB)**. 1만 건 부분 초기 색인 과정은 **114,057,216 bytes (108.8 MiB)**이며 완료 코퍼스 값이 아니다. |
| 인덱스 디스크 크기 | 목표 없음 | 1천 건 완료 후 **43,982,848 bytes (41.9 MiB)**. 1만 건: **확인 못 함**. |
| 코퍼스 생성 시간 | 목표 없음 | 1천 건 **3.022초**. 1만 건 부분 실행 **30.669초**. |

모든 검색 지연과 색인 수치는 이 한 번의 측정 실행에서 나온 값이다. 1만 건 구간은 총 18분 제한에 걸려 초기 색인 중단으로 끝났다. 종료 시 개별 완료 문서 수를 스크립트가 저장하지 않아, 1만 건 완료 기준의 초기 색인 시간·증분 색인·검색 지연·디스크 크기는 산출하지 않았다. 부분 색인 중 관측한 RSS만 참고값으로 남겼다. 실행 제한은 30분 이내였으며, 10만 건은 시작하지 않았다.

## 설정 비교와 시험

Rust `settings-core.exe`는 이 PC의 `docfit_config/target/debug/settings-core.exe`에 없어 Python↔Rust 설정 비교는 **못 함**(기존 통합 시험에서 skip)이다. 이를 대신해 `settings_schema.ALL_DEFAULTS`와 `docs/settings_defaults.json`의 전체 값 일치 시험을 추가했다. 설정 키는 `sqlite`·`rust`·`shadow_compare`를 정규화하며, 알 수 없는 값은 `sqlite`로 처리한다. Rust 모드 요청은 backend 미연결 사유를 로그에 남기고 SQLite 검색 adapter를 사용한다.

## SRCH3 제안: Rust backend IPC 연결

1. Rust 프로세스 IPC의 요청·응답 형식, 오류 코드, 프로세스 생명주기와 취소 규칙을 정하고 Python 서비스 계약의 `index_file`, `remove_file`, `search`, `status`, `cancel`에 대응시킨다.
2. `sqlite` 모드를 기준 동작으로 고정하고 `rust` 모드에서 합성 코퍼스의 검색 결과 구조·순서·본문 위치를 비교한다. 동등성 시험은 키워드, AND, phrase, 위계, 날짜·경로 필터와 빈 결과를 포함한다.
3. `shadow_compare`에서 양 backend 결과 차이를 기록하되 사용자 응답은 SQLite 결과로 유지한다. timeout, 프로세스 종료, 재시작, 색인 취소 때도 SQLite fallback과 기존 API 응답을 보장한다.
4. SRCH2 기준선과 같은 시드·코퍼스·질의·측정 방법으로 한 번씩 비교해 지연·RSS·디스크 변화와 실패 사례를 함께 기록한 뒤, Rust 기본 모드 전환 여부를 별도로 결정한다.
