# QMSBUG1 — 퀵몽땅검색 "합의각서" 0건 (2026-11-28)

대상 보고: 2026-11-20, v2.2.82. 통합 검색(기간·형식 전체)에서 "0개 · 0.00초, 파일명 매치 0, 본문 매치 0, 검색 결과가 없습니다". 오류 문구 없음.

조사는 코드, 합성 색인, 임시 이름의 가짜 파이프로만 했다. 설치된 색인 서비스, 사용자 색인·설정·문서, 실행 중인 앱은 조회·변경하지 않았다. **사용자 PC에서 실제로 어느 경로였는지는 확인하지 못했다.**

## 1. 결론

1. **보고 화면과 맞는 결함(v2.2.82 코드로 확인)**: 작업 순서는 파일명 → 위계 → 본문이다. 파일명 검색이 실패해도(서비스 없음, 색인 `empty`/`building` 등) 창은 세 구간이 모두 실패하지 않으면 그 실패를 **0건 성공**으로 바꿔 상태에 넣었다. 본문 색인이 열리고 0건이면 "검색 결과가 없습니다"만 남는다. 파일명 검색은 돌지 않았는데 오류 문구가 없다.
2. **v2.2.84(`76088898`)에서도 남아 있었다**: 빈 결과 뒤에 온 실패는 보이게 됐지만, 실제 순서인 "파일명 실패가 먼저"에서는 뒤따른 성공이 `error = None`으로 오류를 지웠다. 기존 시험은 실패가 마지막에 오는 순서만 확인했다.
3. **"0.00초"는 검색이 안 돌았다는 증거가 아니다**: 요약 줄이 `timing`을 읽는데, 첫 그림 뒤 `timing.take()`로 비워서 다시 그리면 항상 0.00초였다.

가장 그럴듯한 상황은 "전체 드라이브 색인 서비스가 없고(2026-11-20 조사 PC에서는 미등록, `docs/INDEX_SERVICE_STATUS_2026-11-20.md`), 파일명 검색이 실패한 것이 조용한 0건으로 보였다"이다. 다만 보고 PC의 상태는 알 수 없으므로 추정이다.

## 2. '0건'이 될 수 있는 경로

| # | 경로 | 수정 전 | 조치 | 재현·검증 |
|---|---|---|---|---|
| 1 | 서비스 파이프 없음·연결 실패 + 본문 0건 | 조용한 0건 | 오류 유지, "검색을 완료하지 못했습니다" + 사유 | `zero_results`, `tm_state` |
| 2 | 이름 색인 `empty`(사용자 모드 kfind 포함)·`building`·`failed` | 조용한 0건. `empty`·`failed`도 "준비하는 중"이라 적음 | 위와 같고 상태별 문구 분리 | `zero_results` |
| 3 | 서비스가 아무것도 읽지 못하고 `ready`(항목 0, `last_error` 없음) | 서버가 정상 0건 응답 | 색인 만들기를 `failed`로 처리(옛 색인이 있으면 유지). 창도 `names_status` 항목 0이면 "파일명을 검색하지 못했습니다" | `names_pipe`(수정 전 실패 확인), `zero_results` |
| 4 | 사용자 모드 색인이 일부 폴더만 담음, 일부 드라이브 MFT 실패 | 범위 안내 없이 0건 | 0건일 때 `names_status`를 읽어 범위를 함께 표시 | `zero_results` |
| 5 | 일부 구간이 아직 안 끝남 | 먼저 온 0건이 "검색 결과가 없습니다" | "검색 중…" | `tm_state`, `zero_results` |
| 6 | 통합 검색(선택 기능, 기본 꺼짐)에서 일부 원천 실패 | 큰 안내는 "검색 결과가 없습니다", 사유는 상태줄만 | 목록 자리에 실패 표시 | `zero_results` |
| 7 | 같은 글자 입력·이미 켜진 칩 선택 | 대신할 검색 없이 진행 중 검색을 취소(취소 오류, 통합 경로는 "검색 중"에 멈춤) | 세대가 오를 때만 취소 | 세대가 안 오르는 것만 시험. 창의 취소 호출은 자동 시험 없음 |
| 8 | 설정의 제외 폴더·하위 폴더 미포함이 결과를 모두 거름 | 조용한 0건 | "설정 때문에 결과가 숨겨져 있습니다" | 안내 함수만 시험 |
| 9 | 결과 내 검색·형식 선택·파일명 제외·접힌 묶음 | 빈 목록 | "조건 때문에 결과가 숨겨져 있습니다" | 안내 함수만 시험 |
| 10 | 늦게 온 옛 세대 응답, 창 숨김 | 버려짐(정상) | 변경 없음 | 기존 시험 |
| 11 | 파이프 시간 초과·응답 끊김·동시 요청 상한 | 오류지만 1과 같이 지워질 수 있음 | 1의 수정에 포함 | 개별 재현 안 함 |
| 12 | 본문 색인 취소 | `Error::Cancelled`를 돌려주며 빈 성공이 아님 | 변경 없음 | 코드 확인 |

v2.2.84 이후 이미 해결돼 있던 것: 빈 성공 **뒤에** 온 실패를 오류로 바꾸는 것(`all_search_first_empty_part_does_not_hide_later_service_error`), 파이프 오류의 한글 문구, 색인 `unavailable` 응답을 빈 목록이 아니라 오류로 해석하는 것.

## 3. 보이는 문구

| 상황 | 목록 자리 제목 | 요약 줄 |
|---|---|---|
| 정상 검색, 없음 | 검색 결과가 없습니다(+ 파일명 색인 범위) | 0개 · n.nn초 |
| 진행 중 | 검색 중… | 검색 중… |
| 색인 만드는 중 | 파일명 색인을 준비하는 중입니다 | 검색 못함 |
| 서비스 없음·실패 | 검색을 완료하지 못했습니다(0건은 '파일이 없다'는 뜻이 아닙니다 + 사유) | 검색 못함 |
| 색인이 비어 있음 | 파일명을 검색하지 못했습니다 | 검색 못함 |
| 화면 조건·설정이 거름 | 조건/설정 때문에 결과가 숨겨져 있습니다 | 0개 |

일부 구간만 실패하고 다른 결과가 있으면 결과를 보여 주고 상태줄에 "파일명: …"처럼 사유를 남긴다.

## 4. 사용자 PC에서 확인하는 방법

모두 읽기 전용이다.

1. **창의 문구(이 수정이 든 버전)**: "합의각서"를 검색해 위 표의 제목과 설명을 그대로 적는다.
2. **구버전**: "0개 · 0.00초"는 판단 근거가 아니다. 색인 서비스 유무를 아래 3·4로 확인한다.
3. **서비스 등록**: PowerShell `Get-Service HwpAutoDocFit.Index`. "찾을 수 없습니다"면 전체 드라이브 파일명 색인이 없다.
4. **파이프**: `Get-ChildItem \\.\pipe\ | Where-Object Name -eq 'HwpAutoDocFit.Index'`. 파이프가 있어도 3이 없으면 앱이 띄운 사용자 모드 `kfind`이며 드라이브 전체를 담지 않는다.
5. **창 상태 파일**: `%LOCALAPPDATA%\HwpAutoDocFit\ktm\status.json`의 `state`·`results`·`error`. 마지막 상태 전환 때의 값이다(검색어는 없음). 통합 검색(선택 기능)의 구간 오류는 이 파일에 늦게 반영될 수 있다.
6. **서비스 로그**: `%ProgramData%\HwpAutoDocFit\logs\kfind-service.log`(서비스가 설치된 경우). 서비스 오류만 남고, 이름 색인의 `last_error`는 이 파일이 아니라 `names_status` 응답에만 있어 0건 화면 설명에 표시된다.

## 5. 변경 파일

- `ktm/src/tm_state.rs`: 앞 구간 실패 유지, 실패 구간 수(`failed_parts`)·`parts_pending()`.
- `ktm/src/notice.rs`(새 파일): 0건 안내와 요약 줄, `names_status` 해석.
- `ktm/src/window.rs`: 안내 연결, 소요 시간 보존, 취소 시점, 설정으로 모두 걸러진 경우 표시, 파일명 0건 때 `names_status` 조회(제한 2초, 검색 작업 스레드), 구간 오류에 이름 붙임.
- `ktm/src/window_capture.rs`: 새 화면 필드 초기화.
- `ktm/src/backend.rs`: `empty`·`failed` 문구 분리. `ktm/src/lib.rs`: 모듈 등록.
- `crates/kfind/src/names.rs`: 아무것도 읽지 못한 색인 만들기를 실패 처리.
- 시험: `ktm/tests/zero_results.rs`(새 파일), `tm_state.rs`, `crates/kfind/tests/names_pipe.rs`. 기존 시험은 바꾸지 않았다.
- **`ktm/src/backend/unified.rs`는 바꾸지 않았다**(UNIFIED2와 충돌 없음). 다만 `window.rs`의 `Reply::Unified` 처리와 작업 스레드의 통합 검색 클로저에 몇 줄을 더했으므로 병합 때 확인이 필요하다.

## 7. 남은 문제

- 창을 실제로 띄운 화면 확인(문구 줄바꿈·테마·배율)은 하지 않았다. `window.rs`의 응답 처리 자체는 자동 시험이 없고, 시험은 같은 순서를 상태 함수에 넣어 확인한다.
- 보고 PC의 실제 원인 확인과, 그 PC에서 "합의각서"가 나오게 하는 것: 전체 드라이브 검색에는 색인 서비스 설치(관리자 승인)가 필요하다. 이번 수정은 서비스를 설치하거나 서비스 없는 대체 검색 경로를 만들지 않는다. 즉 **서비스가 없는 PC에서는 여전히 파일을 찾지 못하며, 이제 그렇다고 알려 줄 뿐이다.**
- 사용자 모드 `kfind`에 `names_build`를 보내는 앱 코드를 찾지 못했다. 이 경우 파일명 색인은 계속 `empty`다.
- 분리 검색 경로(기본값)의 파일명 질의에는 기간 칩이 적용되지 않고, 검색창에 직접 쓴 `after:`/`before:`는 파일명 낱말로 전달돼 0건이 될 수 있다. 통합 검색 경로는 처리한다. `UNIFIED2`와 겹쳐 고치지 않았다.
- 설정/통계 화면의 색인 상태 상시 표시(TODO의 진단 제안)는 하지 않았다.
- 버전 올림·릴리스 노트는 하지 않았다.
