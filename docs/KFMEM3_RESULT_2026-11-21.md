# KFMEM3 결과 — 실제 파일 이름 분포와 메모리 모델

## 측정 방법 및 범위

`kfind/names/examples/name_stats.rs`는 `C:\Windows`, `C:\Program Files`, `C:\Users` 바로 아래 프로필 디렉터리 트리를 읽기 전용으로 순회했다. 사용자 파일은 이름/메타데이터만 열거했고 파일 내용은 열지 않았다. 저장·출력한 것은 집계 숫자뿐이며, 경로·파일 이름 목록은 남기지 않았다. 재분석 가능한 표본 데이터는 저장하지 않았다.

제한은 60초, 최대 3,000,000개 디렉터리 항목이다. 47.06초에 1,442,679개 항목을 처리해 두 제한 전에 순회를 마쳤다. `errors=54`는 접근/열거 실패 건수이며 원인은 세분해 저장하지 않았다. 루트 및 권한 때문에 접근할 수 없던 하위 트리는 포함되지 않는다.

## 실측

명령:

```powershell
$env:PATH="$env:LOCALAPPDATA\DocFitTools\mingw64\bin;$env:PATH"
$env:CARGO_TARGET_DIR='<외부 빌드 캐시 경로>'
cargo run --release --manifest-path kfind/names/Cargo.toml --example name_stats
```

| 지표 | 결과 |
|---|---:|
| 항목 수 | 1,442,679 |
| 디렉터리 / 파일 | 209,554 / 1,233,125 |
| 열거 오류 | 54 |
| 이름 UTF-8 바이트 평균 / 중앙값 / p90 / 최대 | 30.119 / 21 / 50 / 167 B |
| 한글 코드포인트가 든 이름 비율 | 0.171% |
| 평균 폴더 깊이 (루트의 바로 아래 디렉터리를 깊이 1로 계산) | 6.320 |
| 폴더 / 파일 비율 | 0.169937 |
| 경과 / 제한 도달 | 47.06초 / 아니오 |

평균·분위수는 파일과 디렉터리 이름을 함께 집계한 값이다. 한글 비율은 한글 이름의 항목 비율이다(한글 글자 수 비율이 아니다). 경로별 분포, 접근 거부 위치 및 미열거 항목의 특성은 수집하지 않았다.

## 합성 모델과 서비스 수치 대조

`mem_probe` 기준 모델에서 원래 이름은 22.717 B, 접힘 이름은 21.250 B, 이름 이외 고정 필드는 39.000 B/항목이다. 여기서는 실제 이름 길이가 접힘본에도 동일하게 반영된다고 가정했다. Unicode 정규화/소문자화가 UTF-8 바이트 수를 바꾸는 효과는 이번 통계로 재지 않았다.

| 기준 | 이름 원본 | 접힘본 | 고정 필드 | 모델 합계 | 서비스 대비 |
|---|---:|---:|---:|---:|---:|
| 합성 `mem_probe` | 22.717 | 21.250 | 39.000 | 82.967 B/항목 | 약 104.0 B 낮음 |
| 실측 평균을 양쪽 이름에 대입 | 30.119 | 30.119* | 39.000 | 99.238 B/항목 | 약 87.8 B 낮음 |
| 서비스 보고값 | — | — | — | 약 187 B/항목 | 기준 |

*접힘본 길이는 실측하지 않아 원본과 같은 길이라고 가정했다. 서비스 기준은 선행 문서의 3,343,333개 항목, 힙 약 624 MB(약 187 B/항목)라는 보고값이다. `heap_bytes`와 서비스 힙의 계측 범위가 동일한지도 보장되지 않는다.

**판정: 이름이 합성보다 길다는 가설은 일부 차이를 설명하지만, 주원인으로 확인되지 않았다.** 실측 길이 대입으로 합성 모델보다 16.271 B/항목 증가하지만 서비스 수치와는 여전히 약 87.8 B/항목 차이가 남는다. 따라서 이름 길이만으로 약 187 B를 설명한다는 주장은 맞지 않는다. 남은 차이에는 번호 희소도·확장자/HashMap 용량과 모델 누락, allocator 여유 용량, 서비스 보고 힙과 모델의 범위 차이 등이 후보로 남지만 이번 측정으로 원인을 분리하지 못했다.

## 메모리 절감 후보 (설계 평가만, 구현 안 함)

3,343,333개 항목에 대한 환산은 실측 평균을 전체 서비스에 적용한 단순 추정이다. MB는 10^6 B 기준이다.

| 후보 | 실측 분포 기반 예상 절감 | 질의 속도 영향 추정 | 위험·미확인 |
|---|---:|---|---|
| 접힘본을 저장하지 않고 질의 시 계산 | 약 30.1 B/항목, 약 100.7 MB | 검색 중 후보 이름을 접거나 비교할 때 추가 CPU 비용. 후보 수·질의 종류별 지연은 측정 안 됨 | 정규화/대소문자 규칙의 일관성 및 정렬 키 재사용 여부를 확인해야 함. 이름 길이만 적용한 모델 추정 |
| ASCII이면 원본과 접힘본 바이트 공유 (`원본==접힘본` 비트) | 최대 약 30.1 B/항목(약 100.7 MB)이라는 상한만 산출 가능 | ASCII 이름은 별도 접힘 문자열 접근을 없앨 수 있음. 비ASCII 이름은 기존 비용 유지 | 실제 ASCII 이름 비율을 측정하지 않았다. 한글 포함 이름 비율 0.171%만으로 ASCII 비율을 알 수 없으므로 기대 절감은 확정 불가. 비트/분기 비용과 소유권 구조 검토 필요 |
| 폴더 이름 인터닝 | 이번 측정에서 절감량 산출 불가 | 동일 폴더명의 반복 조회/복사 비용이 줄 수 있으나 캐시 접근이 추가될 수 있음 | 폴더 이름 전용 길이 및 중복률을 세지 않았다. 고유 폴더명·수명·해시 테이블 오버헤드를 측정해야 함 |

## 미확인 사항

- 전체 드라이브 색인의 파일/폴더 이름 분포와 이번 디렉터리 표본의 일치 여부.
- 파일명만 분리한 길이 분포, ASCII 이름 비율, 폴더 이름 길이와 중복률.
- 접힘/정규화 이후 실제 UTF-8 바이트 길이 변화.
- 서비스 `heap_bytes`의 배열별 용량, 번호 분포 및 실제 할당자/HashMap 오버헤드.
- 각 절감 후보의 실제 메모리 회수량과 질의 p50/p95 영향.
