# SRCH5 결과 — Rust 몽땅검색엔진 5단계

- 기준 커밋: `1177bf13` (SRCH4), 작업 브랜치 `feature/SRCH5`, 구현 커밋 `a9e9cd00`, 검증 보강 커밋 `76cf16bd`
- 환경: Windows x64, Python 3.15.2, 로컬 MinGW release 빌드, 합성 코퍼스 시드 `20261124`. 한/글 COM과 사용자 문서는 사용하지 않았다.
- 기본 모드는 계속 SQLite이며 기존 기본 모드 API 응답은 변경하지 않았다. Rust opt-in 검색 응답만 위계·위치 정보를 확장했다.

## 구현

- Rust 검색 스키마를 v4에서 v5로 올렸다. 기존 인덱스는 버전 불일치 시 안전하게 재색인하는 경로로 처리한다.
- 색인 문단에 `node_id`, `parent_id`, `breadcrumb`, `level`, 페이지·문단·표/행 위치를 추가했다. Rust 응답에 breadcrumb 문자열과 배열, 문단 번호, 위치 객체를 실었다. 페이지를 추출할 수 없는 텍스트 형식은 페이지를 `null`로 둔다.
- 파일 SHA-256과 `extractor_version`을 저장한다. 문서 이름·박스 정보와 지문이 같으면 색인을 생략하며, 바뀐 파일만 재색인한다. 추출기 버전 변경도 재색인 조건이다.
- `shadow_compare` 로그에 전체 집합 일치, 상위 20 집합 일치, 상위 20 겹친 수를 남긴다.

## 순위 품질 평가

120개 합성 Markdown 문서에 질의별 정답 4개를 두고, 각 질의어가 제목에 있고 본문 밀도도 높은 정답 문서와 본문에만 있는 36개 distractor를 비교했다. 파일 이름에는 질의어를 넣지 않았다.

| 질의 | SQLite Recall@10 / MRR | Rust Recall@10 / MRR | 정답 4개 순서 일치율: SQLite / Rust |
|---|---:|---:|---:|
| 행정 절차 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 0.3333 |
| 예산 편성 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 0.5000 |
| 안전 점검 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 0.3333 |
| 평균 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 0.3889 |

두 backend 모두 정답 네 문서를 첫 네 자리에 반환했고 Recall@10·MRR에는 차이가 없었다. 합성 정답의 밀도 순서를 더 잘 보존한 것은 SQLite였다. 따라서 현재 표본은 Rust BM25·위계 가중치가 SQLite 발생 횟수 신호보다 순서 품질이 높다는 근거가 되지 않는다. Rust 순위 가중치를 더 조정하려면 실제 사용자가 판정한 질의·정답 평가가 필요하다. 이 결과는 세 개의 제한된 합성 질의만 다루며 실제 검색 품질을 대표하지 않는다.

## 성능 측정

SRCH2~4의 과거 기준과 SRCH5 측정을 나란히 놓았다. SRCH5 두 backend는 같은 합성 생성기·시드·질의를 사용했다. 1만 문서 SQLite는 SRCH4에서 20분을 넘겼으므로 요청에 따라 5천 문서로 대체했다. warm 질의는 `행정 / 행정 정책 문서 안전 지원 / 행정 정책 / phrase` 순서다. RSS와 디스크는 MiB로 환산했다.

| 측정 | 초기 색인 | 증분 변경 색인 | 미변경 재요청 | warm 질의 중앙값(ms) | 색인 중 질의 중앙값/최댓값(ms) | 최대 RSS | 디스크 |
|---|---:|---:|---:|---|---:|---:|---:|
| SRCH4 1천 SQLite | 49.591초 | 10개 6.314초 | 미측정 | 19.160 / 9.293 / 15.760 / 15.080 | 1003.871 / 1162.054 (8회) | 84.3 MiB | 41.9 MiB |
| SRCH4 1천 Rust | 3.827초 | 10개 2.935초 | 미측정 | 27.925 / 9.725 / 22.159 / 23.966 | 280.024 / 328.176 (12회) | 63.0 MiB | 4.50 MiB |

SRCH5에서 Rust는 미변경 50개를 재색인하지 않았다. SQLite adapter는 `changed` 응답을 제공하지 않아 미변경 문서 처리와 생략을 구분할 수 없다. 5천 문서 Rust의 초기 색인 시간은 SQLite의 약 8.8%, 인덱스 크기는 약 14.3%였다. 반면 Rust의 warm 질의는 이 조건에서 SQLite보다 느린 유형이 있어, 색인 성능만으로 기본 backend 승격을 결정할 수 없다. 측정은 각 조건 1회다.

## 시험 및 승격 판단

- Rust release 빌드 성공. Rust 검색 테스트 하네스 95개 실행 종료 코드 0; 라이브러리 단위 시험 19개 통과.
- 관련 Python 검색 시험 12개 통과. 전체 명령 `python -m unittest discover -s tests`: 3,597개 실행, 20개 skip, `OK` (종료 코드 0). Python 3.15.2로 실행했다. 종료 시 기존 테스트 샌드박스 SQLite 잠금으로 정리 `PermissionError` 경고가 출력됐으나 시험 결과는 성공이었다.
- 합성 corpus 품질 평가, SQLite 1천·5천 및 Rust 1천·5천 성능 벤치 완료.

**기본 backend 승격은 불가.** 순위 품질 근거가 세 개의 합성 질의에 한정되고 Rust의 정답 내부 순서가 SQLite보다 낮다. 실제 한글 문서, 스캔 PDF/OCR, 설치본 시험도 남아 있다. 기본 SQLite 동작과 API 응답을 유지한다.

## SRCH6 제안

1. 사용자 동의가 있는 실제 한글 문서에서 질의별 판정 정답과 Recall@10·MRR을 수집해 순위 가중치를 비교한다.
2. 스캔 PDF의 OCR 페이지·문단 좌표와 표 행 위치를 추출기별로 검증하고 색인/응답 필드의 결측 규칙을 확정한다.
3. 설치본에서 v4→v5 자동 재색인, 중단 후 복구, shadow fallback을 확인한다. SQLite 기본 모드 유지 상태에서 장기간 상위 20 일치 로그도 관찰한다.
