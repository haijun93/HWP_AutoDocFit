# RSXML3 결과 — hwpx_fmt 처리기 5종 추가: 별표 위첨자·붙임 글꼴·콜론 라벨·빈 줄 서식·강조 낱말 (2026-11-23)

범위: `별표위첨자_hwpx_처리`(`asterisk_superscript`), `붙임글꼴_hwpx_처리`(`attachment_font`), `콜론라벨_hwpx_처리`(`colon_label`), `빈줄서식_hwpx_처리`(`blank_lines`), `강조낱말_hwpx_처리`(`emphasis`)를 `hwpx_fmt` 에 옮기고 파이썬 처리기와 결과 XML 차이 0을 시험했다. 한/글 COM·사용자 문서는 쓰지 않았다(합성 HWPX + `tests/fixtures` 18건과 그 변형). 앱에는 연결하지 않았다(프로토타입).

## 결론

- **다섯 처리기 모두 이식했고 하네스에서 차이 0.** 문서 556건 · 처리기×문서 쌍 1,699개(RSXML1·2 처리기 5종 포함) 통과 1,699 · 실패 0. 실제로 파이썬이 무언가를 바꾼 쌍 403, 둘 다 입력을 거부한 쌍 136. 엄격(공백 포함) 비교 잡음 0.
- **미이식으로 남긴 처리기는 없다.** 다만 아래 '남은 한계'의 입력(앱 설정 → JSON 연결, 프로필 이름공간)은 이식 범위 밖이거나 거부한다.
- **미지원 입력 거부** 검사 29건(RSXML2 12 + 이번 17) 중 실패 0.
- **하네스가 헛돌지 않음**: (1) Rust 의 새 서식 ID 부여를 일부러 `+1`→`+2` 로 망가뜨리니 같은 하네스가 3개 처리기 529쌍 중 71쌍 실패를 잡았다(복구 후 최종 실행은 위 결과). (2) 출력을 일부러 망가뜨린 시험(`--sabotage`): 글자·문단 모양 참조 번호, `itemCnt`, 새 정의 id, 글자 크기, 글 안 글자/공백, 이름공간 주소, run 삭제 9가지가 5개 처리기 모두에서 전부 잡혔고(45/45), 의미가 같은 변형(속성 순서·요소 사이 공백·접두사 이름 바꿈)만 같다고 보았다(15/15).

### 하네스가 잡은 차이
- 처음 실행(별표·붙임·콜론 529쌍)에서 **3쌍 실패**: 붙임 글꼴의 `paragraph_text` 가 탭을 문자로 펼친 사본으로 문단을 판정하는데, Rust 는 원본으로 판정해 탭이 든 붙임 문단을 놓쳤다(`att_tab_child` 등 3건). 이식 쪽 버그였고 고쳤다(`general_texts_opt(flat)`).
- 빈 줄·강조 첫 실행 1쌍 실패: 프로필 XML 의 이름공간이 대상 문서에 없는 경우 파이썬은 선언을 덧붙여 처리하고 Rust 는 거부한다. 숨기지 않고 **의도된 거부로 분류**해 미지원 검사(`proc_emph_profile_unknown_ns`)로 옮겼다.
- 그 밖의 실패는 없었다.

## 서식 ID 규칙(파이썬과 같게 맞춘 것)
- 새 charPr/paraPr/font/borderFill/tabPr 는 해당 그룹 **끝**에 붙이고 `id = (그룹 안 숫자 id 최댓값 + 1)`, `itemCnt`(글꼴은 `fontCnt`)는 자식 수로 갱신. 원본 정의는 수정하지 않는다(복제 후 수정).
- 같은 (원본 id, 변경)에는 사본 하나를 공유(캐시). 단 콜론 라벨은 변화 없는 값이라도 글자마다 `stretched(...)` 사본을 만들며(파이썬 동작 그대로), 키 `(id, 자간, 장평)`으로 공유한다.
- id 부여 방식이 처리기마다 다르다: 별표·콜론·붙임은 숫자 id 만 세는 쪽(`isdigit`), 빈 줄·강조는 모든 자식 id 를 `int` 로 읽는 쪽(숫자가 아닌 id 가 있으면 파이썬이 중단 → Rust 도 오류).
- 부수 동작도 일치: 선택이 모두 비면 원본 복사, 콜론은 늘린 문단이 0개면 복사, 빈 줄·강조는 프로필이 비어도 선택이 있으면 재직렬화, 문자 오프셋은 코드 포인트 단위(astral 문자 사례 포함), 구역 순서(별표·붙임은 압축 순서, 콜론·빈 줄·강조는 번호 오름차순).
- `dom.rs`: 글이 빈 문자열인 요소를 `<t />` 로 쓰도록 바꿨다(ElementTree 와 같음; 기존 처리기 결과는 불변, 전체 하네스 통과).

## 설정 전달(추가 키)와 거부
`--config` JSON 에 추가: `std_symbols`(표준서식_기호_사용, 기본 true), `symbol_rules`(표준서식_설정["기호_규칙"]), `colon_label_enabled`(알파_콜론라벨_정렬_사용, 기본 true), `ratio_reduce`(장평_줄이기_사용, 기본 false), `blank_line_profile`(표준서식_설정["빈줄_서식"]), `emphasis_words`(표준서식_설정["강조_낱말"]). 처리기 이름: `asterisk_superscript`·`attachment_font`·`colon_label`·`blank_lines`·`emphasis`(파이썬 함수 이름 별칭 포함). 조사 결과 JSON 은 별표 `[[문단, 개수]]`, 붙임 `[[시작, 끝]]`, 콜론·빈 줄 `[번호…]`, 강조 `[0]`(파이썬과 같음).

거부(`미지원 입력:`, 종료 코드 4, 출력 없음): 알 수 없는 키, 형식 오류(규칙 배열·글꼴/크기 형식, 불리언 아님, 프로필 객체·배열 아님), `title_owner_text` 가 있는 빈 줄 서식(서식표 판별에 반영 못 함), 처리 중 만난 프로필 XML 의 이름공간이 문서에 없을 때.
`marker_scheme_active`·`indent_rules` 는 이 5개 처리기가 쓰지 않는다(코드로 확인: 모두 `leading_marker(text)`·`classify_marker(text)` 를 체계 없이 호출). 하네스에서 파이썬에 실제 체계 객체를 넣은 사례(`*_scheme_on`)로 결과가 같음을 확인했다.

## 남은 한계
- 프로필 XML 조각의 이름공간이 대상 문서 머리에 선언돼 있지 않으면 거부한다(파이썬은 선언을 덧붙임). 같은 URI 에 접두사가 여럿이면 마지막 선언을 쓴다(파이썬은 전역 등록기의 마지막 등록 — 같은 프로세스의 앞선 문서 영향이 있을 수 있음).
- 앱이 실제 설정(`표준서식_설정` 등)을 JSON 으로 내려 주는 연결 코드는 없다. 프로필은 파이썬 학습 결과(JSON 직렬화 가능)를 그대로 넘기면 된다.
- 시험은 합성·fixture 기반이며 실제 한/글 문서 코퍼스는 쓰지 않았다(사용자 문서 사용 금지). 파이썬 `\s`/`isspace`·`isdigit`(유니코드 숫자) 차이는 알려진 사례(NBSP·전각 공백·astral)만 시험했다.
- 파이썬 `isdigit()` 는 위첨자 숫자(`²`) 등도 참이라 이 경우 파이썬은 중단하는데 Rust 는 id 로 보지 않아 다르게 동작할 수 있다(시험하지 않음).
- 속도 이득은 3~5배 규모로 RSXML2 보다 작다.
