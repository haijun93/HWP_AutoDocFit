# INDENTW4 결과 — HWP 작업용 HWPX의 폭 표 내어쓰기

## 판정과 변경 범위

- `feature/INDENTW4`에서 `feature/INDENTW3`를 병합했다. `TODO.md` 양쪽 기록과 EFF5의 순회 종료 조건·INDENTW3 연결 심볼을 함께 보존했다.
- HWP 적용을 켜기 전에 합성 HWP를 다시 열어 작업용 HWPX로 저장하고, 계산 가능한 **384문단**을 실제 앱의 Shift+Tab 함수와 비교했다. 최대 오차 **0.04pt**, 0.5pt 초과 **0건**이었다.
- HWP 원본은 실제 변환된 작업용 HWPX 패키지가 있을 때만 허용한다. 바이너리 직접 처리·설정 끔·환경 불일치·미검증 문단의 기존 폴백을 유지한다. 설정·버전·글꼴 지문 기준을 넓히지 않았다.
- HWP·HWPX 전후 각 2회에서 출력 차이 0, COM 호출 약 6.2% 감소. 다만 **이번 14문단 입력은 켬이 약 4~5초 느렸다.** 정확도 조건에 따라 기능 브랜치에서 연결했으며, 속도 개선 합격이나 main 반영으로 판단하지 않는다.
- 로컬 커밋만 한다. 푸시·태그·main 병합·배포·설치본·서비스·사용자 설정 변경은 하지 않는다.

## 활성화 전 HWP 대조

도구 `scripts/validate_indent_hwp_pc.py validate`는 저장소의 기본 서식으로 합성 문서를 만들고, 새 `DispatchEx` 인스턴스에서 HWP 저장 → 닫기 → HWP 다시 열기 → 작업용 HWPX 저장 순서로 처리했다. 표 계획을 세운 다음 실제 앱의 `문단_내어쓰기_적용`을 실행했다. 비교 중에는 HWP 원본에 대한 폭 표 연결이 꺼져 있었다.

| 항목 | 측정 결과 |
|---|---|
| 설치된 한/글 판 | 9.6.1.10778(NEO), 환경 지문과 일치 |
| 글꼴 | TTF 7종·HFT 24종, 총 31종 |
| 문단 | 384개 계획·비교 완료, 폴백 0개 |
| 조합 | 글꼴 31종 × 정렬 3종 × 항목기호 4형태 = 372개 + 한 문단 안 TTF/HFT 혼합 12개 |
| 정렬 | 왼쪽, 양쪽 한글 글자 나눔, 양쪽 한글 어절 나눔 |
| 기타 조건 | □·ㅇ·-·※·*, 콜론 라벨, 앞 빈칸, 12·13·15·17pt, 장평 90·95·100·105%, 자간 −5·−3·0·3%, 굵게, 왼쪽·오른쪽 문단 여백 |
| 최대 `left`·`intent` 오차 | 0.04pt, 0.5pt 초과 0개 |
| HWP 저장 왕복 단위 | 384문단의 `case=HWPUNIT`, `default=case×2`, COM 값=`case×2`; 값·단위 불일치 0개 |
| 글·글자 모양 | 작업용 원본 대 표 적용 후 HWP 왕복, Shift+Tab 결과 대 표 결과 모두 불일치 0개 |
| 문단 수 | 구역 설정 빈 문단 포함 385개 유지 |
| 쪽수 | 내어쓰기 없는 입력 61쪽 → Shift+Tab 73쪽 / 표 적용 73쪽 |
| 원본 HWP | SHA-256 불변 |

쪽수 보존 판정은 같은 내어쓰기를 적용한 Shift+Tab 결과와 표 결과 사이의 73쪽 일치다. 내어쓰기가 없던 입력과의 61→73쪽 변화는 두 방식에서 동일하게 발생했다.

`inventory`는 글꼴 참조 ID를 글꼴 이름·TTF/HFT 형식으로 해석해 글자마다 비교한다. 문단 모양에서는 변경 대상인 `left`·`intent`를 별도로 대조하고 나머지 속성도 비교했다. 서로 다른 run 분할 때문에 글자 모양 변화가 숨겨지지 않게 했다.

문단별 실측·표 값·왕복 단위와 합성 원본 해시는 [측정 원자료](measurements/INDENTW4_SHIFT_2026-11-27.json)에 보존했다. 합성 HWP/HWPX 바이너리는 저장소 밖 시험 산출물로 둔다.

## HWP·HWPX 전후 측정

`scripts/validate_indent_hwp_pc.py benchmark`로 글이 서로 다른 14문단의 합성 서식을 만들고 HWPX·HWP로 각각 저장했다. 입력마다 끔1 → 켬1 → 끔2 → 켬2 순서로 총 8회 실행했다. 임시 설정 폴더에 `indent_table`만 바꾸고 동일한 합성 프로필과 실제 `format` 파이프라인·COM 계측을 사용했다.

합성 프로필은 ㅇ 문단에 HFT `신명 중명조`, 다른 항목에 TTF를 적용하며 ㅇ·※·*를 양쪽 정렬로 지정한다. 실제 출력에서도 HFT 1종과 TTF 4종(HY견고딕·한컴돋움·함초롬바탕·휴먼명조), 왼쪽 정렬 3문단·양쪽 정렬 12문단을 확인했다(빈 구역 문단 포함).

| 입력 / 회차 | 끔 전체(초) | 켬 전체(초) | 끔 COM 호출 | 켬 COM 호출 |
|---|---:|---:|---:|---:|
| HWPX / 1 | 27.281 | 32.028 | 19,894 | 18,653 |
| HWPX / 2 | 27.642 | 31.430 | 19,894 | 18,653 |
| HWP / 1 | 28.638 | 33.649 | 19,898 | 18,657 |
| HWP / 2 | 28.049 | 33.310 | 19,898 | 18,657 |

전체 시간은 COM 생성·정상 종료를 포함한 파이프라인 호출 시간이다. COM 호출 수는 기존 계측기의 문서 처리 구간이다.

| 내어쓰기 두 단계 합계 | 끔 1 / 2(초) | 켬 1 / 2(초) | 끔 호출 / 켬 호출 |
|---|---|---|---|
| HWPX | 2.857 / 2.674 | 6.792 / 6.762 | 4,368 / 3,126 |
| HWP | 2.796 / 2.647 | 6.995 / 7.130 | 4,368 / 3,126 |

- 켬 4회 모두 XML 직접 기록 **10문단**. 첫 내어쓰기 단계는 표 2 / 한/글 12문단, 재확인은 표 14 / 한/글 0문단이었다. 끔은 두 단계 모두 표 0 / 한/글 14문단이다.
- 두 내어쓰기 단계의 호출은 1,242회(28.4%), 문서 전체는 1,241회(약 6.2%) 감소했다.
- 전체 시간은 HWPX 평균 **27.462→31.729초(+4.268초)**, HWP 평균 **28.344→33.480초(+5.136초)**였다. 두 내어쓰기 단계에서 Python 쪽 시간이 약 0.5초에서 4.6~5.0초로 늘었다. 추가되는 스냅샷 저장·표 계획 작성 비용이 작은 문서의 호출 절감보다 큰 것으로 추정한다. 저장/계산 세부 분해는 별도로 계측하지 않았다.
- 끔/켬 네 쌍 모두 글·글자별 모양·`left/intent`를 제외한 문단 모양 차이 **0건**, `left/intent` 최대 차이 **0pt**. 문단 수 **15개**, 쪽수 **3쪽**으로 동일했다. 입력 원본과 처리 사본의 SHA-256은 8회 모두 불변이었다.
- 호출 감소가 작은 문서의 시간 단축을 보장하지 않는다. 문서 크기별 적용 판단과 저장 비용 개선은 후속 과제다. 이 결과로 속도 개선을 주장하지 않는다.

각 실행의 단계별 시간·호출 수·보존 판정은 [전후 측정 원자료](measurements/INDENTW4_PIPELINE_2026-11-27.json)에 보존했다.

## 시험

- 신규 비교 도구 시험: `Ran 6 tests in 3.029s` / `OK`.
- HWP 연결 후 신규·기존 관련 5모듈: `Ran 74 tests in 27.074s` / `OK`.
- 최종 코드 관련 **41모듈 389개 통과**, 제외 0개. 신규 10개에는 같은 이름의 TTF/HFT 구분, 글자 모양·문단 누락 검출, 0.5pt 경계, HWP 변환 패키지·이름만 바꾼 바이너리·설정/판 불일치·엔진 스냅샷 연결을 포함했다. 기존 시험은 수정하지 않았다.

```text
Ran 389 tests in 79.077s
OK
```

관련 범위는 내어쓰기·폭 계산·일괄 서식·첨부/기호/부연설명·파이프라인·실행 컨텍스트·저장·작업 상태·롤백이다. 전체 Python 시험은 아니다. 오류 주입 시험이 출력한 예상 예외 로그와 별개로 unittest 최종 결과는 위와 같다. 본체 `hwp-auto-docfit.py`의 CRLF 3,569줄, 단독 LF 0개를 확인했다.

## 도구 수정·미확인

- 첫 파이프라인 측정은 최소화 도구가 초기 네임스페이스의 `hwp=None`을 읽어 저장 전에 실패했다. 원인은 실행마다 상태를 격리하는 `RunContext`를 사용하지 않은 것이었다. 도구를 고쳤고, 실패 실행은 시간·호출 수 비교에서 제외했다.
- 두 번째 측정 입력에는 같은 문장이 반복되어 XML 일괄 적용이 0문단이었다. 폭 표를 끈 기준선도 기존 COM 글자 모양 적용의 `RequiredEditError`로 실패했다. 이 반복 입력의 전체 처리 성공은 미확인으로 남긴다. 기존 오류 차단을 바꾸거나 실패를 성공으로 처리하지 않았다. 문단마다 고유한 글을 넣은 입력으로 최종 8회 측정했다.
- 위 실패에서 저장 확인 창이 떠 정상 종료가 대기했다. Orca CLI는 실행 파일을 찾을 수 없어 사용하지 못했다. 새로 생성한 PID·시험용 문서 경로와 대화상자를 확인하고, 그 창에만 Win32 메시지로 ‘저장 안 함’을 전달해 정상 종료했다. 이후 도구의 종료 경로에 `Clear(1)`을 넣었다. 프로세스 강제 종료·사용자 창 조작은 하지 않았다.
- 전체 Python 시험 잠금이 있는 동안 COM을 호출하지 않고 기다렸다. 이후 COM 잠금을 배타 생성하고 자기 `DispatchEx` 인스턴스에서 합성 사본만 처리한다. 강제 종료 시간 제한을 사용하지 않는다.
- 한/글 2020 이상·다른 한/글 판·다른 글꼴 파일 환경은 확인하지 않았다. 판·글꼴 지문이 다르면 기존 방식으로 처리한다.
- 사용자 실문서, 큰 문서의 저장 비용, 표 칸·다단·개체가 섞인 HWP의 확대 적용, 전체 Python·Flutter·EXE·설치본 검증은 이번 결과에 포함하지 않는다. 기존 미검증 조건은 폴백을 유지한다.
