## 1. 목표 지연(한 글자 입력 → 결과가 화면에 보일 때까지)

| 검색 | 목표(p95) | 기준 규모 | 근거 |
|---|---|---|---|
| 파일명 | **50ms** (백엔드 10ms 이하) | 이름 20만 개 | 기존 목표 100ms(`TM_SEARCH_DESIGN.md` 12줄)를 지시("최고 속도")에 맞춰 절반으로. 계산은 Python 메모리 리스트로도 10만 개 6.9ms(조사 (나)) → 남는 시간은 IPC·그리기 몫. 흔히 쓰는 "0.1초 안이면 즉시로 느낀다"는 경험칙(이번에 출처 확인 안 함)보다 여유 |
| 타임라인 | **100ms** | `files` 10만 행 | 지금 LIKE 한 번 144ms(조사 (나)). 기간·종류 필터가 같이 걸리므로 파일명보다 한 단계 느슨하게 |
| 본문 1단계(파일명·제목 일치) | **100ms** | 3,000문서 | 파일명 색인을 그대로 씀 |
| 본문 2단계(본문 일치 첫 20건) | **300ms** | 3,000문서 × 40문단, 흔한 말 | 지금 첫 질의 2.0~6.3초(조사 (나)). 입력 중에는 상위 일부만 있으면 된다 |
| 본문 완료(전체 순위·횟수) | **1,000ms** | 같음 | 기존 확정 목표(`TM_SEARCH_DESIGN.md` 12줄) |
| 입력 중 앞 요청 | 다음 글자 도착 후 **50ms 안에** 계산 중단 | — | 낡은 계산이 다음 요청을 막지 않게 |

측정은 계획 S0의 도구로, 1회 실행·실행 중 다른 빌드 금지(운영 규칙 52줄).

## 2. 설계

### 2.1 파일명 메모리 색인 — 어디에 둘까

| 선택지 | 내용 | UX | DX | AX | 되돌리기 |
|---|---|---|---|---|---|
| A. Python 메모리 리스트 | `ContentSearchIndex`/`Store` 옆에 이름·경로 리스트를 두고 질의마다 훑기 | 10만 개 약 7ms로 목표 충족 | 가장 작은 변경 | 상태가 Python 안에만 | 쉬움 |
| B. KAgent(상주 Rust)에 둔다 | 이미 타임라인 폴더를 감시(`kagent/src/watch.rs`)하므로 변경을 바로 반영. 파이프로 질의 | 앱을 닫아도 색인 유지 → 첫 검색도 즉시 | 클립보드 상주 프로그램에 책임 추가, 메모리 증가가 KAgent "최소 자원" 원칙과 충돌 | 상태 파일(`write_status`) 재사용 가능 | 중간 |
| C. 새 Rust 상주 프로세스(klib 서버 모드) | klib에 장기 실행 모드 추가, 파이프로 이름·본문 질의 | Python 잠금과 무관 | 프로세스 하나 더(수명·재시작·업데이트) | 명시적 상태 | 어려움 |

**권고: A로 먼저 목표를 맞추고(S2), 실측이 20만 이름에서 10ms를 넘을 때만 B로 옮긴다.** 이유: 운영 규칙 61줄(Rust 전환은 계산량이 큰 몫일 때만). 지금 느린 원인은 계산이 아니라 디바운스·상태 조회 왕복·IPC 전역 잠금·SQL 전체 읽기다(조사 (나)). 사용자 지시의 "Rust 기반"은 S6(본문 후보 계산)과 B 전환에서 쓰며, 보고 때 이 판단을 명시한다(Q7).

### 2.2 변경 감지

- 지금: KAgent가 `ReadDirectoryChangesW`로 감시 → 400ms 모아 증분 스캔(`kagent/src/main.rs:289-324`) → 타임라인 DB 갱신. 앱 쪽 파일명 색인은 DB가 바뀐 것을 알아야 한다.
- 설계: 메모리 색인에 **세대 번호**(DB의 변경 표지, 예: `files`의 최대 갱신 시각 또는 KAgent 상태 파일의 세대)를 두고, 질의 때 값이 다르면 바뀐 행만 다시 읽는다. 폴링 타이머를 두지 않는다(질의가 올 때만 확인).
- 관리자 권한이 허락되면(Q1) USN 읽기를 나중에 검토. 1차 범위 아님.

### 2.3 입력마다 취소·대체

- 화면: 파일명·타임라인은 디바운스를 **0ms**(매 글자), 본문은 **120ms**로 줄인다. 검색 전 `_readContentStatus()` 대기를 빼고 상태는 응답에 함께 싣는다(`timemachine_screen.dart:315,487`).
- 서비스: 검색 명령에 `search_id`(세대)를 받는다. 같은 화면의 새 검색이 오면 앞 검색을 중단한다 — SQLite는 `Connection.interrupt()`, Python 루프는 세대 확인. 응답에 `search_id`를 돌려줘 화면이 세대로 거른다(지금의 revision 방식 유지).
- IPC 잠금: 검색 명령은 읽기 전용이므로 `ipc_server.py:67`의 전역 `app.lock` 밖, 검색 전용 잠금에서 돌게 한다. **이 변경은 다른 명령과의 동시 실행을 처음 허용하므로** 타임머신 서비스의 읽기 경로가 스레드에 안전한지(각 객체의 `_lock`) 먼저 확인한다(S1의 완료 조건).

### 2.4 다중 단어 일치 규칙(공통 질의 해석기)

- 질의 해석은 하나(`ContentSearchIndex.parse_query`, `content_search.py:963`)로 통일하고 파일명·타임라인도 같은 해석기를 쓴다. 공백 = AND, 순서 무관, 조사는 부분 일치로 처리(기존과 같음).
- 파일명·타임라인: 낱말마다 `lower(name) LIKE ?`를 AND로(지금은 질의 전체 한 덩어리, `store.py:171-174`). 결과가 바뀌는 변경(지금 0건이던 "예산 집행"이 걸림)이지만 사용자 지시 그대로이므로 결정 없이 진행한다.
- 본문: 순위 계층(사용자 결정 Q3·Q4 전 기본안) — ① 한 문장에 모두 ② 한 문단에 모두 ③ 한 문서에 모두. 문장 경계는 일치 문단 안에서만 검색 때 자른다(색인 변경 없음). 일반 본문검색은 지금 문단 단위 AND라 ③을 새로 넣으면 결과가 늘어난다 → Q3에서 정한다.
- 붙여 친 낱말의 띄어쓰기 무시(조사 (다-1) W1)는 Q5 결정 뒤 별도 단계.

### 2.5 본문 색인 구조

- 지금: FTS5 `trigram` 문단 표 + 2글자 조각 표(`content_short_grams`) + 1글자는 `LIKE`(`content_search.py:730-769`). Rust 색인기도 같은 표에 쓴다(`klib/src/index_content.rs:52-53`).
- 유지한다. 느린 원인은 색인이 아니라 검색 뒤처리(후보 문서의 모든 문단을 Python으로 읽음, `content_search.py:1873-1881`)로 보인다 → S0에서 프로파일로 확정한 뒤 S5에서 뒤처리를 SQL 집계·`LIMIT`으로 옮긴다.
- 1글자 질의: 본문은 **2글자부터** 검색한다(1글자는 파일명만). 1글자 본문 `LIKE`는 전체 훑기라 실시간 목표와 맞지 않는다. 사용자 영향이 있으므로 Q8.
- 대안(S5가 목표 미달일 때만): klib의 tantivy 색인(`klib/src/search.rs`, `KoBigram`)을 타임머신 본문에 쓰고 검색도 Rust에서. 색인 이전·결과 동일성 검증 비용이 커서 2차.

### 2.6 단계적 결과(본문)

1. 1단계: 파일명·문서 제목 일치(메모리 색인) → 즉시 표시, 표지 "본문 찾는 중".
2. 2단계: 본문 일치 상위 20건(문단 FTS + `LIMIT`, 횟수는 근사 표시 없이 비워 둠).
3. 3단계: 전체 순위·키워드별 횟수·위계 경로 → 목록을 교체하되 사용자가 고른 항목·스크롤 위치는 유지.
- 서비스 응답: `{"search_id", "phase": "names"|"partial"|"complete", "items", "done": bool}`. IPC가 요청-응답 1회 구조라 단계마다 화면이 같은 `search_id`로 다음 단계를 요청한다(서버 밀어주기 없음 → IPC 변경 최소).

### 2.7 화면 상태 기계(대원칙: 암묵적 상태 드러내기)

지금 암묵적 상태: `_contentMode`·`_relatedMode`·`_fileTableView`·`_fileSearchActive`·`_fileSearchSupported`·`_debounce`·두 revision 번호·`_contentIndexRunning`이 흩어져 "지금 검색 중인지, 어느 단계인지"가 코드에 없다(`timemachine_screen.dart:55-104`).

명시적 상태 `SearchSession`(한 곳, Dart enum + 값):

| 상태 | 뜻 | 화면 표시 |
|---|---|---|
| `idle` | 검색어 없음 | 타임라인 |
| `waiting` | 디바운스 중(본문만) | 그대로 |
| `searching(id, phase)` | 요청 보냄, phase = names/partial | 이전 결과 흐리게 + 단계 표지 |
| `partial(id)` | 1·2단계 결과 표시 중 | "본문 찾는 중" |
| `complete(id)` | 완료 | 결과 수 |
| `failed(id, reason)` | 오류 | 오류 문구, 다시 시도 |
| `indexNotReady` | 본문 색인 없음·진행 중 | 색인 진행률(기존 `content_status`) |

전이: 입력 → (`waiting`|`searching`) → `partial` → `complete`; 어느 상태든 새 입력 → 새 `id`로 `searching`(앞 `id` 응답은 버림). **불가능한 전이**: 낡은 `id`의 응답으로 `complete` 진입, `failed`에서 사용자 입력 없이 재시도, `indexNotReady`에서 본문 2단계 요청. 에이전트용: 서비스 로그에 `search_id·phase·ms` 한 줄(측정·회귀 비교에 사용).

| S8 (선택) 띄어쓰기 무시·정규식 | W1(공백 없는 비교), `re:` 파일명 정규식(Rust `regex` 선형 시간 확인 뒤) | 미정 | Q5·Q6 결정 뒤 별도 카드 | S2, S7 |
| S9 (조건부) KAgent 이전 | 파일명 색인을 KAgent로 | `kagent/src/` | S2 측정이 목표 미달일 때만 | S2 |

병렬 가능: S2·S3은 S0 뒤 동시에(파일 겹침: `timemachine_service.py`는 S2만 고치게 나눈다). S4는 S1 뒤, S5와 동시 가능(파일 겹침 없음).

### 실기 확인 절차(총괄용, S4·S5 뒤)

1. 조사 폴더에 문서 3,000개 이상(사본) 등록, 본문 색인 완료까지 둔다.
2. 이름 찾기 모드에서 "예산 집행"을 한 글자씩 친다 → 글자마다 목록이 바뀌고 멈춤이 보이지 않아야 함(화면 녹화로 글자→목록 변화 100ms 이하 확인).
3. 본문 모드에서 "예산 집행 계획"을 친다 → 파일명 일치가 먼저 뜨고 "본문 찾는 중" 표지 뒤 본문 결과가 1초 안에 완성.
4. 본문 검색 도중 다른 단추(달력·정렬)를 누른다 → 즉시 반응(전역 잠금 대기 없음).
5. 합격: 2·3·4 모두. 하나라도 어긋나면 서비스 로그의 `search_id·phase·ms` 줄을 첨부해 보고.

## 4. 사용자 결정이 필요한 것

- **Q1 관리자 권한**: 관리자 권한 없이도 돌아가야 합니까? (기본: 예. MFT·USN 직접 읽기는 쓰지 않고 폴더 감시로 대신. Everything도 NTFS 색인에는 관리자 또는 서비스 설치가 필요하다고 공개 자료에 적혀 있음)
- **Q2 대상 범위**: 파일명 검색 대상은 지금처럼 조사 폴더(본문 색인 대상 형식)만입니까, 조사 폴더의 모든 파일입니까, 드라이브 전체입니까? (기본: 조사 폴더. 드라이브 전체는 관리자 권한·메모리 문제로 권하지 않음)
- **Q3 "함께 있는 문장"의 범위**: 같은 문장 > 같은 문단 > 같은 문서 순으로 순위만 나누고 모두 보여 줄까요, 같은 문단 안에 모두 있는 문서만 보여 줄까요? (기본: 순위만 나눔. 단, 일반 본문검색은 지금 문단 단위라 결과 수가 늘어남)
- **Q4 위계 정렬과의 순서**: 확정된 위계 정렬(가장 높은 위계 > 언급 횟수 > 날짜)보다 "같은 문장에 모두"를 먼저 볼까요, 위계 다음에 볼까요? (기본: 위계검색은 위계 우선 유지, 일반 본문검색은 문장 계층 우선)
- **Q5 붙여 친 낱말**: "예산집행"으로 쳤을 때 "예산 집행"도 찾을까요? (기본: 1차는 아니오. 색인 저장량이 늘어 측정 뒤 결정)
- **Q6 정규식**: 정규식 검색을 줄까요? (기본: 1차는 안 줌. 준다면 파일명부터 `re:` 접두로, 본문은 시간 상한을 둔 뒤)
- **Q7 Rust 범위**: 측정상 Python 메모리 색인이 목표(파일명 10ms)를 맞추면 파일명 색인은 Python에 두고, Rust는 본문 계산(S6)과 규모가 커질 때(S9)에 씁니다. 지시하신 "Rust 기반"을 이렇게 단계적으로 적용해도 됩니까?
- **Q8 1글자 본문검색**: 본문은 2글자부터 검색하고 1글자는 파일명만 보여 줘도 됩니까? (기본: 예. 1글자 본문은 전체 훑기라 실시간 목표와 맞지 않음)
