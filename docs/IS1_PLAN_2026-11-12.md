# IS1 실시간·다중 단어 검색 — 계획 (2026-11-12, 사용자 결정 Q1~Q8 반영판)

조사: `docs/IS1_RESEARCH_2026-11-12.md`. 작업 브랜치: `feature/instant-search`. 이 문서는 계획만 담는다(코드 변경 없음).
고친 이유: 첫 판의 Q1~Q8에 사용자가 답했다(cards/IS1.md 끝 "사용자 결정 Q1~Q8"). 첫 판의 "파일명 색인은 Python 먼저"(옛 Q7)는 **기각**되었고, 이 판은 그 결정에 맞춰 결정 표·설계·단계를 다시 썼다.
표기: **확인**은 이번에 코드를 직접 읽은 것, **추정**은 계산·공개 자료로 낸 값(S0·S2에서 실측으로 바꾼다), **미확인**은 읽지 않은 것.

## 2. 설계

### 2.1 어느 프로세스·크레이트에 둘까

책임별로 셋으로 나눈다. 기준은 ① 권한(SYSTEM으로 돌 코드는 가장 작게) ② 수명(색인은 늘 떠 있어야 첫 검색도 즉시) ③ 기존 결정(가상 폴더 창은 별도 exe `kvf.exe` — 사용자 결정, cards/VF1B.md)과의 일관성.

| 기능 | 놓을 곳 | 이유 |
|---|---|---|
| 드라이브 전체 파일명 색인(MFT·USN) | **새 크레이트 `kfind/` → `kfind.exe`(Windows 서비스)** | 관리자 권한이 필요한 유일한 부분. 문서 파서·이름 바꾸기·편집기 코어를 품은 klib을 통째로 SYSTEM으로 돌리면 공격면이 커진다. kagent는 "초경량 클립보드 상주" 원칙(`kagent/Cargo.toml` 설명)과 맞지 않고 UI 프로세스를 높은 권한으로 돌리면 끌어 놓기(UIPI) 등이 깨진다 |
| 본문 문장 색인·실시간 본문 질의, 타임라인 이름 질의 | **klib 확장**(기존 `klib.exe` 파이프 서버 모드, `klib/src/pipe.rs`·`main.rs:234` 확인) | 사용자 문서를 읽는 일이라 사용자 권한이 맞다. klib에는 이미 `tantivy`·`KoBigram`(`klib/src/search.rs:121`)·`rusqlite`·본문 색인기(`index_content.rs`)가 있어 새 의존성이 없다 |
| 화면 중계 | Python `timemachine_service.py` + 새 `docfit_app/kfind_client.py` | Flutter(Dart)는 지금 Python 루프백 소켓으로만 말한다(`native_client.dart:80`). 중계 한 단계는 1ms대(S4에서 실측). 넘으면 Q |

kvf와의 관계: "책임마다 exe를 나누고 UI 프로세스는 일반 권한"이라는 원칙이 같다. `kfind`는 창이 없는 백그라운드 서비스라 kvf·kagent와 단축키·트레이·창이 겹치지 않는다. 나중에 kvf가 드라이브 전체 이름 찾기를 쓰려면 `kfind` 파이프를 부르면 된다(이번 범위 아님). kagent 코드는 복사하지 않는다(VF1B 원칙) — `kfind`의 파이프 코드는 접근 규칙(ACL)이 달라 새로 쓰고, klib·kagent·kvf·kfind 공용 파이프 크레이트로 뺄지는 Q14.

klib 수명 문제(확인): klib 서버는 60초 유휴면 스스로 끝난다(`klib/src/main.rs` watchdog, `KLIB_IDLE_SECS`). 문장 색인은 디스크 mmap이라 다시 떠도 여는 데 수십 ms(추정)지만, 타임머신 화면이 열려 있는 동안은 Python이 화면 열 때 klib을 미리 띄우고 검색 요청이 활동 시각을 갱신하므로 유휴 종료가 걸리지 않는다. 다시 뜰 때 첫 질의 목표는 §3에 따로 둔다.

### 2.2 관리자 권한을 얻는 방법

| 선택지 | 사용자 경험 | 보안 | 판단 |
|---|---|---|---|
| A. 앱 전체를 관리자로 실행 | 켤 때마다 UAC 창. 관리자 창에는 탐색기에서 끌어 놓기 불가(UIPI). 한/글 COM 자동화는 무결성 수준이 다른 한/글과 섞여 실패할 수 있음(미확인, 위험 큼). 설치기가 `PrivilegesRequired=lowest`(`installer/setup.iss:12` 확인) 사용자별 설치라 기본 방식과도 어긋남 | 사용자 문서 파서·COM·WebView 전부가 관리자 권한으로 돎 → 문서 한 개의 파서 결함이 곧 관리자 권한 탈취 | **채택 안 함** |
| B. 색인 서비스만 관리자(Windows 서비스, SYSTEM) | UAC는 **설치할 때 1번**. 이후 부팅 때 자동 시작(지연 자동 시작), 앱을 닫아도 색인 유지 → 앱 켜자마자 즉시 검색. USN은 서비스가 꺼진 동안의 변경도 OS가 보관하므로 다시 켤 때 따라잡음(조사 (가) 확인) | SYSTEM 코드는 "이름 열거 + 질의 응답"만. 파일 내용을 열지 않음. 아래 보호 조치 필수 | **권고** |
| C. 로그온 때 "가장 높은 권한" 예약 작업 | 설치 때 UAC 1번. 로그온해야 시작 | 사용자 세션의 관리자 토큰으로 돎 — B보다 권한이 넓고 서비스 관리 기능(복구·중지)을 직접 만들어야 함 | B가 막힐 때 대안 |

B의 보호 조치(모두 S3 완료 조건):
1. **실행 파일 위치**: 앱은 사용자별 폴더(쓰기 가능)에 깔린다. 서비스가 그 파일을 직접 가리키면 일반 권한 악성 코드가 `kfind.exe`를 바꿔 SYSTEM 권한을 얻는다. 설치 명령(`kfind.exe --install-service`, UAC로 실행)은 자신을 `%ProgramFiles%\HwpAutoDocFit\kfind\`(관리자만 쓰기)로 복사하고 그 사본을 등록한다.
2. **파이프 접근 규칙**: 원격 거부(`PIPE_REJECT_REMOTE_CLIENTS`, klib와 같음), 대화형 사용자·SYSTEM만 연결, 요청 크기 상한(klib처럼 64KB). 명령은 `query`·`cancel`·`status`·`path_of` 읽기 전용뿐 — 파일을 만들거나 실행하는 명령 없음.
3. **권한 줄이기**: 필요한 특권만 남김(`SERVICE_CONFIG_REQUIRED_PRIVILEGES_INFO`). 볼륨 열기에 꼭 필요한 최소 집합은 S2에서 실측으로 확정(미확인).
4. **이름 노출**: 드라이브 전체 색인에는 다른 사용자 프로필의 파일 이름도 들어간다. 기본은 다른 사용자 프로필·`$Recycle.Bin`·`System Volume Information` 결과 제외(Q9).
5. **갱신**: 앱 업데이트가 새 `kfind.exe`를 가져오면 버전이 다를 때 화면에 "검색 서비스 갱신"을 띄우고 UAC 1번으로 교체. 몰래 교체하는 경로 없음. 앱 제거 때 서비스 제거도 UAC 필요(사용자별 설치기는 스스로 못 함 → 앱 안 "드라이브 전체 찾기 끄기" 단추로 제거, 제거 안내를 설치기 제거 화면에).

설치 시점은 기본으로 **처음 파일명 찾기를 열 때 "드라이브 전체에서 찾기 켜기" 단추 → UAC 1번**(Q10).

### 2.3 파일명 색인(`kfind`) 구조와 메모리 상한

읽기: 볼륨마다 `FSCTL_ENUM_USN_DATA`로 MFT 항목(파일 참조 번호·부모 참조 번호·이름·속성)을 한 번에 열거 → 이어서 `FSCTL_READ_USN_JOURNAL`을 "새 기록이 올 때까지 기다림"으로 계속 읽어 만들기·지우기·이름 바꾸기·옮기기를 반영. 크기·수정 날짜는 1차에 저장하지 않고 화면에 보이는 줄만 그때 읽는다(보이는 50줄 × `GetFileAttributesEx`, 추정 수 ms). 원시 `$MFT` 해석(크기·날짜까지 메모리에)은 Q11.

메모리 배치(항목당, 추정):

| 부분 | 바이트 | 설명 |
|---|---|---|
| 항목 구조 | 16 | 이름 위치 u32, 이름 길이 u16, 비교형 길이 u16, 부모 번호 u32, 속성·볼륨 u32 |
| 원래 이름(UTF-8) | 평균 28 | 평균 이름 약 18글자(한글·영문 섞임) 가정 — 미확인, S2에서 실측 |
| 비교형 이름 | 평균 24 | 소문자화 + 공백·`_`·`-`·`.`(확장자 앞 제외) 제거(Q5). 질의는 이 열만 훑는다 |
| MFT 번호 → 항목 표 | 약 5 | MFT 레코드 번호를 바로 첨자로 쓰는 u32 배열(레코드 수가 항목 수의 약 1.2배). 해시표(항목당 16~24B)보다 작다 |
| **합계** | **약 73** | 100만 항목 약 73MB, 200만 약 146MB |

구청 PC 항목 수 추정: Everything 공개 수치로 Windows 11 새 설치 약 25만(조사 (가) 확인). 오피스·한/글·업무 자료가 더해진 C: 50만~100만, 자료 드라이브 D: 10만~50만으로 **설계 기준 150만 항목**(추정, S2에서 실제 업무 PC 1대 항목 수 실측 — 이름 길이 분포 포함). 상한: 100만 80MB / 200만 160MB. 300만을 넘으면 색인은 하되 상태에 "항목 많음"을 표시하고 보고(Q9 제외 목록으로 줄임). Everything은 100만에 약 100MB(조사 (가) 확인)라 이 상한은 그보다 작다.

질의(S1): 낱말마다 비교형으로 바꿔 모두 포함(AND, 순서 무관) → 항목 배열을 스레드 4개로 나눠 `memchr::memmem`식 부분 문자열 찾기(새 크레이트 `memchr`, 무의존·널리 쓰임) → 상위 N(기본 200)만 정렬해 반환, 전체 개수는 따로 셈. 정렬: 이름 완전 일치 > 이름 앞부분 일치 > 그 밖, 같은 등급은 경로 짧은 순 → 이름 순(Q12). 경로 문자열은 반환할 N개만 부모 사슬로 조립.

시작·재시작: 서비스 종료 때 색인을 스냅숏(`%ProgramData%\...\kfind\vol-<일련번호>.snap`, USN 저널 ID·마지막 USN 포함)으로 저장 → 다음 시작 때 읽고 그 USN부터 따라잡기. 저널 ID가 바뀌었거나 기록이 잘려 나갔으면(저널 재생성·넘침) 그 볼륨만 처음부터 다시 열거, 그동안은 옛 스냅숏으로 답하고 상태를 `rebuilding`으로.

### 2.4 다중 낱말 일치 규칙(이름·타임라인·본문 공통)

비교형 `fold(s)` = 유니코드 NFC → 소문자화 → 공백류·`_`·`-`·`·` 제거(본문은 문장부호 `,`·`(`·`)` 등도 제거, 목록 S5에서 고정). 질의 해석:
1. 질의를 공백으로 낱말로 나눈다. 각 낱말 `w`를 `fold(w)`.
2. 대상(이름 또는 문장)의 `fold`에 모든 `fold(w)`가 들어 있으면 일치. 순서 무관.
3. Q5가 저절로 성립: "예산집행" 한 낱말 → `예산집행`이 `fold("예산 집행 계획")=예산집행계획`에 들어 있음. "예산 집행" 두 낱말 → `예산`·`집행`이 `fold("예산집행을")`에 들어 있음.
4. 조사는 부분 일치라 따로 처리하지 않는다("예산을"은 "예산"으로 찾힘). 형태소 분석 없음.
5. 대가(속도 우선으로 감수): 비교형은 경계를 지우므로 "산집" 같은 낱말 걸침 일치도 생긴다. 이름 한 낱말 질의 결과도 지금보다 늘 수 있다(예: 지금 0건인 "예산집행"이 `예산_집행.hwp`를 찾음) — Q5가 원한 변화. 단계 보고에 늘어난 예시를 적는다.
6. 본문에서 2글자 미만 낱말(Q8): 낱말 하나뿐이면 본문 검색을 하지 않고 파일명만. 여러 낱말 중 섞이면 그 낱말은 일치 판정에서 빼고 화면에 "‘및’은 너무 짧아 뺐습니다"로 표시(Q13).
7. 기존 문법(`parse_query`, `content_search.py:963` 확인): `ext:`·`path:`·`after:`/`before:`는 그대로 거르개로. `-제외`는 "그 문장에 없음"이 아니라 **문서에 없음**으로 유지(지금과 같음). `"구문"`은 공백까지 그대로 같은 문장 안 연속 일치. `~N` 근접은 문장 규칙과 겹쳐 폐지 제안(Q15).

### 2.5 본문: 문장 경계 저장과 문장 색인(klib)

지금(확인): 본문은 SQLite `content_paragraph_fts`(trigram, 문단 한 행 = `path, paragraph_index, level, level_rank, body, …`)와 `content_short_grams`(2글자 조각→문서)에 있다(`content_search.py:705-769`, Rust 색인기도 같은 표, `klib/src/index_content.rs` `initialize`). **문장 경계는 어디에도 저장되지 않는다.** 검색 뒤처리는 후보 문서의 모든 문단을 Python으로 읽는다(조사 (나)).

설계: klib에 **파생 문장 색인**을 새로 둔다(tantivy, 디스크 mmap). 문장 하나 = tantivy 문서 하나.

| 필드 | 종류 | 용도 |
|---|---|---|
| `fold_body` | 2글자 조각 토큰(기존 `KoBigram` 재사용, 비교형 위에서) | 일치 판정. 위치 포함 → 낱말 = 연속 조각 구문 질의로 정확한 부분 문자열 일치 |
| `doc_id` | 빠른 필드 u32 | 문서(`content_meta.path`)와 연결 |
| `para` / `start` / `end` | 빠른 필드 u32·u16·u16 | 문단 번호와 문단 안 글자 위치 → 미리보기 강조는 SQLite 문단 원문에서 잘라 씀(문장 원문 중복 저장 안 함) |
| `level_rank` | 빠른 필드 u8 | Q4 위계 정렬 |
| `date` · `ext` · 경로 접두 | 빠른 필드 | `after:`·`ext:`·`path:` 거르개 |

문장 나누기 규칙(Rust `klib/src/sentence.rs`, 규칙 판 번호 `SENTENCE_RULE_VERSION`):
- 문단 안 줄바꿈은 문장 경계.
- `.`·`?`·`!`·`。` 뒤에 공백·줄 끝이 오면 경계. 단, 숫자 사이(`1.5`), 맨 앞 목록 표지(`1.`·`가.`·`(1)`), 날짜(`2026. 11. 12.`)는 경계 아님.
- 마침표 없는 개조식 문단(`○ 예산 집행 계획 수립`)은 문단 전체가 한 문장. 표 칸 하나도 한 문장.
- 이 규칙으로 정답 표(합성 문장 100개 이상, 개조식·숫자·날짜·표 포함)를 만들어 시험.

**재색인 필요 여부**: 문서를 다시 읽는(한/글·HWPX 추출) 재색인은 **필요 없다**. 문장은 이미 저장된 문단 원문(`content_paragraph_fts.body`)에서 잘라 만들기 때문이다. 처음 한 번 "문장 색인 만들기"(문단 전체 읽기 → 나누기 → tantivy 쓰기)가 필요하고, 이후에는 문단이 바뀐 문서만 갱신. 문장 규칙 판이 바뀌면 문장 색인만 다시 만든다. 기존 SQLite 표·스키마는 바꾸지 않는다(기존 기능·시험 그대로).

갱신 연결: ① Rust 색인기(`index_content.rs`)가 문서를 쓰고 나면 같은 실행에서 그 문서의 문장 색인도 갱신 ② Python 대체 색인기로 쓰인 문서는 klib이 `content_meta`의 (path, mtime, size) 세대 표지를 비교해 바뀐 문서만 따라잡음(질의가 올 때만 확인, 폴링 없음).

크기(추정): 3,000문서 × 40문단 × 문장 약 1.5 = 18만 문장, 위치 포함 조각 색인 문장당 약 150~200B → **약 30~40MB 디스크**. 3만 문서면 약 0.4GB(Q16). S5에서 위치 포함 구문 질의와 "조각 AND + 문단 원문 확인" 두 방식을 같은 자료로 재고 빠른 쪽을 고른다(결과는 같아야 함).

질의(S6): 낱말별 구문 질의의 AND → 일치 문장 → 문서별로 모아 정렬(Q4): 문서의 일치 문장 중 **가장 높은 위계** > **일치 문장 수(언급 횟수)** > **날짜**. 위계검색 화면도 같은 경로를 쓰되 위계 경로(조상 제목) 표시는 기존 `hierarchy_path.py` 정보를 SQLite에서 읽어 붙인다. 지금 위계검색의 "직접 일치 없으면 조상 제목까지 합쳐 일치"(`content_search.py:1537-1570`)는 문장 규칙(Q3)에 따라 빠진다(Q17로 확인).

### 2.6 입력마다 취소·대체와 단계적 결과

- 화면: 디바운스 **0ms**(모든 검색). 대신 검색 통로마다 "보낸 요청 1개 + 대기 1개(가장 최신만)"로 묶는다 — 앞 요청이 끝나기 전 여러 글자가 오면 마지막 것만 보낸다. 검색 전 `_readContentStatus()` 대기를 없애고 상태는 응답에 싣는다(`timemachine_screen.dart:315,487` 확인).
- Python: 검색 명령(`file_search`·`content_search`·`range`의 이름 질의)은 전역 `app.lock`(`ipc_server.py:67` 확인) 밖 검색 전용 경로에서 Rust로 넘기기만 한다. 넘긴 요청의 `search_id`를 기록.
- Rust: `kfind`·klib 모두 통로마다 `AtomicU64` 세대 번호. 새 `search_id`가 오면 세대를 올리고, 진행 중 질의는 항목 4,096개(kfind)·문서 256개(klib 수집기)마다 세대를 확인해 멈춘다.
- 단계(본문): ① `names` — kfind/본문 색인 문서 이름 일치(즉시) ② `top` — 문장 일치 상위 20문서 ③ `complete` — 전체 개수·문서별 횟수·위계 경로. 응답 `{"search_id","phase","items","total","done"}`. IPC가 요청-응답 1회 구조라 화면이 같은 `search_id`로 다음 단계를 요청(서버 밀어주기 없음). ②와 ③이 같은 질의 한 번에 끝나면(목표대로면 대부분) ②를 건너뛰고 ③을 바로 돌려준다.

### 2.7 화면 상태 기계(대원칙: 암묵적 상태 드러내기)

지금 암묵적 상태(확인): `_contentMode`·`_relatedMode`·`_fileTableView`·`_fileSearchActive`·`_fileSearchSupported`·`_debounce`·두 revision 번호·`_contentIndexRunning`이 흩어져 있다(`timemachine_screen.dart:55-104`). 이를 둘로 나눠 명시한다.

**(가) 색인 상태 `IndexAvailability`** — 검색과 독립, `status` 응답으로만 바뀐다.

| 상태 | 뜻 | 화면 |
|---|---|---|
| `driveIndexOff` | kfind 설치 안 됨 | 파일명은 지금 방식(본문 색인 문서만) + "드라이브 전체에서 찾기 켜기" 단추 |
| `driveIndexInstalling` | UAC 대기·설치 중 | 단추 비활성, "설치 중" |
| `driveIndexBuilding(progress)` | 첫 열거 중 | 지금 방식으로 답하며 진행률 |
| `driveIndexReady` | 정상 | 표시 없음 |
| `driveIndexRebuilding(volume)` | 저널 재생성으로 한 볼륨 다시 열거 | 옛 색인으로 답하며 작은 표지 |
| `driveIndexUnavailable(reason)` | 서비스 멈춤·버전 다름 | 지금 방식으로 대체 + 사유·"갱신" 단추 |
| `sentenceIndexBuilding(progress)` / `sentenceIndexReady` | 문장 색인 | 만드는 중이면 본문은 지금 방식(Python `keyword_search`)으로 답하고 "문장 단위 검색 준비 중" 표시 |

**(나) 검색 세션 `SearchSession`** — 통로(파일명·타임라인·본문)마다 하나.

| 상태 | 뜻 | 화면 |
|---|---|---|
| `idle` | 검색어 없음 | 타임라인 |
| `tooShort` | 본문 통로에 2글자 미만(Q8) | 파일명 결과만, "본문은 2글자부터" |
| `inFlight(id, phase, pendingQuery?)` | 요청 보냄(대기 질의 최대 1개) | 이전 결과 유지·흐리게 + 단계 표지 |
| `partial(id, phase)` | `names`/`top` 결과 표시 중 | "본문 찾는 중" |
| `complete(id)` | 완료 | 결과 수 |
| `failed(id, reason)` | 오류 | 문구 + 다시 시도 |

전이: 입력 → (`tooShort`|`inFlight`) → `partial` → `complete`. `inFlight` 중 새 입력은 `pendingQuery`만 바꾸고, 응답이 오면 낡은 결과는 버리고 대기 질의를 새 `id`로 보낸다.
**불가능한 전이**(위젯 시험으로 막음): 낡은 `id` 응답으로 `partial`/`complete` 진입, `failed`에서 입력 없이 재시도, `tooShort`에서 본문 요청, `sentenceIndexBuilding` 중 문장 단계 요청, `driveIndexOff`에서 kfind 질의.
에이전트용: Python 로그에 `search_id·channel·phase·rust_ms·total_ms` 한 줄(측정·회귀 비교).

### 실기 확인 절차(총괄용, S9)

1. 시험 PC에 kfind 설치(UAC 1번) → 재부팅 → 앱 켜자마자 파일명 찾기 상태가 `ready`인지.
2. 파일명 모드에서 "예산집행"을 한 글자씩 친다 → 글자마다 드라이브 전체 결과가 바뀌고 멈춤이 없다(화면 녹화로 글자→목록 변화 **50ms 이하**). "예산 집행"으로도 같은 파일이 보인다.
3. 탐색기에서 새 파일 `IS1확인_예산집행.txt`를 만든다 → **1초 안에** 검색 결과에 나타난다.
4. 본문 모드에서 "예산 집행 계획"을 친다 → 문장 하나에 세 낱말이 모두 있는 문서만, 위계 순으로 **250ms 안** 완성. 서로 다른 문장에 흩어진 문서는 나오지 않는다(사본 문서로 미리 준비).
5. 본문 검색 도중 다른 단추(달력·정렬)를 누른다 → 즉시 반응.
6. kfind 서비스를 멈춘다 → 화면에 대체 표시가 뜨고 파일명 검색은 지금 방식으로 계속 된다.
7. 합격: 1~6 모두. 하나라도 어긋나면 Python 로그의 `search_id·channel·phase·rust_ms·total_ms` 줄을 첨부해 보고.

## 5. 남은 사용자 결정

- **Q9 결과에서 뺄 곳**: 드라이브 전체 색인에 다른 사용자 프로필(`C:\Users\<다른 사람>`)·`$Recycle.Bin`·`System Volume Information`의 이름도 들어갑니다. 결과에서 빼도 됩니까? 숨김·시스템 파일은 기본으로 감출까요? (기본: 셋 다 빼고, 숨김·시스템 파일은 감추되 설정에서 켬. `C:\Windows`는 결과에 포함)
- **Q10 서비스 설치 시점**: 처음 파일명 찾기를 열 때 "드라이브 전체에서 찾기 켜기" 단추로 UAC 1번(기본) / 앱 설치할 때 바로(설치기가 지금은 관리자 없이 깔리는 방식이라 설치 때 UAC 창이 새로 생김) 중 어느 쪽입니까?
- **Q11 크기·날짜 열**: 드라이브 전체 결과에서 크기·수정 날짜로 정렬해야 합니까? (기본: 1차는 보이는 줄만 표시하고 정렬은 안 됨. 정렬이 필요하면 원시 `$MFT` 해석 단계를 더하고 메모리가 항목당 약 16B 늘어남 — 100만 항목 약 +16MB)
- **Q12 파일명 결과 순서**: 이름 완전 일치 > 앞부분 일치 > 그 밖, 같은 등급은 경로 짧은 순으로 해도 됩니까? (기본: 예)
- **Q13 짧은 낱말 섞임**: "예산 및 집행"처럼 1글자 낱말이 섞이면 그 낱말은 본문 일치에서 빼고 화면에 알려도 됩니까? (기본: 예. 넣으면 1글자 조각 색인이 필요해 색인이 커지고 느려짐)
- **Q14 공용 파이프 크레이트**: klib·kagent·kvf·kfind의 파이프 서버 코드를 작은 공용 크레이트로 뺄까요? (기본: 이번에는 kfind만 새로 쓰고, kvf 작업이 끝난 뒤 별도 카드로 묶음 — 진행 중인 kvf 브랜치와 충돌 피함)
- **Q15 `~N` 근접 문법**: 문장 규칙(Q3)과 겹치므로 폐지해도 됩니까? (기본: 폐지. `"구문"`·`-제외`·`ext:`·`path:`·날짜는 유지)
- **Q16 문장 색인 디스크 사용**: 문장 색인이 3,000문서 약 30~40MB, 3만 문서 약 0.4GB(추정) 더 씁니다. 괜찮습니까? (기본: 예. 줄이려면 위치 없는 방식으로 바꾸고 검색이 다소 느려짐 — S5 실측으로 차이 보고)
