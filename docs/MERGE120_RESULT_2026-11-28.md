## 병합하며 찾아 고친 것

1. **통합 검색에서 폴더 이름 결과가 사라짐.** 통합 검색(앱 통합 보기, 퀵몽땅검색 `unified_search`)은 파일명 질의에 늘 `file:` 을 붙였다. v2.2.119 의 폴더 이름 검색이 통합 검색을 켜면 없어졌다.
   - 파일 질의는 그대로 두고 `folder:` 질의를 따로 보낸다(`unified::fetch_names`). 파일명 단에서 폴더가 먼저 나온다.
   - 종류(확장자)를 고르거나 `ext:` 를 쓰면 폴더를 묻지 않는다.
   - 앱: '폴더' 꼬리표, 열기는 그 폴더를 열고 미리보기는 부르지 않는다. 서비스 `open`/`reveal` 은 조사 폴더 안의 폴더를 받는다(제외·점 폴더, 정션 밖 연결은 거부).
   - **동작 변경**: UNIFIEDAPP1 결과 문서의 '통합 보기에는 폴더 항목이 없다'는 더 이상 맞지 않는다. 통합 보기는 기본 끔 그대로다.
   - 비용: 통합 검색마다 파일명 질의가 최대 하나(조사 폴더마다) 늘어난다. 측정하지 않았다.
2. **앱 통합 보기의 연관 검색(`;`)에서 파일명 단이 늘 0건.** 호스트가 `file:` 을 붙여 보냈는데 서비스의 연관 질의 문법은 이를 낱말로 읽는다. 입력을 그대로 보내고 범위는 받은 뒤 거른다(퀵몽땅검색 창과 같은 방식). 합성 색인의 실제 질의 엔진으로 확인: 연산자 없이 2건, 붙이면 0건. 기존 `app_host` 시험의 가짜 파이프는 이를 드러내지 못했다.
3. **Python 색인 클라이언트가 시험 중에도 설치된 서비스 파이프에 연결할 수 있었음.** `KfindClient()` 기본값에 차단이 없었다. `DOCFIT_FORBID_REAL_DATA=1` 이면 기본 파이프를 열지 않는다(따로 준 파이프는 연다). 색인 초기화가 앱 문서를 지우게 된 뒤라 위험이 커졌다.
   - 이번 실행에서 Python 시험은 이 차단을 넣은 뒤에만 돌렸다. **이전 작업(INTEG119 등)의 시험이 설치 서비스에 닿았는지는 확인하지 못했다.**

## 남은 문제·미확인

- **[기존 문제, 고치지 않음]** 앱 3탭 '이름 찾기'의 검색 결과(`file_search`)에 항목 번호와 `folder` 가 없다. 표에서 열기(`{'id':0}`)·미리보기가 실패하고 경로 칸이 비는 것으로 보인다. v2.2.119 의 폴더 결과도 같다. 코드 확인만 했고 재현하지 않았다.
- 설치본·설치 서비스·실제 화면·다크 테마 실기·IME·한/글 COM 시험은 하지 않았다. 전체 `unittest discover`, CI(MSVC) 빌드도 돌리지 않았다.
- 폴더 결과는 설치된 색인 서비스의 실제 색인으로 확인하지 않았다. MFT 색인의 폴더에 수정 시각이 없으면 기간을 고른 검색에서 빠진다(코드 추정).
- 입력에 `folder:` 를 직접 쓰면 통합 검색은 폴더와 파일을 함께 보인다(파일 질의의 `file:` 이 뒤에서 이기는 기존 동작).
- 연관 검색(`;`)의 폴더는 서비스 연관 질의가 돌려주는 그대로이며 폴더 우선 정렬을 하지 않는다.
- INTEG119·QMSDARK1 결과 문서의 남은 문제는 그대로다. 파일명 단에는 `names_snapshot` 을 아는 새 서비스가 필요하다.
