# DOCDBPERF1 — 문서뷰 배경 비교 비용 (2026-11-27)

## 판정

- **미사용 확인 시각의 전체 행 재저장만 생략하는 개선을 채택한다.** 전후 각 3회, 2원천×3상황으로 각각 18회 측정했다. 재열기·1% 변경 완료 시간은 네 조건 모두 전후 범위가 겹치지 않는다.
- **첫 열기 개선은 확인하지 못했다.** 모의 서비스·klib 모두 전후 범위가 겹친다. 첫 DB 삽입·원천 읽기·목록 전달은 그대로 두었다.
- 18쌍 모두 최종 목록·변경분·DB 행의 해시가 일치한다. 1% 변경은 수정 260·추가 195·삭제 195이며 삭제 안전 조건을 유지한다.
- 기존 관련 시험 167개와 신규 2개: `Ran 169 tests` / `OK (skipped=1)`. Rust 변경은 없으므로 `cargo test` 대상 크레이트도 없다. 전체 Python·실제 설치본 검증은 하지 않았다.
- 기능 브랜치 `feature/DOCDBPERF1`, 기준 `e038ec73`. 로컬 커밋만 수행하며 푸시·태그·게시·설치·자동 실행·사용자 설정 변경은 하지 않는다.

## 측정 조건

새 도구 `scripts/bench_docdbperf1.py`로 빈 합성 PDF 65,000개를 650폴더에 만들었다. 파일명·초기 크기·수정 시각을 고정하고 1% 변경 뒤 복원하여 두 코드가 같은 합성 자료를 읽는다. 각 반복·원천마다 DB를 새로 만들고 첫 열기 → 저장 목록 재열기 → 1% 변경 순서로 실행했다. 파일 준비·모의 색인 준비·결과 검증은 측정에서 제외한다. 준비용 16스레드는 생성 완료 후 모두 종료하며 측정은 순차 실행한다.

- Windows, 앱 개발 가상환경 Python 3.14.0 / SQLite 3.50.4. 작업 사본에 `.venv`가 없어 공유 개발 저장소의 `.venv` 인터프리터로 현재 사본을 실행했다. 앱 버전·설정은 바꾸지 않았다.
- `service`: 이미 준비한 path/name/ext/size/mtime/cloud를 즉시 전달하는 **모의 원천**. 신형 서비스 메타데이터 재사용 비용을 재며 실제 파이프·서비스 응답 시간은 포함하지 않는다.
- `klib`: 동일한 개발용 release 실행 파일의 실제 합성 폴더 스캔. 실행 파일 SHA-256은 원시 결과 JSON에 기록했다. 설치된 실행 파일은 사용하지 않았다.
- 화면과 같이 `list_default` → 120ms 간격 `scan_progress(since)` 호출, 4,000행씩 수신·JSON 변환/해석·변경분 적용. 실제 Flutter/WebView 렌더링 시간은 포함하지 않는다.
- 기본 루트·썸네일·DB·이전 캐시 위치는 전부 합성 폴더로 지정한다. `DOCFIT_FORBID_REAL_DATA=1`과 원천 대체로 설치된 서비스·사용자 문서·사진·DB에 접속하지 않는다. COM은 호출하지 않았다.
- 다른 Rust 빌드가 있던 때는 파일 준비만 진행했다. 판정 측정 중 별도 시험·빌드는 실행하지 않았다. 재부팅·다른 앱 종료·전원 설정 변경은 하지 않았으므로 실제 사용 환경 전체를 통제한 수치는 아니다.
- 과거 DOCDB1의 1.1→3.7 / 5.2→10.2초는 다른 회차·메타데이터·측정 조건이다. 아래의 현재 기준선과 직접 차감하지 않는다.

## 원인과 수정 범위

`ViewSync.finish`가 추가·변경·삭제 외에도 `_seen` 전체를 넘겨 `UPDATE items SET seen_at=...`를 실행했다. 재열기만 해도 65,000행을 다시 쓰고, 1% 변경에서도 실제 변경 455행 외에 나머지 확인 행을 갱신했다. 저장 시간에는 JSON 준비와 SQLite 트랜잭션·WAL 반영·연결 종료 비용이 포함되며 이를 디스크 대역폭 또는 특정 SQLite 내부 동작만의 비용으로 단정하지 않는다.

저장소 전체 검색에서 `seen_at`의 소비자는 없고 스키마·쓰기 코드만 있었다. 삭제는 DB 시각 대신 해당 회차의 메모리 `_seen`과 디스크 확인으로 판단한다. 따라서 `finish`에서 `seen=` 전달만 제거했다. 공용 `LibraryDB.write(seen=...)` API와 스키마는 호환성을 위해 유지한다. **`seen_at`은 이제 이 흐름에서 행을 추가·변경 저장한 시각이며, 변경 없는 재확인마다 갱신되지 않는다.** DB 파일 전체 바이트 동일성을 주장하지 않는다.

변경 없는 재열기는 실제 SQL 쓰기 0건이다. 1% 변경은 455행 upsert와 195행 삭제만 저장한다. 첫 열기는 여전히 65,000행 삽입이 필요하다. `feed`·`publish_snapshot`·폴더 확인·원천 선택·목록 정렬·브리지·Rust 코드는 바꾸지 않았다. 별도 행 비교·SQL 삽입 최적화는 추가하지 않았다.

## 결과와 상태 전이 보존

흐름은 기존의 저장 목록 발행 → 원천 행 비교 → 마무리(추가·변경·삭제 저장) 그대로다. 마무리에서 미변경 행의 DB 갱신만 빠진다.

| 조건 | 유지한 동작 |
|---|---|
| 완전하고 비지 않은 원천 | 확인 집합 밖이고 연결된 루트 아래이며 실제 디스크에도 없는 항목만 삭제 |
| 취소·실패·부분 결과·빈 원천 | 삭제 금지, 찾은 추가·변경만 저장 |
| 색인에서 누락됐지만 디스크에 있음 | 보존 |
| 빠진 드라이브·확인 불가 | 보존 |
| 제외 폴더·클라우드 전용 | 기존 표시·보관 규칙 유지 |
| 파일 작업과 비교가 겹침 | forget/adopt 및 되살림 방지 유지 |
| 구형·누락·미상 메타데이터 | 폴더 확인 폴백 유지 |

합성 18쌍의 최종 정렬 목록(모든 공개 필드), 경로/op로 정렬한 이벤트, `LibraryDB.load()`의 8필드 해시를 각각 대조해 전부 일치했다. 경로는 합성 루트 기준으로 상대화했으며 의도적으로 갱신을 생략한 `seen_at`은 해시에 포함하지 않는다. klib의 병렬 발견 순서는 보장하지 않으므로 이벤트는 정렬 후 대조한다. 첫 열기 추가 65,000 / 재열기 변경 0 / 1% 변경 추가 195·수정 260·삭제 195를 별도로 확인했다.

## 시험·실패 시도·한계

신규 `tests.test_docdbperf1` 2건은 변경 없는 완전/부분 확인에서 DB 바이트가 바뀌지 않는지, 변경분만 저장하면서 부분·빈 원천의 삭제 금지와 디스크에 남은 파일 보존이 유지되는지 검사한다. 기존 시험은 수정하거나 약화하지 않았다.

기존 합성 실행기 `scripts/test_merge110_synthetic.py`의 16모듈에 신규 모듈을 추가했다. 사진 DB·EXIF·목록·FILEOPS·열기·제외·메타데이터·서비스 폴백·손상·취소·썸네일 관련 169개다. 실행기가 기존 공개 HWP fixture 입력을 메모리에서 만든 합성 CFB/PNG로 대체하며 기존 단언과 실제 klib 동작은 그대로다.

앱 가상환경에서 `KLIB_EXE`를 개발용 실행 파일로, `TEMP`·`TMP`를 저장소 밖 합성 임시 폴더로 지정한 뒤 실행한다.

기존 실제 휴지통 시험 1건은 원래 조건으로 제외됐다. 최초 실행은 `Ran 169 tests in 40.098s` / `OK`인데 PowerShell 오류 출력 리다이렉션의 셸 반환이 1로 기록되어, 종료 코드를 명시하는 동일 시험으로 위와 같이 최종 종료 코드 0을 확인했다.

준비 중 순차 파일 생성은 너무 느려 측정 시작 전 두 차례 중단했다(유효 측정 0건). 생성만 병렬화하고 같은 합성 자료를 복원·재사용하도록 도구를 보완했다. 신규 시험 초기에는 시험 코드의 SQLite 연결 미종료 및 현재 시각의 JSON 정밀도 비교로 실패해 연결을 명시적으로 닫고 합성 시각을 고정했다. 제품 코드 우회나 기존 시험 변경은 하지 않았다.

실제 설치 서비스의 응답 지연·설치본 UI·사용자 규모와 다양한 파일 분포는 미확인이다. 빈 PDF의 메타데이터 목록 측정이며 실제 문서 파싱·썸네일 생성 성능을 뜻하지 않는다. 실제 서비스·사용자 문서·사진·DB 사용은 이번 금지 범위라 실행하지 않았다. 첫 열기의 DB 삽입 비용과 service의 1% 변경분 도착 지연은 남아 있다.
