# HS2-J 제목+본문 검색 지연 조사 (2026-11-12)

## 범위 및 방법

`scripts/benchmark_hs2_hsa.py`를 그대로 사용했다. 지정 Python(`C:/HWP_AUTODOCFIT/v1803/exfile/.venv/Scripts/python.exe -X utf8`), SQLite 합성 색인 300문서 × 40문단, 질의 10개, 질의별 예열 1회 후 5회 중앙값, 10개 중앙값이며 기본 `limit=100`이다. 부모는 `16c03725^`인 `09f261bf`, 후는 작업 시작 HEAD `5a0cb63e`다. 두 worktree에서 같은 스크립트를 사용했고 부모/후를 교차해 3회 측정했다.

## 재현값

교차 측정의 전체 중앙값(ms):

| 반복 | 부모 09f261bf | 후 5a0cb63e |
|---:|---:|---:|
| 1 | 108.296 | 127.913 |
| 2 | 117.933 | 148.323 |
| 3 | 117.933 | 132.841 |

각 3회 값의 중앙값은 부모 **117.933ms**, 후 **132.841ms**로 후가 **12.64% 느리다**. 절대 측정은 변동이 컸다. 동일 코드 후속 측정도 115.871ms 및 129.156ms가 나와, 단일 회차 수치보다는 교차 반복 중앙값을 대표값으로 삼았다. 기존 HS2-H 보고의 115.958→131.879ms(+13.73%) 방향과 유사하다.

## 병목 계측

`cProfile`로 직접 일치 질의 1개를 계측했다(총 0.179초). SQLite `execute` 누적 0.097초, `fetchall` 0.026초, Python `hierarchy_path.breadcrumb` 100회 누적 0.004초였다. 이는 전체 질의 프로파일이며 각 SQL 단계별 독립 타이밍은 아니다. 자료로 보면 조상 계산은 주요 비용이 아니며 SQL/행 회수 비용이 더 크다. `search()` 내부는 문맥 후보 문단 전체 조회 외에도 선택 결과의 breadcrumb용 문단 조회를 따로 수행한다.

## 시도 및 결론

직접 일치 문서 수가 `limit` 이상이면 문맥 후보 계산을 건너뛰는 안전 조건을 잠정 적용해 보았다. 이 합성 데이터에서 실행 중앙값 132.252ms로 개선이 관찰되지 않았고, 연속한 원본 코드 측정의 편차 범위 안이었다. 따라서 이 코드 변경은 되돌렸다. 최종 작업 트리에는 검색 구현 변경이 없다.

추가한 `test_context_search_results_match_across_all_synthetic_queries`는 동일 합성 자료와 질의 10개에서 전체 limit(500) 결과를 확인하며 반환 수, 순위 연속성, 선택 문단의 snippet 및 breadcrumb/context_hits 필드를 검증한다. 구현 변경이 되돌려져 이 시험은 현재 결과의 전량 회귀 기준을 제공한다.
