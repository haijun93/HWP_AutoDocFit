# IS-S1 본문 문장 검색 엔진 비교: Tantivy 대 직접 구현(fst + roaring) (2026-11-12)

작업: `feature/instant-search`. 앱 코드(klib·Python·화면)는 고치지 않았다. 시제품은 독립 크레이트 `kfind/engine-bench/`(앞으로 만들 `kfind/` 파일명 서비스 크레이트와 겹치지 않게 하위 폴더), 원자료는 [JSON](IS_S1_ENGINE_COMPARE_RAW_2026-11-12.json).

## 결론(권고 하나)

**(B) 직접 구현(조각 사전 fst + 문장 번호 roaring 비트맵 + 비교형 원문 확인)을 채택할 것을 권고한다.**

근거:
1. **속도(제1목표)**: 같은 자료·같은 결과에서 B가 흔한 질의에서 3~6배 빠르다. 3만 문서(120만 문장) "예산 집행" 상위 20 p50 **A 17.34ms / B 3.06ms**, 전체 p95 **A 20.97ms / B 6.87ms**. 가장 흔한 "예산"(문장 40%)도 전체 p95 A 33.65 / B 12.65ms. 입력 흉내 글자 하나당 최악 p95도 B가 낮다(아래 표).
2. **정확도**: 두 엔진 모두 Python 전수 기준 구현과 문장 집합·문서 순위가 완전히 같다(규모별 46건 × 2규모, 불일치 0). 정확도로는 우열 없음.
3. **IS-QCACHE 설계와 맞음**: 캐시 단위가 "낱말별 일치 문장 비트맵"이고 삭제는 "살아 있는 문장 비트맵과 교차"다. B는 결과 자체가 roaring 비트맵이라 그대로 쓰인다. A는 결과를 매번 비트맵으로 바꿔야 해서 재사용 모드가 오히려 느려지는 경우가 있었다(붙여쓰기 입력 30k: 새로 찾기 21.00 → 재사용 27.61ms).
4. **라이선스**: B의 실행 의존성(fst·roaring·memmap2·memchr)은 모두 MIT/Apache 계열. Tantivy는 BSD-3(zstd·zstd-safe·zstd-sys·frostem)과 Zlib(foldhash)을 끌어온다(아래 표). "MIT/Apache만" 기준을 글자 그대로 적용하면 A는 그 기준에 맞지 않는다(다만 klib이 이미 tantivy 0.27을 쓰고 있다 — 기존 상태이며 이번에 바꾸지 않음).

B의 대가(S5에서 해결해야 함, 사용자 결정 아님):
- **디스크가 2.2배**: 3만 문서 A 123.6MB / B 269.4MB. 주로 비교형 원문 사본(`fold.bin` 129.6MB, 4글자 이상 낱말 확인용)이다. 줄이는 방법: 원문을 SQLite 문단에서 읽기(느려짐 측정 필요), 원문 압축, 또는 4글자 이상도 조각 위치 비트맵으로 확인. 계획 Q16 추정(0.4GB)보다는 작다.
- **증분 갱신·삭제·병합·충돌 안전을 직접 만들어야 한다**(Tantivy는 기본 제공). 시제품은 한 번에 새로 만드는 방식만 있다. 권고 구조: 추가 전용 조각(세그먼트) + 살아 있는 문장 비트맵 + 백그라운드 병합, 파일 교체는 임시 파일→이름 바꾸기.
- 색인 시간은 둘이 비슷하다(아래, 측정 흔들림 큼).

## 측정 조건

- Windows 11 10.0.26300, rustc 1.99.1(windows-gnu, release·LTO), Python 3.14.0. 한 번 실행, 측정 중 다른 빌드·시험 없음. 디스크 캐시 비우지 않음.
- 자료: S0 `scripts/benchmark_is1.py`의 생성기·seed 7을 그대로 써서 같은 난수 순서로 만든 3,000문서×40문단(12만), 30,000문서×40문단(120만). 앞 3,000문서는 S0 자료와 같은 글이다. S0 문단은 모두 마침표 하나로 끝나는 12어절 문장이라 **문단 = 문장**(문장 나누기 규칙을 적용했지만 한 문단이 한 문장으로 나뉨). 위계 순위는 모두 8, 날짜도 모두 같다(순위의 위계·날짜 비교가 사실상 시험되지 않음).
- 질의 규칙: 공백으로 낱말을 나누고, 비교형 = 소문자화 + 글자·숫자만 남김(공백·문장부호 제거), 2글자 미만 낱말 제외(Q8), 같은 문장에 모든 낱말(Q3), 문서 순위 = 가장 높은 위계 > 일치 문장 수 > 문서 번호(Q4, 날짜 생략).
- 지연: 프로세스 안 첫 질의 1회(`first`) 뒤 반복 20회의 중앙값/p95(nearest-rank). "상위 20" = 일치 문장 계산 + 문서별 모으기 + 상위 20 부분 정렬. "전체" = 일치 문장 계산 + 모든 문서 정렬 + 문장 번호 목록 만들기.
- 정확도: `bench.py`의 Python 전수 기준 구현(문장마다 `all(w in fold(s))`)과 문장 수·문장 번호 지문(FNV-1a)·전체 문서 순위 지문·상위 20 목록이 모두 같은지. **S0의 현행 Python `keyword_search` 결과와는 비교하지 않았다** — 현행은 문단 단위·공백 비교형 없음·상위 100개 자름·bm25 순위로 규칙이 달라서 같을 수 없다. 대신 같은 S0 말뭉치에 새 규칙을 적용한 기준 구현과 비교했다.

엔진 구성:
- (A) Tantivy 0.27.0(klib과 같은 판): 문장 = 문서. 비교형 글을 `bi`(2글자 조각, 위치 없음)·`tri`(3글자 조각, 위치 포함) 두 필드로 색인. 낱말 2글자 → bi 용어, 3글자 → tri 용어, 4글자 이상 → tri 조각 구문 질의(0,3,6…와 끝 위치로 덮음). 점수 계산 없는 수집기가 `sid` 빠른 필드를 읽음. 쓰기 4스레드·200MB, 커밋 뒤 한 조각으로 병합.
- (B) 직접 구현: 비교형 2·3글자 조각 → roaring 비트맵, 조각 사전 fst(조각 → 비트맵 위치), 비트맵·비교형 원문은 mmap. 2·3글자 낱말은 비트맵 하나가 정답, 4글자 이상은 3글자 조각 비트맵 교집합 후보를 비교형 원문에서 `memchr::memmem`으로 확인. 낱말 여러 개는 작은 비트맵부터 교집합.
- 재사용(입력 흉내): ① 앞 질의 낱말이 새 질의 같은 자리 낱말에 모두 포함되면(글자 덧붙임·낱말 추가) 앞 결과 비트맵 안에서 바뀐 낱말만 판정 ② 낱말별 일치 비트맵 캐시. 두 엔진 같은 구조, 모든 단계에서 재사용 결과 = 새로 찾은 결과 확인.

- A는 재사용으로 띄어쓰기 순서가 거의 절반이 됐다(30k 197 → 103ms). Tantivy 질의 자체가 비싸서 낱말 캐시 적중 효과가 크다.
- B는 질의가 이미 비트맵 몇 개의 교집합이라 재사용 이득이 없고 앞 결과 복제 비용만큼 비슷하거나 약간 느리다. B에서는 앞 결과 재사용을 기본으로 켤 필요가 없고, 낱말 비트맵 캐시만 두면 된다(IS-QCACHE 6항 "색인이 이미 목표 안이면 비트맵 캐시만"과 일치).
- 어느 쪽이든 글자 하나당 백엔드 최악 p95가 37ms 이하(30k)로, 계획의 "입력마다 취소" 없이도 따라잡는다. 다만 화면 목표에는 Python 중계·그리기가 더해진다(S4·S8에서 측정).

## 실패 기록

- 첫 본 측정 실행에서 30k Tantivy 색인이 `writer.merge`에서 "merged segments could not be found" 오류로 끝났다. 기본 병합 정책이 백그라운드에서 이미 조각을 합쳐 명시적 병합이 사라진 조각 번호를 가리켰기 때문이다. `NoMergePolicy`로 바꾸고 커밋 뒤 한 번만 병합하도록 고쳤고, 그 실행의 3k 결과는 버리고 두 규모를 처음부터 다시 한 번 쟀다. 구동기는 실패 때 stderr를 남기고 규모마다 결과를 저장하도록 고쳤다.

## 남은 문제·확인 못 한 것

- 합성 자료 한계: 낱말 24개라 조각 7,801개, 문단 = 문장, 위계·날짜가 모두 같음. 실제 문서(조각 수십만, 긴 문단·표·개조식)에서 두 엔진 차이가 유지되는지 미확인. S5 전에 실제 색인 사본으로 B만이라도 다시 잴 것.
- B의 증분 갱신·삭제·병합·충돌 안전·동시 읽기는 구현·측정하지 않았다(A는 Tantivy가 제공). 이것이 B 채택의 주 비용이다.
- B 디스크 2.2배(비교형 원문 사본). 줄이는 방식 비교 미실시.
- NFC 정규화 미적용(합성 자료는 이미 NFC). Rust `is_alphanumeric`과 Python `isalnum`은 일부 결합 문자에서 다를 수 있다 — 합성 자료에는 없음. S5 비교형 규칙 확정 때 둘을 맞출 것.
- 위계 경로 붙이기·`ext:`/`path:`/날짜 거르개·`"구문"`·`-제외`, 취소(세대 번호), 다중 스레드 질의, 차가운 디스크 캐시, Python 중계·화면 지연은 재지 않았다.
- 색인 시간의 흔들림이 크다(3k B 9.6초 대 23.1초). 우열 판정에서 뺐다.
- Docufinder와의 같은 자료 비교는 하지 않았다(사용자 승인 필요 항목).
