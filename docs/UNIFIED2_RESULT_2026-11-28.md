# UNIFIED2 — 몽땅검색 전역 단 배정·이어보기

기준 `be87c53f`, 작업 브랜치 `feature/UNIFIED2`. 전역 배정과 이어보기를 구현했다. 최종 첫 표시 중앙값은 **20.7169 / 17.7589ms로 16ms 목표 미달**이다. `unified_search=false`를 유지하며 기본값 승격은 보류한다. 설치본·설치 서비스·자동 실행·사용자 설정·사용자 색인·사용자 문서·기존 실행 앱은 변경하지 않았다. 로컬 커밋만 하며 푸시·태그·릴리스·main 병합은 하지 않는다.

## 구현과 검색 의미

- 변경 크레이트는 `ktm`, `kfind-names`, 서비스 `kfind` 3개다. `kfind-core`·Python·Flutter·제품 버전·설정 기본값은 변경하지 않았다.
- `ktm::backend::unified::collect`는 첫 파일명 20개를 먼저 발행하고, 후보 절단 없는 파일명·위계·본문 응답으로 전역 세션을 만든다. 기존 `merge`/`stream`은 기존 후보 계약의 호환 API로 남기고 실제 통합 창은 새 경로를 쓴다.
- 파일명 서비스에 별도 `names_snapshot` 명령을 추가했다. 기존 `names_query`/`names_related`의 1,000개 상한은 그대로다. 새 명령은 같은 SID 제외 규칙·검색기·순위를 사용해 전수 결과를 반환한다. 클라이언트는 `complete=true`와 `total == items.len()`을 확인한다. 구 서비스·잘린 응답·8MiB 전송 한도·시간 초과를 전수 성공으로 오인하지 않는다. 설치 서비스는 교체하거나 호출하지 않았다.
- 본문 `Backend::search_snapshot`은 `top=0` 전수 계약을 사용하고 wildcard의 부분 결과는 오류로 처리한다. 기존 공개 bounded API의 200개 상한은 그대로다. 일반 전수 조회에서는 후보별 발췌 선행 조회를 하지 않고 화면의 기존 지연 발췌 경로를 쓴다. AnyTerm 전수 동점은 문서 ID로 안정화한다.
- 경로의 대소문자·슬래시·확장 경로·ID 별칭을 기존 정책으로 정규화한다. 전수 집합에서 파일명 > 위계 > 본문 하나에만 배정하므로, 상위 단의 201번째·1,001번째 이후 문서도 하위 단으로 재등장하지 않는다. 동명 다른 폴더는 보존한다.
- `Session::page(Cursor, limit)`는 단별 커서 3개를 사용한다. 페이지마다 20/20/40까지, 전체 최대 80개를 내고 **실제로 낸 수만큼만** 커서를 이동한다. 전체 상한이 1·7·20·39일 때도 누락 없이 이어진다. 마지막은 `next=None`이다. 같은 커서 재호출은 같은 페이지를 돌려주므로 이전 보기가 가능하다.
- 모든 페이지와 증분 응답에 기존 강조어·묶음·원천의 폴더 집계·자동완성 메타데이터를 보존한다. 최종 검토에서 이 필드들의 계승 누락을 보완하고 전수 대조 시험에 페이지별·부분 실패 응답 보존 검증을 추가했다. 전역 문서 개수의 기준은 `Page.totals`다.
- 실제 창에서 Ctrl+PgDn 이어보기, Ctrl+PgUp 이전 보기를 연결하고 하단에 안내한다. 새 페이지는 세대를 올려 이전 페이지의 늦은 발췌 응답을 막는다. 새 질의·숨김은 세션을 해제한다. 기본값 false 경로는 기존 세 검색 작업을 유지한다.
- 상태는 첫 파일명 발행 → 전수 원천 수집 → `Ready` 또는 `Incomplete`다. 상위 단 전수 조회 실패 후에는 하위 단을 확정하지 않는다. 이미 확인한 상위 결과와 오류를 남긴다. 취소 확인 전후·세대 검사로 오래된 응답을 발행/적용하지 않는다.

**위계 의미는 바꾸지 않았다.** 기존 위계 검색은 제목만의 필터가 아니라 본문 일치 집합을 위계순으로 정렬하는 검색이다. 따라서 두 전수 집합이 같으면 파일명에 없는 본문 일치 문서는 모두 위계 단에 들어가며 본문 단은 빈다. 이는 후보 200개 제한 때문에 이전에는 가려졌던 결과다. 제목 전용 위계 검색으로 변경하려면 별도 검색 의미 결정이 필요하다.

pipe 모드에서도 전수 본문은 로컬 mmap의 같은 색인 루트를 사용한다. 기존 본문 파이프 명령은 전수 보증이 없으므로 그대로 전수라고 사용하지 않는다. 로컬 색인이 없는 pipe 전용 환경은 명시적 오류이며 이번에 설치·실서비스 호환을 검증하지 않았다.

## 전후 각 5회 측정

동일 seed의 합성 TXT 1,000개·파일명 색인·본문 mmap·문단 SQLite·격리 파이프를 사용했다. release 실행 파일과 `--unified-measure`만 새로 띄웠다. 설치 서비스와 기존 앱을 조작하지 않았고, 이 작업의 다른 빌드·시험을 측정과 병행하지 않았다. 다른 작업의 시스템 부하는 통제하지 못했다.

시계는 SetWindowText **직전**부터 해당 결과 GDI EndPaint까지다. DWM 실제 화면 표시·물리 키 입력·IME 조합 시간은 포함하지 않는다. 과거 UNIFIED1 단일 기록 19.768/15.844ms 대신 이번 변경 전 5회를 직접 비교 기준으로 삼는다. 이번 변경 전에는 메시지 전달 대기와 GDI 처리 지연이 크게 관측됐다.

초기 후보·키 분기 보완 후보·그리기 지연 후보도 각각 5회 측정했다. 호환성 검토에서 새 페이지 키 분기를 세션이 있을 때로 제한해 기본 경로의 Ctrl+PgDn/PgUp 기존 선택 이동을 보존했다. 이어서 첫 결과가 빈 검색 중 화면 그리기를 기다리는 구간을 줄이고 페이지 응답의 메타데이터 계승을 보완했다. 아래 최종 표는 이 수정들을 포함한 release의 별도 5회이며, 중간 후보 15회도 측정 JSON에 구분해 보존한다.

각 실행은 두 질의를 한 번씩 측정했다. 첫 파일명 행의 이름·순서·단·위치 근거는 전후 5회 모두 일치했다. 원자료에는 최종 전후 각 5회의 시간·자원 수치, 중간 후보 15회, 바이너리 SHA-256을 함께 보존했다.

| 질의 | 변경 전 첫 GDI 5회(ms) | 최종 첫 GDI 5회(ms) |
|---|---|---|
| 예산집행 | 123.2295, 108.3775, 50.1105, 101.8943, 96.1095 | 22.5055, 19.5624, 23.9646, 16.5700, 20.7169 |
| 2026; 공사 계약 | 125.1914, 133.4568, 218.3456, 123.2314, 176.4640 | 19.1985, 18.1378, 17.7589, 13.3979, 13.8950 |

| 질의 | 첫 GDI 중앙값 전 → 후 | 최종 범위 | 16ms 이하 |
|---|---:|---:|---:|
| 예산집행 | 101.8943 → **20.7169ms** | 16.5700~23.9646ms | **0/5** |
| 2026; 공사 계약 | 133.4568 → **17.7589ms** | 13.3979~19.1985ms | **2/5** |

이번 표본에서 첫 표시 지연이 줄었으나 외부 부하를 통제하지 못해 이 차이를 코드만의 효과 크기로 단정하지 않는다. 16ms 기준은 두 질의 모두 미달이다. 단발 지연 도입 전 첫 후보와 최종의 각 3회차 진단에서는 첫 결과 전달 대기가 7.5351ms / 0.5448ms였고, 최종 결과 반영·그리기 구간은 20.8770ms였다. 이는 서로 다른 실행의 진단값이며 별도 통계로 취급한다.

| 질의 | 단 합성 완료 GDI 중앙값 전 → 후 | 첫 페이지 행 수 전 → 후 |
|---|---:|---:|
| 예산집행 | 282.9598 → 63.2732ms | 80 → 40 |
| 2026; 공사 계약 | 481.0019 → 56.5666ms | 4 → 4 |

예산집행은 전역 위계 배정으로 첫 페이지가 달라졌다. 두 번째 질의는 UI 덤프의 이름·순서·단·위치 4개가 일치했다. 완료 GDI는 단 합성 완료 시점이며 후속 지연 발췌 완료와는 구분한다. 일반 전수 조회의 선행 발췌 조건도 달라졌으므로 이 표를 동일 결과·동일 발췌 조건의 전체 속도 개선 판정에 사용하지 않는다.

| 숨김 대기 2초, 각 5회 | 변경 전 | 최종 |
|---|---:|---:|
| 개인 작업 집합 중앙값 | 2,932,736B | 2,875,392B |
| 개인 작업 집합 최대 | 2,953,216B | 2,936,832B |
| 개인 바이트 중앙값 | 3,694,592B | 3,756,032B |
| CPU 시간 증가 중앙값 / 최대 | 0 / 15.625ms | 0 / 0ms |

대기 개인 작업 집합은 5회 모두 기존 5MB 목표(5,000,000B) 이내다. 이는 합성 1천 문서·2초 대기의 관측값이다. 대량 자료 검색 중 최대 메모리와 장시간 누수는 확인하지 않았다.

첫 파일명 요청 상한을 200 → 20으로 줄여 직렬화·디코딩·합성 대상을 줄였다. 이미 파일명 첫 화면을 발행한 경우 같은 파일명 중간 화면을 다시 그리지 않는다. 일반 전수 후보의 불필요한 발췌 선행 조회와 전수 Row 복제를 줄였고, 이름 전수 정렬의 순차 삽입을 한 번 정렬로 바꿨다. 첫 표시와 전수 정확도 계산 비용은 별도로 판단한다.

통합 입력에서는 빈 검색 중 화면의 그리기만 단발 10ms 타이머로 미룬다. 빠른 파일명은 도착 즉시 타이머를 해제하고 바로 그린다. 느린 원천에서는 타이머가 한 번 검색 중 화면을 표시하며 새 입력·결과·숨김에서 해제된다. 입력 EDIT와 측정 시계는 그대로다. 숨김 뒤 상주 타이머는 추가하지 않았다.

| 첫 표시 | 두 대표 질의 전후 각 5회, 변경 후 5회 모두 16ms 이하. 같은 첫 파일명 문서·순서 대조 | **미달**: 0/5, 2/5. 중앙값 20.7169 / 17.7589ms. 물리 입력·IME 미확인 |

**기본값은 false 유지.** 합성 전수 정확도 통과만으로 승격하지 않는다. 16ms, 동일 결과 전체 지연, 대량 자료 자원, 실제 서비스·IME·장시간 대기가 함께 충족되어야 한다.

## 2단계 앱 화면에서 같은 결과를 사용하는 호출 설계

공통 결과 원천은 공개 Rust API `ktm::backend::unified::{collect, Session, Cursor, Page, SessionState}`다. 화면에서 다시 최고 단을 계산하거나 페이지마다 검색을 재실행하지 않는다.

```rust
let session = unified::collect(limit, &cancel, fetch_complete_sources, publish_part)?;
let page = session.page(unified::Cursor::default(), limit)?;
// page.answer.rows: 표시할 문서, match_kinds는 최고 단 하나
// page.totals: 단별 전역 개수, page.next: 다음 커서 또는 None
let next_page = page.next.map(|cursor| session.page(cursor, limit)).transpose()?;
```

`fetch_complete_sources(kind, top)`의 top=0은 전수 보증이다. 파일명은 일반/연관 선택과 `names_query`의 범위 변환을 공유하고 전수일 때 `pipe_names_snapshot`, 본문은 같은 범위·match_mode로 `Backend::search_snapshot`을 호출한다. 첫 파일명(top≤20)은 기존 상한 API를 쓴다. 일반·연관 문법을 섞거나 단 사이 낱말을 합쳐 AND하지 않는다.

WebView 앱은 Rust 라이브러리를 직접 가져올 수 없으므로 Rust 호스트의 JSONL stdio 명령을 Python 브리지로 감싸는 방식을 권고한다. 이번에는 설계만 하며 앱 화면·브리지·상주 프로세스는 추가하지 않았다.

| 요청 | 호스트 동작·응답 |
|---|---|
| `unified_start {generation, query, scope, match_mode, related_queries, sort, limit}` | 기존 활성 요청 취소·세션 해제, collect 실행. `unified_part {generation, completed, answer, errors, final_part}`로 증분 발행. answer에는 rows·terms·groups·folder_counts·autocompletes를 함께 전달. 완료 시 `session_id`, `state`, `totals`, 첫 페이지, opaque `next_cursor` 반환 |
| `unified_page {session_id, cursor_id, limit}` | 저장한 같은 Session의 page 호출. 같은 커서는 같은 결과. 처음·이전 커서는 호스트가 세션별로 보관 |
| `unified_cancel {generation}` | 취소 플래그 설정. 취소 후 늦은 part 폐기. 페이지의 지연 발췌도 별도 페이지 세대로 대조 |
| `unified_close {session_id}` / 숨김 / 연결 종료 | 세션·커서·원천 핸들 해제. 사용자 설정이나 색인을 쓰지 않음 |

scope에는 기간·폴더·확장자를 명시한다. 커서는 다른 세션에 재사용하지 못하게 호스트가 검증한다. 프로토콜 `limit=0`, 잘못된 세션/커서, 시간 초과·전수 기능 부재는 명시적 오류다. `Incomplete`의 개수는 확인된 상위 결과만의 개수이며 전체 검색 완료로 표현하지 않는다. 세션 생성 후 색인이 바뀌어도 페이지는 같은 순서를 유지한다. 수집 중 두 서비스 사이의 원자적 동시 스냅샷 및 실시간 색인 교체는 이번 검증 범위 밖이다.

## 미확인·후속

- 설치 서비스 교체·실제 계정별 색인 권한·실제 드라이브/사용자 문서·IME·DWM·물리 단축키·장시간 대기·대량 색인 최대 메모리·Mac/MSVC/CI는 미확인이다.
- 제목 전용 위계 검색 여부는 검색 의미 결정 사항이다. 현재 위계 전수 집합과 본문 전수 집합이 같은 경우 본문 단이 비는 동작을 구현 결함으로 숨기지 않는다.
- 전체 Python 시험은 이번 범위에 넣지 않고 관련 모듈만 실행한다. 앱 화면 2단계는 위 API 설계만 제공했다.
- 표시 정렬·버전 묶기·후처리 필터는 기존처럼 현재 페이지에 적용한다. 모든 페이지를 다시 배치하는 정렬 전환과 연관 검색의 모든 범위 조합별 실창 검증은 이번 범위 밖이다.
