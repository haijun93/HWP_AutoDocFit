# SRCH4 결과 — Rust 몽땅검색엔진 4단계 (배치 색인·질의 의미 일치·상태 계약)

- 기준 커밋: `15d8399e`(SRCH3), 작업 브랜치 `feature/SRCH4`, 구현 커밋 `b7394307`
- 환경: Windows x64, Python 3.15.2, 합성 코퍼스 시드 `20261124`. 한/글 COM·사용자 문서 사용 없음.
- 원래 워커가 쓴 결과 문서는 한글이 `?`로 깨져(셸 인코딩 문제) PM이 손상되지 않은 숫자를 근거로 다시 작성했다. 숫자는 원문 그대로이고, 원문에서 읽을 수 없던 서술은 넣지 않았다.
- 기본 모드는 계속 `sqlite`다. 기존 API 응답은 바뀌지 않았다.

## 구현

- `klib search-content` 에 `index_batch` JSONL 요청 추가. 1~500문서를 `SearchIndex::batch()` 한 범위로 색인하고 문서별 `{indexed, error}` 를 돌려준다. Python `RustBackend` 는 250문서씩 보낸다.
- 키워드 질의는 모든 질의어 포함(AND)이 기본이고, 오타 확장(fuzzy)이 OR 로 새는 경로를 막았다. 위계 질의는 문서 단위 AND 로 맞췄다.
- 상태 계약: `document_count`(파일 수)와 `paragraph_count`(문단 수)를 분리해 Python 의 `indexed_document_count` 가 파일 수 의미가 되도록 했다.
- 오류 처리: 배치 색인 중 문서별 오류는 `error` 로 보고하고, Rust 경로가 실패하면 SQLite 로 fallback 한다.

- 1천 문서 Rust 초기 색인은 SRCH3 의 272.463초에서 3.827초로 줄었고, 같은 코퍼스의 SQLite(49.591초)보다 빠르다. 인덱스 크기는 SQLite 의 약 11%다.
- warm 질의는 1천 문서에서 SQLite 쪽이 약간 빠르거나 비슷하다(키워드 19.2 대 27.9ms). 색인 중 질의 지연은 Rust 가 훨씬 짧다.
- 1만 문서 SQLite 는 20분 상한을 넘어 측정하지 못했다. 1만 문서의 backend 간 비교는 아직 없다.

## 결과 일치도 (1천 문서, 시드 20261124)

| 질의 유형 | SQLite / Rust 일치 문서 수 | 전체 결과 집합 일치 | 상위 20 겹침 |
|---|---:|---:|---:|
| 키워드 `행정` | 1000 / 1000 | 100% | 2/20 (10%) |
| AND `행정 정책` | 994 / 994 | 100% | 0/20 (0%) |
| phrase `"행정 절차 지원"` | 1000 / 1000 | 100% | 0/20 (0%) |
| 위계 `행정 정책 문서 안전 지원` | 1000 / 1000 | 100% | 1/20 (5%) |

**일치하는 문서 집합은 같지만 순위(상위 20)는 거의 다르다.** 순위 기준이 서로 달라서(SQLite: trigram 발생 횟수 등, Rust: bigram BM25 + 문단 위계 집계) 생긴 차이로 보인다. 어느 쪽 순위가 사용자에게 더 낫다는 근거는 이번에 만들지 못했다.

## 기본 backend 승격: 불가

막는 항목:
1. 상위 순위 일치가 0~10% 라서 사용자가 보는 결과 순서가 크게 달라진다. 순위 기준을 합의하거나 Recall@k·MRR 같은 품질 평가가 필요하다.
2. 1만 문서 SQLite 기준선이 없어 대규모 비교가 안 됐다.
3. 위계 필드(breadcrumb·level), 페이지 위치, 변경 감지 hash 가 아직 Rust 색인에 없다(TODO 해당 항목).
4. 실제 한글 문서·스캔 PDF·설치본(EXE)·폐쇄망 시험을 하지 않았다.

## 시험과 남은 확인

- Rust release 빌드 성공(로컬 MinGW, `CARGO_TARGET_DIR` 은 별도 드라이브).
- 전체 Python 시험: 3,594건 실행, 28건 건너뜀, 결과 OK(워커 진행 기록 기준). 종료 때 기존과 같은 샌드박스 SQLite 파일 잠금 `PermissionError` 경고가 나올 수 있다.
- 측정 도구 `scripts/search_bench.py`, `scripts/search_compare.py` 는 Python 구문 검사 통과.
- 확인 못 한 것: 1만 문서 SQLite, 질의 순위의 사용자 관점 품질, Rust 오류·취소·재시작 경로의 실제 장애 시험.

## SRCH5 제안

1. 위계 필드(`node_id`·`parent_id`·`breadcrumb`·`level`), 문단·페이지·표 위치를 Rust 색인에 추가하고 SQLite 응답과 같은 구조로 반환.
2. 순위: 같은 질의 모음에 대해 두 backend 결과를 평가하는 소규모 세트(합성 정답 포함)로 Recall@k·MRR 비교. 필요하면 Rust 순위에 SQLite 의 발생 횟수 신호를 반영.
3. 문서별 content hash·extractor 버전으로 변경 감지, 변경 문서만 재색인.
4. 취소·재시작·fallback 장애 시험, `shadow_compare` 로 실제 사용 질의 비교 로그 수집.
5. 1만 문서 SQLite 기준선을 20분 상한 없이(또는 배치로) 확보.
