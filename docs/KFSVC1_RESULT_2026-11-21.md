## 코드 경로와 메모리 정의

- `enum_mft`는 1 MiB 재사용 버퍼로 MFT 레코드를 순회하고 각 이름 레코드를 `Builder`에 넣는다. hard link는 별도 이름 레코드로 들어올 수 있다. 짧은 이름이 열거 결과에 얼마나 포함되는지는 여기서 실측하지 않았다.
- `Builder::finish`는 볼륨별 레코드 번호 → 항목 번호 `RecMap`을 만든다. 현재 `RecMap`은 최대 레코드 번호까지 조밀하게 3바이트/슬롯(표현 범위 초과 시 4바이트) 할당한다. 큰 희소 FRN 공간이면 항목 수 대비 비용이 커지는 유력 후보다.
- `read_usn`은 볼륨마다 최소 64 KiB 버퍼와 변경 묶음 `Vec<Change>`를 만든다. `apply`는 변경을 기존 `Names`에 반영하고, 임계값을 넘으면 `compact` 결과로 교체한다. 변경 묶음은 영구 복사되지 않는다.
- 재빌드 중 질의는 기존 `Names`를 계속 본다. 성공 시 `*g = Some(names)` 대입으로 이전 색인을 교체하며, 별도 보관 참조가 없다면 즉시 drop된다. 실패하면 이전 색인을 유지한다.
- `Searcher` SID 캐시와 deny 캐시는 `NamesService`의 별도 힙이다. `names_status.heap_bytes`에는 포함되지 않는다. `Searcher` 내부 캐시 크기는 별도로 산출하지 않았다.
- 파이프 `names_status.heap_bytes`는 `Names::heap_bytes()`를 그대로 호출한다. 이 값은 각 색인 배열의 `capacity`와 `RecMap` 용량을 합산한 근사치이며, 할당자 오버헤드, 빌드 임시 배열, 서비스 캐시 및 USN 버퍼는 포함하지 않는다. 따라서 프로세스 PrivateUsage와 같은 정의가 아니다.

## 가설 판정과 변경

`RecMap`의 조밀한 최대 FRN 할당은 구현상 확정되지만, 현재 서비스는 RecMap별 슬롯 수/바이트를 내보내지 않는다. 이번 상태 응답의 합계만으로 약 79 B/항목 차이를 RecMap에 귀속할 수 없어 **원인은 미확정**이다. `RecMap`을 희소 자료구조로 바꾸면 부모 연결 구축과 질의 경로에 영향이 있어, 용량 실측과 성능 비교 없이 바꾸지 않았다. `shrink_to_fit`도 기존 KFMEM4에서 구조 용량을 줄이지 못한 것으로 기록되어 있어 호출만 추가하지 않았다.

변경 전후 코드·질의 결과·속도는 동일하며 코드 변경은 없다. 서비스 재시작이 필요한 변경도 없다. 정확한 분해를 위해서는 후속 진단에서 `Names::heap_breakdown()`과 볼륨별 `RecMap::capacity_bytes()`를 상태 응답 또는 별도 계측으로 노출하고 같은 시점에 읽어야 한다.
