# VF1 계획: 가상 폴더를 단축키로 부르는 경량 창 (2026-11-12)

조사는 `docs/VF1_RESEARCH_2026-11-12.md`. 기준 커밋 `d3173daa`, 브랜치 `feature/vfolder-popup`. 이 문서는 설계만 담는다(코드 변경 없음).

**고친 내역(2026-11-12, VF1B)**: 사용자 결정 "가상 폴더 창은 별도 실행 파일로 실행되도록 개발한다"에 따라 (가)를 'kagent 안의 두 번째 창'에서 **별도 실행 파일 `kvf.exe`**로 바꾸고, 자원 목표·배포·단계·프로세스 수명을 그에 맞게 다시 썼다. 조사 문서는 고치지 않았다 — 조사 문서의 Q2 권고("kagent가 떠 있을 때만 동작")는 이 결정으로 전제가 바뀌었다(4절).

## 0. 범위와 제약

### 넣는 것 (이번 범위, 단계 V0~V10)
- 별도 실행 파일 `kvf.exe`. 단축키·트레이 메뉴·`kvf.exe` 실행으로 부르는 가상 폴더 창. 앱 본체·몽땅클립보드(kagent)가 꺼져 있어도 동작.
- 상자(가상 폴더) 고르기, 영역 칸(전체·핵심자료·기초자료·참고자료·임시저장소), 항목 목록.
- 찾기: 고른 상자 안에서 이름·경로로(글자를 치면 바로, 한글 조합 중 글자 포함).
- 열기(Enter·두 번 클릭), 탐색기에서 위치 열기, 원본 위치 열기(`origin_path`가 있을 때).
- 창 틀·크기 조절·최소화·최대화·항상 위·위치 기억은 몽땅클립보드와 같게.
- 명시적 상태 기계(창 상태 + 프로세스 수명)와 kvf 자체 `status.json`.
- 설치·자동 실행·업데이트 교체·끄기(`kvf.exe --install`·`--enable`·`--upgrade-if-stale`·`--disable`·`--status`), CI 빌드와 꾸러미 포함, 앱의 켜기·끄기 한 줄.

### 빼는 것 (다음 범위, 단계 V11~V12는 설계만)
- 파일 끌어 넣기로 추가, 영역 이동, 삭제, 이름 바꾸기, 새 상자 만들기 — 모두 쓰기라 klib.exe가 필요하다.
- 본문 찾기(tantivy), 모든 상자에서 찾기.
- 관계선, 캔버스, 메모 편집, 업무자료함 연결, 내보내기 — 앱 화면에 남긴다.
- 창에서 끌어 내기(다른 프로그램에 파일 놓기), 클립보드로 파일 복사.
- 앱 설정 화면에서 가상 폴더 단축키 바꾸기(이번에는 kvf `settings.json`을 고치고 `kvf.exe --reload`로만).
- kvf의 명령 파이프(이번에는 두지 않는다. 명령은 모두 명령줄 인자 → 창 메시지).

## 1. 결정

### (가) 어느 프로세스에 넣을지 → **B. 별도 실행 파일 `kvf.exe` (사용자 결정, 2026-11-12)**

처음 계획은 A(kagent 안의 두 번째 창)를 권고했다. 그 뒤 사용자가 "가상 폴더 창은 별도 실행 파일로 실행되도록 개발한다"고 정했으므로 B로 확정한다. 아래 표는 A가 거저 얻던 것을 B에서 어떻게 얻는지다.

| A에서 거저 얻던 것 | B(`kvf.exe`)에서 얻는 방법 |
|---|---|
| 이미 상주 | kvf가 스스로 상주한다. 전역 단축키는 누군가 등록하고 있어야 하므로 '부를 때만 띄우기'는 못 쓴다(kagent가 대신 등록해 kvf를 띄우면 몽땅클립보드에 다시 묶인다). 숨긴 동안은 숨은 주 창 하나 + 메시지 고리만 남긴다 |
| 자동 실행 | 자기 Run 값 `HwpAutoDocFit.Kvf` = `"<자료 폴더>\kvf.exe" --hidden --delay 30`(HKCU, 관리자 권한 불필요). kagent의 `HwpAutoDocFit.KAgent`(`kagent/src/settings_menu.rs:251`)와 이름이 달라 서로 건드리지 않는다. 사용자가 켰을 때만 등록(기본값은 Q5) |
| 단축키 체계 | kvf 프로세스가 `RegisterHotKey`로 직접 등록한다. 해석·실패 알림 판정은 kagent의 순수 함수를 같이 쓴다((나), 공용 방식은 아래) |
| klib.exe 없이 읽기 | `winsqlite3.dll` 읽기 전용 직접 열기는 프로세스와 무관하다((마) 그대로). kagent의 `sqlite.rs`를 같이 쓴다 |
| 설치·업데이트 | kagent와 같은 방식을 kvf에 따로 둔다: 꾸러미의 `resources/kvf.exe`(+`.sha256`) → `%LOCALAPPDATA%\HwpAutoDocFit\kvf\kvf.exe`로 복사, 앱 시작 때 `--upgrade-if-stale`(2절) |
| 상태 한 파일 | 상태 파일이 둘이 된다: kagent `...\kagent\status.json`(바뀌지 않음), kvf `...\kvf\status.json`(새로) |

B로 새로 얻는 것: 몽땅클립보드를 켜지 않은 사용자도 쓴다(클립보드 기록 동의와 무관 — kvf는 아무것도 기록하지 않는다). 한쪽이 죽거나 업데이트로 교체돼도 다른 쪽은 그대로다. 몽땅클립보드 코드의 실행 흐름(메시지 처리·메뉴·설정)을 건드리지 않는다.

B의 비용: 프로세스·트레이 아이콘·자동 실행 항목·설치 경로·상태 파일이 하나씩 는다. 꾸러미·업데이트·제거 시험이 하나 더 는다. 개인 메모리 약 1.5~2.0MB 추가(0절).

| 코드 중복 | 없음 | 없음 | 틀·단축키·열기 규칙이 두 벌(사실상 복사 — 지시 위반) |
| 깨질 수 있는 것 | 몽땅클립보드 빌드 구성이 바뀐다. CI에 공용 크레이트 시험 단계 추가 | 공용 파일은 `std`·`windows-sys`·`crate::util`만 써야 한다는 약속이 생긴다(어기면 kvf 빌드가 깨져 CI에서 바로 드러난다) | 고칠 때 두 곳을 맞춰야 한다 |

| 되돌리기 | 크레이트 이동을 되돌려야 한다 | `kvf/` 폴더를 지우면 끝. V1의 옮기기는 남겨도 해가 없다 | `kvf/` 폴더 삭제 |

권고 P2. 이유: 중복이 없으면서 몽땅클립보드에 가는 변화가 가장 작다(빌드 구성·시험 수·lock 불변). P1은 더 반듯하지만 이번 범위에서 몽땅클립보드의 빌드를 바꿀 이유가 없다 — kvf가 자리 잡은 뒤 별도 카드 후보로 남긴다. P3은 복사 금지에 어긋나 뺀다.

P2의 규칙:
1. 공용 파일 목록은 `kvf/src/main.rs` 맨 위 한곳에 `#[path]`로 모은다: `sqlite.rs`·`json.rs`·`util.rs`·`lifecycle.rs`·`frame.rs`·`hotkey.rs`·`open_rules.rs`. 이 일곱 파일 머리에 "kvf도 이 파일을 컴파일한다. `std`·`windows-sys`·`crate::util` 말고는 쓰지 말 것" 주석을 단다(V1).
2. kagent 쪽 옮기기는 내용 변경 없이 한다. `frame.rs`·`hotkey.rs`·`open_rules.rs`는 kagent에서도 `mod`로 그대로 쓰이고 시험도 함께 옮겨 109개가 유지된다.
3. 공용 파일의 시험은 kvf 시험 실행에서도 한 번 더 돈다(같은 시험이 두 크레이트에서 통과해야 한다).
4. kvf가 쓰지 않는 함수 때문에 나는 경고는 kvf 쪽 `mod` 선언에 `#[allow(dead_code)]`를 붙여 끈다(kagent 파일은 그 때문에 고치지 않는다).
5. `open_item.rs`에서 `crate::clip`에 닿지 않는 함수만 `open_rules.rs`로 옮긴다. 이 파일의 세부는 이 세션에서 다 읽지 않았다 — V1 워커가 먼저 읽고, 깨끗이 나뉘지 않으면 멈추고 보고한다.

### (나) 단축키 기본값과 충돌 처리 → **`Win+Shift+F`, 판정 함수는 kagent 것을 같이 쓰고 알림은 kvf 것**

- 기본값 `Win+Shift+F`(Folder). 전역 단축키는 다른 프로그램의 같은 조합을 빼앗으므로 프로그램들이 흔히 쓰는 `Ctrl+Shift+글자`는 피한다. `Ctrl+Shift+F`는 Excel 셀 서식·편집기의 전체 찾기와 겹친다고 알고 있다(이 세션에서 실기 확인 안 함). `Win+Shift+F`가 비어 있는지도 실기 확인이 필요하다(조사 C2). 사용자 영향이 있는 선택이라 Q1로 올린다. 설정 값이라 되돌리기 쉽다.
- 설정은 kvf `settings.json`의 `hotkey`(글자 40자 이하, kagent `hotkey`와 같은 규칙 — `kagent/src/store.rs:150`). 빈 글자면 단축키를 등록하지 않는다(끄기).
- 충돌 처리:
  1. kvf 주 창이 자기 프로세스에서 id 1로 `RegisterHotKey`를 부른다. id는 프로세스·창마다 따로라 kagent의 id와 무관하다. kagent의 `register_hotkey`는 **고치지 않는다**.
  2. 해석 `parse_hotkey`와 실패 판정 `hotkey_failure_notice`·`hotkey_failure_body`는 V1에서 `kagent/src/hotkey.rs`로 옮긴 것을 같이 쓴다 — 같은 조합의 연속 실패는 한 번만 알린다(몽땅클립보드와 같은 동작).
  3. 알림은 kvf 트레이 아이콘의 풍선으로 낸다. 제목 "가상 폴더 단축키를 쓸 수 없습니다", 본문은 `hotkey_failure_body` 그대로("Win+Shift+F는 다른 프로그램이 이미 쓰고 있습니다. 트레이 아이콘을 눌러 열 수 있고…"). 몽땅클립보드 쪽 글은 글자 하나 바뀌지 않는다(기존 시험 `invalid_hotkey_notice_reason_and_deduplication`이 본문 앞부분을 검사한다 — 시험도 함께 옮긴다).
  4. 몽땅클립보드와 같은 조합: kvf가 등록 직전에 kagent `settings.json`(`%LOCALAPPDATA%\HwpAutoDocFit\kagent\settings.json`, `kagent/src/main.rs:378`)의 `hotkey`를 **읽기만** 한다(파일이 없거나 못 읽으면 kagent 기본값 `Ctrl+Shift+V`로 본다, `store.rs:60`). 해석한 조합이 같으면(순수 함수 `same_hotkey`) kvf는 등록하지 않고 "몽땅클립보드와 같은 단축키입니다"로 알린다. kagent가 꺼져 있어도 같은 판정을 한다 — 나중에 kagent가 켜질 때 kvf 때문에 실패하지 않게. 이 읽기는 등록할 때(시작·`--reload`)만 한다(감시·폴링 없음). 사용자가 나중에 몽땅클립보드 단축키를 kvf와 같게 바꾸면 kagent가 자기 알림을 낸다(기존 동작).
  5. kvf `status.json`에 `hotkey`, `hotkey_ok`를 싣는다. 트레이 메뉴 '가상 폴더 열기'와 `kvf.exe` 다시 실행으로 단축키가 막혀도 열 수 있다.

### (다) 상태 기계

대원칙(운영 규칙 0절)에 따라 상태를 값으로 두고, 전이는 순수 함수 한곳에서만 한다. 상태는 두 층이다: **프로세스 수명**(`enum Proc`)과 그 안의 **창 상태**(`enum View`). 창 처리 코드는 사건을 만들고 '할 일'을 실행할 뿐 상태를 직접 바꾸지 않는다. 몽땅클립보드 창처럼 플래그(`minimized`)와 `IsWindowVisible`을 섞어 읽지 않는다.

#### 프로세스 수명

| 상태 | 뜻 | 갖고 있는 것 |
|---|---|---|
| `NotRunning` | 프로세스 없음 | 디스크의 `kvf.exe`·`settings.json`뿐. `status.json` 없음 |
| `Starting` | 인자 해석 → 뮤텍스 → 설정 읽기 → 숨은 주 창 → 단축키·트레이 등록 | 뮤텍스 |
| `Resident(View)` | 상주. `View`가 `Hidden`이면 메시지 고리만 돈다 | 뮤텍스, 주 창, 단축키(성공했을 때), 트레이 아이콘, `status.json`. 목록 창은 처음 부를 때 만든다(시작할 때 만들지 않음) |
| `Exiting` | 정리 중 | — |

| 지금 | 사건 | 다음 | 할 일 |
|---|---|---|---|
| `NotRunning` | `kvf.exe`(인자 없음) | `Starting` → `Resident(Loading)` | 상주 시작, 창 보이기, DB 읽기 |
| `NotRunning` | `kvf.exe --hidden`(자동 실행·앱의 켜기) | `Starting` → `Resident(Hidden)` | 상주 시작. DB를 열지 않는다 |
| `NotRunning` | `--quit`·`--reload` | `NotRunning` | 없음(뮤텍스를 잡았다가 놓고 끝냄) |
| `Starting` | 뮤텍스가 이미 있음(이미 떠 있음) | 이 프로세스는 끝남 | 먼저 뜬 창에 메시지를 보내고 종료 코드 0. 먼저 뜬 창을 못 찾으면 아무것도 하지 않고 끝냄 |
| `Starting` | 주 창·뮤텍스 만들기 실패 | `Exiting` | 종료 코드 1. 단축키 등록 실패는 종료 사유가 아니다(`hotkey_ok=false`로 상주) |
| `Resident(v)` | 부름(단축키·트레이·둘째 실행의 `WM_KVF_SHOW`) | `Resident(창 전이 표의 다음 상태)` | 창 전이 표대로 |
| `Resident(v)` | `WM_KVF_RELOAD` | `Resident(v)` | 설정 다시 읽기, 단축키 다시 등록, 트레이 갱신, `status.json` 갱신 |
| `Resident(v)` | 창 닫기 단추·Esc·바깥 클릭 | `Resident(Hidden)` | 창만 숨긴다. **프로세스는 끝내지 않는다** |
| `Resident(v)` | 트레이 '가상 폴더 끝내기'·`--quit`(`WM_CLOSE`)·`--disable`·업데이트 교체 | `Exiting` | 아래 정리 |
| `Resident(v)` | 로그오프·종료(`WM_ENDSESSION`) | `Exiting` | 아래 정리 |
| `Exiting` | — | `NotRunning` | 창 위치·마지막 상자 저장(바뀌었을 때만), 단축키 해제, 트레이 아이콘 제거, `status.json` 삭제(kagent와 같음 — 떠 있는지의 표시), 뮤텍스 닫기 |

비정상 종료(강제 종료): `status.json`이 남는다 → 읽는 쪽(앱·`--status`)은 `pid`가 살아 있는지로 판정한다(kagent와 같은 방법, `docfit_app/kagent_client.py:105-116`). 뮤텍스는 프로세스와 함께 사라지므로 다음 실행이 막히지 않는다. 자동 재시작은 하지 않는다(감시 프로세스를 두지 않는다) — 다음 로그인의 자동 실행이나 사용자의 다시 실행으로 뜬다.

#### 창 상태

| 상태 | 뜻 | 화면 | 메모리 |
|---|---|---|---|
| `Hidden` | 닫힘 | 안 보임 | 목록 없음(비움), DB 연결 없음 |
| `Loading` | 부름을 받아 DB를 읽는 중 | 틀 + "불러오는 중" | — |
| `List { box, space }` | 상자·영역의 목록 | 목록 | 고른 상자의 항목만 |
| `Search { box, query }` | 찾기 글자가 있음 | 거른 목록 | 같음 |
| `Empty(이유)` | DB 없음·상자 없음·항목 없음 | 이유 한 줄 + 할 수 있는 일 | — |
| `Failed(오류)` | DB를 못 읽음(잠김·손상·`winsqlite3.dll` 없음) | 오류 글 + "F5로 다시" | — |
| `Minimized(이전 상태)` | 숨겼지만 상자·영역·찾기·선택 유지 | 안 보임 | 목록 유지 |

'항목 열기'와 '메뉴 열림'은 상태가 아니라 할 일이다(끝나면 곧바로 다음 상태가 정해진다). '끌어 넣기'(`DropHover`, `Adding`)는 다음 범위에서 추가한다.

전이:

| 지금 | 사건 | 다음 | 할 일 |
|---|---|---|---|
| `Hidden` | 부름(단축키·트레이·둘째 실행) | `Loading` | 창 보이기(처음이면 만들기), DB 읽기 |
| `Loading` | 읽기 성공(항목 있음) | `List` | 그리기 |
| `Loading` | 읽기 성공(없음) | `Empty` | 그리기 |
| `Loading` | 읽기 실패 | `Failed` | 그리기 |
| `List` | 글자 입력 | `Search` | 메모리 목록 거르기 |
| `Search` | 글자를 다 지움·Esc(글자 있음) | `List` | 거르기 |
| `List`·`Search` | 상자 바꿈 | `Loading` | 그 상자 읽기 |
| `List`·`Search` | 영역 칸 바꿈 | `List`(찾기 글자 지움) | 거르기 |
| `List`·`Search` | Enter·두 번 클릭 | 붙박이면 그대로, 아니면 `Hidden` | 열기. 실패하면 상태 유지 + 알림 + 다시 읽기 |
| `List`·`Search`·`Empty`·`Failed` | F5 | `Loading` | DB 읽기 |
| 보이는 상태 모두 | Esc(글자 없음)·닫기 단추·바깥 클릭(붙박이 아님) | `Hidden` | 숨기기, 목록 비우기 |
| 보이는 상태 모두 | 최소화 단추 | `Minimized(지금)` | 숨기기 |
| 보이는 상태 모두 | 부름(단축키, 붙박이) | `Hidden` | 숨기기(몽땅클립보드와 같은 토글) |
| 보이는 상태 모두 | 부름(둘째 실행·트레이) | 그대로 | 창을 앞으로 가져오기만 한다(실행했는데 창이 사라지면 안 된다) |
| `Minimized(s)` | 부름 | `Loading`(끝나면 s의 상자·영역·찾기·선택 복원) | 보이기, DB 다시 읽기 |

불가능한 전이(시험으로 막는다): `Hidden`에서 열기·찾기·영역 바꿈, `Loading`에서 열기, `Empty`·`Failed`에서 열기, `Minimized`에서 키 입력 처리, `Starting`·`Exiting`에서 부름 처리. DB 읽기는 주 스레드에서 한다(200ms 상한, 작업 스레드 없음). 그래도 결과에 번호(`seq`)를 붙여 번호가 다르면 버린다(`popup.rs:357-362`와 같은 방법 — 나중에 읽기를 스레드로 옮겨도 규칙이 그대로다).

대원칙 세 축:
- UX: 지금 무엇을 하고 있고 왜 비어 있는지 항상 한 줄로 보인다(`Empty`의 이유, `Failed`의 오류). 닫기는 숨기기이고 끝내기는 트레이 메뉴라는 것이 메뉴 글에 드러난다.
- DX: 상태·전이가 한 파일의 표와 순수 함수이고 창 없이 시험한다.
- AX: kvf `status.json`에 `version`, `pid`, `hotkey`, `hotkey_ok`, `view`(`hidden`·`loading`·`list`·`search`·`empty`·`failed`·`minimized`), `box`, `items`, `error`를 **바뀔 때만** 쓴다. 파일이 없으면 떠 있지 않은 것이다.

몽땅클립보드 창의 암묵적 상태(`minimized`·`sticky_popup`·`popup_collapsed`·`restore_rect`)는 이번에 고치지 않는다(아무것도 깨뜨리지 않기). 같은 방식으로 옮기는 일은 별도 카드 후보로 남긴다.

### (라) 첫 화면에서 할 수 있는 일

화면(위에서 아래): ① 머리글 '가상 폴더' + 상자 이름(누르면 상자 목록 메뉴) + 항상 위·최소화·최대화·닫기 ② 영역 칸: 전체·핵심자료·기초자료·참고자료·임시저장소(←→·Tab) ③ 찾기 줄(글자가 있을 때만) ④ 목록(종류 표시·이름·영역, ↑↓·PgUp·PgDn·Home·End·휠).

끌어 넣기를 다음으로 미루는 이유: 사본 만들기·링크와 정션 거부·자기 폴더 복사 방지·색인 갱신이 모두 klib 안에 있고(`klib/src/db.rs:263-307`, `361-443`), kvf가 이를 다시 구현하면 원본 보호 규칙이 두 곳으로 갈린다. klib.exe는 앱 꾸러미 안에만 있고 사용자 자료 폴더에 설치되지 않으므로(kvf는 앱 꾸러미 위치를 모른다 — 포터블은 실행할 때 푸는 위치가 따로다) 설치 절차부터 넓혀야 한다. 읽기와 열기는 klib 없이 된다.

### (마) klib DB를 읽는 방식 → **읽기 전용으로 직접 열기**

| 기준 | A. `winsqlite3.dll`로 읽기 전용 직접 열기 (권고) | B. klib 파이프 |
|---|---|---|
| 단독 실행 | 된다. klib.exe가 없어도 읽는다 | klib.exe가 kvf 옆에 설치돼 있어야 하고, 부를 때마다 띄워야 한다 |
| 속도 | 프로세스를 띄우지 않는다. 파일 하나 열고 질의 두 번 | klib.exe 첫 실행 시간 + 파이프 왕복. klib는 tantivy까지 든 큰 실행 파일이다(크기·시작 시간 미측정) |
| 메모리 | 읽는 동안만 연결 | klib.exe가 60초 동안 떠 있다 |
| 동시 접근 | WAL이라 읽는 쪽이 klib의 쓰기를 막지 않는다. 쓰지 않으므로 충돌 없음 | 요청이 klib 안에서 줄을 선다(안전) |
| DX | 표 구조를 kvf도 알아야 한다 → 구조가 바뀌면 두 곳을 고친다 | 표 구조는 klib만 안다 |
| 깨질 것 | 없음(읽기만) | klib 설치 절차 변경 |

권고 A(프로세스 결정과 무관하게 그대로). 구조 결합은 다음으로 줄인다: 질의는 `box`의 5개 열과 `item`의 9개 열만 읽고, `origin_path`·`managed_path` 열이 없는 예전 DB는 `PRAGMA table_info(item)`로 확인해 빈 글자로 읽는다(klib가 열을 붙이는 방식과 같음, `klib/src/db.rs:113-119`). 표가 없거나 질의가 실패하면 `Failed`로 간다. klib 쪽에는 "이 열을 kvf 가상 폴더 창이 읽는다"는 주석과 구조 고정 시험을 둔다(V10).

읽기 규칙:
1. `SQLITE_OPEN_READONLY`로 연다. 파일이 없으면 만들지 않고 `Empty(자료 없음)`.
2. 실기에서 WAL DB가 읽기 전용으로 안 읽히면(조사 C1) '읽기·쓰기 열기(만들기 없음) + `PRAGMA query_only=ON`'으로 바꾼다. 어느 쪽이든 `CREATE`·`ALTER`·`INSERT`·`UPDATE`·`DELETE`·`PRAGMA journal_mode`는 코드에 없다.
3. `busy_timeout` 200ms. 넘으면 `Failed("다른 작업이 자료를 쓰는 중입니다. F5로 다시")`.
4. 부를 때마다 상자 목록 + 고른 상자의 항목을 읽고 연결을 닫는다. 보이는 동안은 메모리 목록만 쓴다. 다시 읽기는 부름·상자 바꿈·F5·열기 실패 때만.
5. 항목 상한 5,000개(넘으면 "5,000개까지만 보입니다. 앱에서 보세요" 한 줄). 숨기면(`Hidden`) 목록을 비운다.
6. `winsqlite3.dll`은 처음 읽을 때 올린다(상주만 하고 한 번도 부르지 않은 프로세스는 올리지 않는다).

앱이 떠 있을 때의 규칙: 앱(→klib)이 쓰는 동안 창은 읽기만 한다. 창이 보이는 사이에 앱에서 옮기거나 지운 항목은 목록에 남아 있을 수 있다 → 열 때 파일이 없으면 "자료가 옮겨졌거나 지워졌습니다" 알림 뒤 자동으로 다시 읽는다. 창은 klib.exe를 띄우지 않고 색인 폴더를 열지 않는다.

여는 경로 검사(순수 함수 `openable`): `managed_path`가 비어 있지 않고, `..`이 없고, 부모 폴더가 `자료 폴더\<box_id>\<space>`와 같고, 파일이나 폴더가 있고, 실행 파일 확장자가 아니다. 링크는 `safe_web_url`(V1에서 `open_rules.rs`로 옮긴 것). 어긋나면 열지 않고 이유를 알린다. klib의 `validate_copy_location`(`klib/src/db.rs:315-330`)과 같은 뜻이되 링크·정션 검사는 kvf에 그 함수가 없어 이번에 넣지 않는다(읽기·열기만 하므로 klib가 사본을 만들 때의 검사에 기댄다. 남는 위험으로 적는다).

## 5. 남는 위험

- kvf가 klib의 표 구조를 직접 읽는다. V10의 구조 고정 시험이 없으면 klib 쪽 열 이름 변경이 조용히 창을 깨뜨린다.
- kvf가 kagent의 소스 파일 일곱 개를 같이 컴파일한다(P2). 그 파일에 kagent 전용 의존이 새로 들어가면 kvf 빌드가 깨진다 — CI에서 드러나지만 kagent만 고치던 사람은 로컬에서 모를 수 있다. 파일 머리 주석과 CI의 kvf 단계로 막는다.
- (해소, V1) `open_item.rs`는 `open_rules.rs`로 깨끗이 나뉘었다 — `forbidden`·`extension`·`safe_web_url`과 상수 둘은 `std`만 쓴다.
- 자원 목표(개인 메모리 1.5~2.0MB, exe 0.5MB, 시작 100ms)는 kagent 실측에서 미룬 **추정**이다. V2의 빈 상주 프로세스 실측으로 확정한다.
- 여는 경로의 링크·정션 검사가 kvf에는 없다(klib가 사본을 만들 때 한 검사에 기댄다). 누군가 사본 폴더를 손으로 정션으로 바꾸면 창은 그것을 따라 연다. V7에서 `GetFileAttributesW`로 재분석 지점 검사를 넣을지 총괄이 정한다(권고: 넣는다, 함수 하나·시험 하나).
- `Win+Shift+F`가 비어 있다는 것은 확인하지 않았다(C2 — V0에서도 하지 않았다. 사용자 결정 Q1: 충돌하면 등록 실패 알림).
- 서명되지 않은 새 실행 파일이 자동 실행·전역 단축키를 쓴다. 구청 PC의 보안 프로그램이 kagent는 허용하고 kvf는 막을 수 있다(실기 미확인).
- 사용자가 나중에 몽땅클립보드 단축키를 kvf와 같게 바꾸면, 먼저 등록한 kvf가 이기고 몽땅클립보드가 실패 알림을 낸다(kvf는 등록할 때만 비교한다). kvf를 `--reload`하거나 다시 켜면 kvf가 물러난다.
- 설치형을 제거해도 kagent는 남는다(기존 동작, 이번에 고치지 않음). kvf만 `[UninstallRun]`으로 끄면 두 프로그램의 제거 동작이 달라진다 — 총괄이 kagent도 같이 맞출지 별도 카드로 정한다.
- 앱을 한 번도 다시 켜지 않으면 업데이트 뒤에도 예전 kvf가 계속 돈다(kagent와 같은 성질).
- `popup.rs`의 그리기·입력 처리 세부를 읽지 않았다(조사 문서 '미확인'). V6 워커가 먼저 읽고, 공용으로 더 뺄 것이 있으면 V1과 같은 '옮기기만' 규칙으로 따로 커밋한다.
- 설정 화면(Flutter)의 몽땅클립보드 켜기 흐름을 읽지 않았다. V9의 화면 파일 목록은 그 단계 워커가 정한다.
